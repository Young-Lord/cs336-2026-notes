# 推理工作负载概览：重要性、度量与 Transformer 记法

欢迎回来。上一讲 Tatsu 讲了缩放定律，这一讲我们暂时离开那个话题，转向**推理（inference）**。推理的问题很明确：你已经训练好了一个模型，现在给你一个 prompt，你要产生响应——通常要求尽可能准确、尽可能快。推理在整门课里只占一讲，但它正变得越来越重要，而且出现在很多地方。

## 推理为什么重要

模型训练好之后，你当然不会让它闲着。如果你是研究者，你可能只是在论文里放一张"我的模型表现如何"的图；但对其他人来说，你是真的要去**使用**这个模型。使用看起来是什么样？可以是和 AI 助手或聊天机器人对话、做代码补全（code completion）。如今 agent 非常流行，而这需要推理。还有批量数据处理（batch data processing）——比如你有一 PB 的数据要交给语言模型处理。推理也用于**评测（evaluation）**，尤其是需要生成的评测。它甚至出现在训练内部：如果你在做强化学习，你需要一个模型，生成 rollout、给它们打分，再相应更新权重。所以推理无处不在，而"效率"——这门课的主题——比以往任何时候都更重要。

即使只看实际使用的角度，训练与推理的成本结构也完全不同：**训练是一次性成本（one-time cost）**。它可能极其昂贵，但一旦做完就结束了。**推理是重复性成本（repeated cost）**，你每天都要承担。举例来说，OpenAI 估计每天要生成约 **8.6 万亿 token**；作为参照，本讲引用的 DeepSeek v4 用了 **32 万亿 token** 做训练。也就是说，在不到 4 天的时间里，OpenAI 需要产出的 token 数（以及相应的计算量）就超过了训练一个大模型所用的 token 数。所以哪怕只是把推理变快 10%，甚至 2 倍，都是大事。

过去一年里推理的重要性还在上升，这与 **agent** 的兴起有关。曾几何时，我们把语言模型主要当作聊天机器人或助手：输入 prompt、得到响应，目标是让人类去读这段响应。但在 agent 的世界里，事情变成：一个 query 进来，agent 会做一大堆事情——思考、推理、调用工具、自我审视（introspect），最后才产出一段给人类读的输出。**也就是说，agent 产出的大部分 token 并不是给人读的。** 因此你应该把"生成的 token 数量"直接理解为"花费的计算量"。在聊天场景里，人类阅读速度是瓶颈，推理到一定程度就"够快"了；但在 agent 场景里，你从推理中挤压出更多价值的能力几乎没有上限。

### 商业格局与开源工具

正因为如此，有很多人（和公司）在做推理：

- **封闭模型服务商**：OpenAI、Anthropic、Google 等，必须服务自己的模型，推理对他们是大生意；
- **开源权重模型服务商**：Together、Fireworks、Baseten、DeepInfra、Groq、Cerebras 等，为开放权重模型提供推理服务。

开源社区里也有大量工具包：

- **vLLM**：来自 Berkeley，首创了 PagedAttention，目前最流行，是很好的默认选择；
- **SGLang**：也来自 Berkeley，首创 RadixAttention，特别适合 agent 工作负载（但还没有那么流行）；
- **TensorRT-LLM**：来自 NVIDIA，在 GPU 上高度优化、非常快，但更"窄"（适用面有限）；
- **llama.cpp**：纯 C++ 实现，支持 CPU 推理，可以本地运行。

## "快"是什么：三种度量

既然推理如此重要，那"快"到底指什么？有三种度量捕捉"快"的不同侧面，它们适用于不同场景、有不同的权衡：

1. **首 token 时间（time-to-first-token，TTFT）**：用户等待第一个 token 产生之前的时间。你向 ChatGPT 发出 query，经过若干毫秒，第一个 token 开始流出来——这段时间就是 TTFT。它对于**交互式应用**很重要，因为这段时间你只能干等着什么也不做；而一旦 token 开始流出，就不必太快——反正人类阅读速度也有限。
2. **延迟（latency）**：以单个用户为视角，token 流出的速度有多快（秒/token）。这对交互式应用同样重要。
3. **吞吐（throughput）**：以整个系统为视角，对许多查询而言 token 产生的总速度（token/秒）。它适用于**批量处理**：你有一堆数据要交给语言模型处理，只关心整个任务尽快完成，单个查询早一点晚一点无所谓。

延迟（或其倒数）与吞吐显然密切相关。一般来说，很多手段会让延迟和吞吐同时变好；但我们后面会看到，**这里确实存在一个权衡**。

## 训练与推理的根本差异

无论用上面哪个度量衡量效率，有一个**全讲最重要的一句话（high-level takeaway）**：训练时你**一次性看到所有 token**。在监督式微调里，你看到全部 token，可以**沿序列并行化（parallelize over the sequence）**。回想 Transformer 里的注意力与 MLP 计算——序列只是一个维度，是一大块张量，你可以把所有 token 一次处理完。而推理做不到：由于**自回归**（autoregressive）的特性，你必须**逐 token、顺序地生成**。这就是为什么推理是与训练非常不同的工作负载——你不能沿序列并行，因此很难达到高算术强度（arithmetic intensity）、很难让计算单元满负荷运转。

## 复习：Transformer 的形状记法

先建立记法，方便理解后面的图。我们用符号来同时表示**维度本身**和**维度的长度**（类似 einops 的风格）：

- $B$：批（batch）维度，也就是序列的个数；
- $T$：序列维度，也就是 token 的个数；
- $D$：模型维度（model dimension）；
- $H$：头维度（head dimension）。

再看维度之间如何互动。看这个例子：一个形状为 $BTD$ 的张量与一个 $DH$ 的矩阵相乘，得到 $BTH$。这里有两类维度：

- **收缩维（contracting dimension，红色）**：出现在两个操作数中、从结果中消失。比如 $BT\cancel{D} \times \cancel{D}H \to BTH$ 里的 $D$；
- **常规维（regular dimension，黑色）**：只出现在一个操作数中、保留在结果中。

另一个例子：如果两个操作数是 $BD \times BD \to B$，其中 $D$ 是红色收缩维，而 $B$ 是另一种维度：

- **批处理维（batching dimension，蓝色）**：出现在两个操作数中、但**保留在结果中**，不做收缩或归约。

这里的直觉是：对于每个序列、每个 token 位置，我们有一个向量，把它乘以一个矩阵；或者取一堆张量之间的点积。

在这个记法下，Transformer block 的完整描述画出来像一个电路图，细节很多，但讲者认为这大概是 Transformer 最"干脆利落"（crisp）的定义——市面上很多 Transformer 的描述让你很难搞清楚到底发生了什么，而这副图精确告诉你每个张量的形状，还能帮你推理依赖关系。对一层 Transformer block：取上一层激活 $X$，先过注意力（attention），再过 MLP。注意力里，把 $X$ 用 query 矩阵、key 矩阵、value 矩阵投影：query 的形状是 $B \times T \times N \times H$（$N$ 是头的个数、$H$ 是每个头的维度）；而 key 和 value 用的不是 $N$ 而是 $K$——我们后面会看到，这是**可能更少的 key-value 头数**。然后做注意力计算，注意里面有批处理维：$B$ 同时出现在两个操作数中，我们在头维度上收缩。我们后面会回到"为什么这个 $B$ 让推理变难、为什么注意力是推理的瓶颈"这个问题。MLP 则非常简单直接：就是几次矩阵乘法——gating 矩阵、up 投影和 down 投影。

按惯例约定几个关系：

$$F = 4D$$

MLP 把模型维度 $D$ 上投影到 4 倍维度，所以看到 $F$ 就把它想成 $4D$。模型维度被切分到 $N$ 个头上：

$$D = N \cdot H$$

而头的个数在**分组查询注意力**（grouped-query attention，GQA）的情况下按"组"进一步划分：

$$N = K \cdot G$$

（$K$ 个组、每组 $G$ 个头。这里课堂上还有个小插曲，见下。）

最后是两个都表示"序列维度"的变量 $S$ 与 $T$，它们的区别是：$S$ 表示**输入 token 数**（prefill 阶段处理的 prompt），$T$ 表示**输出 token 数**。训练时两者相同——我们以 $S$ 个输入 token 为条件、预测 $T$ 个输出 token；推理时 $T = 1$（每次只生成一个 token），$S$ 是输入。

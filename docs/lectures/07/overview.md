# 开场与动机：为什么需要多 GPU 并行

欢迎回来。今天我们来讲**并行（parallelism）**。回顾一下：上一讲我们讲的是如何**让一块 GPU 变快**——我们写 kernel，真的把这块 GPU 从里到外看了一遍。这一讲，我们要讲的是如何**利用多块 GPU 让代码更快**。

## 从一块 GPU 到一千块 GPU

你脑子里应该有的画面大概是这样的：过去这一周我们盯着的只是其中一个盒子——一块 GPU。还记得它的内部吗：高带宽内存（high-bandwidth memory，HBM）、L2 缓存、L1 缓存、寄存器，还有一堆流式多处理器（streaming multiprocessor，SM）。现在画面要扩展了：你不再只有一块 GPU，而是有四块、甚至一千块 GPU，它们之间要连起来（我们稍后会讲它们是怎么连的），然后你得想清楚怎么利用所有这些算力去训练模型。

有意思的是，把镜头拉远一点，单 GPU 情形和多 GPU 情形在本质上是**一模一样的**：**计算（compute）——算术逻辑单元、tensor core 等等——离数据（data）很远**。对单块 GPU 来说，"很远"意味着数据躺在那一头的 HBM 里；而对多块 GPU 来说，你需要的那份数据可能整个儿在**另一块 GPU** 上，你得想办法把它"铲"过来。但原则是相同的，因为这场游戏的本质始终是：

> **编排计算，以避开数据传输瓶颈（orchestrate the computation to try to avoid data transfer bottlenecks）。**

用很多 GPU 非常容易，但**把它们用得很高效很难**。这是贯穿本讲的态度。

顺着这个思路，我们可以（稍微大胆一点地）构造一条**广义的层级（generalized hierarchy）**，从局部到全局：

- 最靠近 SM 的层面：**单节点、单 GPU**，里面是 L1 缓存 / shared memory——这是**最快**的；
- 再往外：**单节点、单 GPU** 的 **HBM**——上一讲我们哀叹它太慢，但在本讲里，**HBM 要算"快"的**；
- 再往外：**单节点、多 GPU**，GPU 之间通过 **NVLink 与 NVSwitch** 相连；
- 最外面：**多节点、多 GPU**，只能依赖 **InfiniBand** 或 **Ethernet**（取决于你的网络）。

![](/lectures/07/gpu-node-overview.png)

所以你看，这和内存层级是同构的：越往外越慢，而"GPU 越多、节点越多，互联越慢"和"内存越大、离得越远，带宽越低"其实是同一件事。

## 上一讲 vs 这一讲：减少访存 vs 减少通信

上一讲我们讲了不少**改进内存访问**的技巧：**融合**（fusion）与**分块（tiling）**——读进 shared memory，尽可能在里面把事做完，再写回去。这一讲我们要讲的是**如何减少跨 GPU 的通信量**，手段是适当地**复制（replicate）与切分（shard）**。你在脑子里可以把两条线对齐：上一讲优化的是"数据在 SM 与 HBM 之间的移动"，这一讲优化的是"数据在 GPU 与 GPU 之间的移动"。

## 为什么需要多 GPU？

"为什么要多 GPU？"——显然的答案是**你想扩展规模**，但说得更精确一点，理由其实有两条：

1. **放不下**：你的参数、激活、梯度、优化器状态装不进单块 GPU 的 HBM。举个例子：B200 有 192 GB 显存，但如果你要训练一个 **1 万亿（trillion）参数**的模型，那显然塞不进单块 GPU；
2. **想更快**：即使模型能塞进单块 GPU，你也许还是想把它摊到更多 GPU 上、用更多 FLOPs，从而训练得更快。

于是常常要面临一些取舍：你可以把模型都放进少数几块 GPU，但那样"核心"就少；而如果你摊开用更多 GPU，就得**为通信买单**。怎么并行、并行到什么程度，正是一个需要你亲自计算的问题。

## 本讲的结构与运行方式

在进入正题之前，先交代一句本讲的运行方式。之前几讲的讲义是"你执行它，它把一切都展示给你看"；这一讲如果**直接运行**，代码会走 **multiprocessing**（为每个 rank 启动独立进程）。但在课堂上逐行 trace 时，我们用了一种特殊的**单进程模式**（把分布式函数替换成空操作），这样讲起来才跟得上。如果你想看这一讲真正的标准输出（比如每个 rank 的 print），直接以 multiprocessing 方式运行即可。

本讲分两大部分：

- **第一部分：分布式通信与计算的积木（building blocks）**。先讲**编程模型**（集合通信原语 collective operations），再讲一点**硬件**（GPU 怎么连），然后落到 **PyTorch** 里的实现——这也正是你**作业二**（assignment 2）要做的事；
- **第二部分：真正的训练**。看三种并行策略——**数据并行（data parallelism）**、**张量并行（tensor parallelism）**、**流水线并行（pipeline parallelism）**，它们各自以不同方式"切"模型。演示用的是**深度 MLP**（而不是完整的 Transformer），因为 MLP 正是 Transformer 里真正的计算瓶颈所在，核心计算完全能说明问题。

# 动态工作负载：连续批处理、分页注意力与总结

最后一节讲**推理服务（serving）**。前面的分析都假设了一个干净的设定：整齐的 batch、同长度的序列。但真实世界不是这样——你的使用场景是服务一个实时网站，用户随时来跟模型聊天。请求在不同时间到达、有共享前缀、长度也各不相同，远不是训练那种"一大块、同样 token 数、同时处理"的整齐 block。这一节的两个核心系统思想都来自操作系统（OS）：**连续批处理**（调度）与**分页注意力**（paging）。

## 问题：批处理在实时流量下很棘手

讲义把问题归纳为三点：

1. **请求在不同时间到达**——为了攒 batch 而等待，对早到的请求很不好；
2. **序列有共享前缀**——比如系统提示（system prompt）、对同一个 prompt 生成多个样本；
3. **序列长度各不相同**——padding 到一样长很浪费。

## 连续批处理（continuous batching）

**连续批处理（continuous batching）** 来自一个很早期的系统 **Orca**。它解决的问题是：请求到达的时间参差不齐，如果按传统方式"攒够一批再一起跑"，早到的请求就得干等。

Orca 的做法是**迭代级调度（iteration-level scheduling）**：不是等整个 batch 都生成完，而是**一步一步地解码**：

- 每一步，为当前 batch 里的所有序列各解码一个 token；
- 如果某个序列生成完了，就把它**移出**（evict）batch；
- 新请求到达时，随时**加入** batch。

所以"连续"的意思是：batch 是**动态更新**的——完成的老序列被移走、新序列被加进来。这样服务端就不需要为了凑一个 batch 而等待。

但这带来一个新问题：我们前面所有的算术强度分析都假设"批处理时所有序列形状相同"（张量每个切片维度一样）。可现在每个请求长度不同，怎么办？

### 选择性批处理（selective batching）

答案是把计算**分两类**处理。假设有三个请求，长度分别是 3、9、5：

- **注意力计算**：没法合并。注意力本质上依赖序列长度——一个 $9 \times 9$ 的注意力矩阵和一个 $3 \times 3$ 的矩阵没法有效共享同一个张量，所以**每个序列单独算**；
- **非注意力部分（MLP 等）**：这部分占了大量 FLOPs，而且**不关心序列内部结构**——可以把所有序列**拼接（concatenate）成一个 mega-sequence** 再一次性处理，比如 $[3 + 9 + 5, H]$ 的一个大矩阵乘法。

由于 MLP 是计算大头，这种"注意力分开、MLP 合并"的**选择性批处理**让长度不齐不再是灾难。

## 分页注意力（PagedAttention）

最后一个系统想法来自 **vLLM** 论文（PagedAttention 正是 vLLM 成名作；现在的 vLLM 加了很多别的东西，但这是它当年的核心想法）。问题是：**KV cache 到底怎么存在内存里？**

### 碎片化问题

传统做法是：请求进来后，为它的 prompt 和响应**一次性分配一整段连续的 KV cache**（最多到某个最大长度，比如 1024）。

![传统分配带来的碎片化](/lectures/10/paged-attention-fragmentation.png)

这有严重的**碎片化**（fragmentation）问题——就像当年硬盘的碎片化，还得定期 defrag：

- **内部碎片化（internal fragmentation）**：你按"最大长度"分配了一整段内存，但实际生成可能远没有那么多 token——多出来的内存白白占着，放不了别的东西；
- **外部碎片化（external fragmentation）**：不同请求之间留下的空隙太小，无法被有效利用，纯粹浪费。

### 解决方案：像操作系统一样分页

做系统的人对这个问题太熟悉了——"我们以前就解决过一次"，于是直接复用操作系统的想法：**把序列的 KV cache 划分成非连续的块（blocks）**，就像虚拟内存的分页。比如 "Four score and seven years ago our fathers brought forth" 这个序列被切成 4 个 token 一块的小块；块放在哪里不重要，只要对齐到块边界、靠索引（index）追踪每块在哪，就都能工作。

![分页：把 KV cache 切成块，非连续存放](/lectures/10/paged-attention-blocks.png)

这样两个请求共享 KV cache 就变得很自然：

![两个请求共享 KV cache：块可以交织存放](/lectures/10/paged-attention-logical.png)

只要维护好索引，各块散落内存各处也没关系。具体而言，有几类非常有用的共享场景：

![多种 KV cache 共享类型](/lectures/10/paged-attention-sharing.png)

- **共享系统提示**：很多人用同一个系统提示（system prompt），那就把系统提示的 KV cache **只算一次**、让所有请求复用——省下每个请求重算 KV cache 的开销；
- **一个 prompt 生成多个响应**：很多应用需要对同一个 prompt 采样多个不同输出（比如程序综合里采样多份候选程序）——共享 prompt 部分的 KV cache，只让响应部分各自独立。

后一种场景用到了**写时复制**（copy-on-write）语义：

![共享前缀 + 写时复制：多个生成从同一前缀分叉](/lectures/10/paged-attention-parallel.png)

比如从 "Four score and seven years ago are ____" 生成多个续写：前缀 "Four score and seven" 的 KV 块共享；两个样本若恰好在某个位置采到了同一个 token，就继续共享；一旦采到不同的 token，就把块**分裂（split）**，各自继续。这样前缀缓存共享得尽可能多。

### vLLM 的其他优化

vLLM 还有一堆别的优化（讲者时间有限没细讲），比如：把块读取与注意力融合的 kernel（减少 kernel 启动开销）、使用最新的 FlashAttention / FlashDecoding kernel、用 CUDA graphs 避免 kernel launch 开销。

总的思想是：**用操作系统的隐喻（分页）来管理推理系统的内存**，从而优雅地应对动态工作负载。

## 全讲总结

让我们把整讲串起来：

- **推理非常重要**：实际使用、评测、强化学习里都离不开它；
- **推理与训练非常不同**：同一个模型，但你让它做的事很不一样——推理是**访存受限**的，而且（在实时服务里）是**动态**的；
- **一大类技术**：新架构（GQA、MLA、CLA、局部注意力）、量化、剪枝/蒸馏、投机采样——它们背后的统一原则是：**减小 KV cache、不伤精度**；
- **系统思想**：从操作系统借鉴的**投机执行**（speculative execution）与**分页（paging）**，可以直接用在真实的推理服务器上。

最后，讲者想强调一个前面没来得及展开的点：**新架构对推理有巨大的改进潜力**。像状态空间模型（state-space model）、线性注意力、扩散模型这类架构，在某种意义上直接绕开了 Transformer 的痛点——**KV cache 与注意力本质上让 Transformer 成为一个"对推理不友好"的架构**。如果你能发明一个像 Transformer 那样强大、但天生为推理设计的架构，可能会解锁巨大的收益。

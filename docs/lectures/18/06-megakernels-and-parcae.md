# 研究前沿：MegaKernel 与循环语言模型 Parcae

这一节进入本讲的两个研究项目。它们分别对应"把一个 token 的一生"流水线里不同的切片：**MegaKernel** 是从**系统/内核**这一侧出发，让 decode 快得多（Dan 说这是与 Stanford 的合作）；**Parcae** 则是从**架构**这一侧出发，来自 Dan 在 UCSD 的实验室（由 Hayden 主导，与 Zachary 和 Taylor 合作）。两个项目都源于"在真实推理服务里看到的问题"。

## MegaKernel：让 decode 逼近光速

### decode 的根本挑战

decode 阶段的基本难题我们已经很熟悉：**为了生成一个 token，你必须把整个模型跑一遍**。这等于说，你把 GPU 这个大规模并行机器，变成了一个**"光荣的内存加载器"（glorified memory loader）**——prefill 和训练时能用的海量并行，在这里都使不上劲。

让事情雪上加霜的是我们**写 kernel 的方式**。通常我们是一个运算写一个 kernel（kernel-per-operation）：写出 norm kernel、matmul kernel、attention kernel……这样编程确实简单多了（你只需要专心写好某一个运算），但它会在系统里**引入大量停机时间（downtime）**。

### kernel-per-operation 的停机时间

Dan 用一张"卡通示意图"（例子取自一个真实的注意力推理 kernel）说明了这个问题。读图方式：**横轴是时间（从左到右流动），纵轴是 GPU 上所有流式多处理器（streaming multiprocessor，SM）**——H100 上有 132 个 SM，B200 上大概 148 个。图中的"条"表示有用的工作：有一个条，就说明某个 SM 在真正干活；**空白处就是等待**——在等其他运算结束，好让别的事情进行。

结果就是：**不管你 kernel 写得多好，GPU 里总是有停机时间**。来源主要有三类：

1. **kernel 启动与拆除（kernel launch / teardown）**——就是图上红、黄两块之间的大空隙；
2. **尾部效应（tail effects）**——这跟"短 prompt 和长 prompt 一起被处理"是同一个道理，只是它一路渗透到了最基本的注意力运算层面：一批输入里一个很短、一个很长，你就得等那个长的算完；
3. **kernel 与 kernel 之间的空隙**——因为整个模型要一个运算接一个运算地跑，这些空隙会**不断累积**。

### MegaKernel 的思想：把 GPU 当分布式系统来调度

Dan 团队的对策是 **MegaKernel**：**不再为模型里的每个运算各写一个 kernel，而是写一个 kernel 一次覆盖多个运算**。这类似于 Flash Attention 里做的算子融合（fusion），只不过**激进得多、覆盖面大得多**。

具体地说，MegaKernel 把 GPU 从"一个设备、一次一个运算"的视角，转变为**把 GPU 看作一个庞大的分布式系统**：你有一堆工作要做，其中一些工作依赖另一些（图里红色的条依赖绿色的条）。问题变成：**怎么调度、怎么分发工作，才能最大化 GPU 的利用率？**

只把注意力推理这一小块做成 MegaKernel，就能拿到 **30% 到 70% 的加速**；更棒的是，这套做法可以推广到**整个模型**。

### 两个具体的重叠技巧

**例一：QKV 投影 + RoPE 与 KV cache 加载重叠。** 现代语言模型的注意力层里，先做 QKV 投影、再叠加 RoPE 旋转位置编码（图里的蓝色部分），然后才开始注意力计算（橙色部分）。一个关键的洞察是：**可以在 QKV + RoPE 还没算完时，就开始把 KV cache 加载进注意力**——尤其是在 decode 阶段。等 QKV 算完、拿到新的 query token，注意力剩下部分立刻就能继续。也就是说，**有了对 GPU 的细粒度控制，你就可以让某些运算先于另一些开始**，而不是干等。

**例二：O 投影与注意力重叠。** 注意力算完之后是 O 投影（把注意力输出投影回模型维度）。同样地，**O 投影可以在注意力还没结束时就开始加载自己的权重**——又一段等待被消除了。

这些重叠在图里表现为"条与条奇怪地交错"：比如把下一层的权重加载叠进本层注意力、或者在本层注意力还没结束时提前开始部分归约。

### ThunderKittens 与结果

为了写出这种 kernel，Dan 团队搭了一个相当复杂的 CUDA 框架——**ThunderKittens**。它采用一种**指令级（instruction-based）抽象**：每个子 kernel 可以在自己的文件里实现，然后由一个**大的虚拟化共享内存系统（virtualized shared memory system）**来编排这些子 kernel 的运行。你可以把它理解成一个 kernel 编写库，几乎像 Triton、但更低层、对硬件有**精细得多**的控制。

收益是**接近光速的 decode**：

- 把 Llama 1B 的**整个一层**放进一个 kernel，条与条之间出现大量我们上面说的重叠；
- 在 H100 上达到了 **72% 的带宽利用率（bandwidth utilization）**——也就是说，如果忽略所有实现的复杂性、只问"GPU 物理上做这件事能有多快"，我们已经很接近那个速度极限了；
- 图上那条蓝绿色的 MegaKernel 横条，比许多其他 SOTA 推理引擎都快一大截（Dan 说现在这些数字其实又更好了）。

Dan 的总结：**对 kernel 的深层控制、对硬件的深入理解，可以开启非常不同的计算范式**——而这些事情，只有当你把推理玩到很深的层面才会看到。

## Parcae：稳定地循环使用参数

### 动机：除了缩放参数和数据，还有别的路吗

本讲开头提到，新能力来自缩放——参数变多、数据变多。**Parcae** 想问的是：**这是唯一的缩放方式吗？有没有别的办法获得同样的质量？**

Parcae 是 Dan 团队对一种叫**循环 Transformer（looped transformer）**技术的诠释：取出 Transformer 的一些 block，让它们在循环里反复执行。token 不是一层层地单向穿过模型，而是走到某个位置后**被送回同一个 block 循环若干次**（图上那个紫色的 recurrent block），然后再继续往下走。

这么做有几方面的吸引力：

- **参数不变、FLOPs 可调**：循环给你一个"增加 FLOPs"的旋钮。如果你相信"FLOPs 越多、质量越高"，这就是一条**不增加参数成本**就能提升质量的路；
- **表达力更强**：有一篇"旧"工作（几年对学术来说已算旧）指出，循环模型比相同参数的普通模型更能表达一些东西——某些东西你用同样数量的参数表达不出来；
- 所以驱动问题很明确：**每参数的最佳质量是多少？每参数、每数据的最佳"智能"是多少？**

早期结果也很有希望：Tom Goldstein 的组（马里兰大学）有篇论文暗示循环模型可能比 Transformer 更好（在 ARC 任务上）；加上一片 Twitter 炒作——Parcae 发布前大约一周，OpenAI 的某个人声称"Claude 是个循环语言模型"，Dan 觉得这多半是编的（那人最后发了篇博客道歉："我瞎编的，全是假的"），但它确实让循环模型这个话题火了一把。Dan 团队在炒作之前就一直在做这个方向。

### 问题：循环模型一碰就炸

循环模型最大的问题是**训练极不稳定**。只要你改动一点点训练设置——比如把学习率调一下——模型就炸。做个简单的学习率扫描，10 次里有 9 次不收敛：NaN、大 loss spike（损失尖刺）。

之前的补救都是一些"hack"：在每个层里加 norm、或者"就把学习率固定成 $2\times10^{-4}$，别选别的学习率"。Dan 团队觉得：**loss spike 的存在，说明背后一定还有更深层的问题**。于是他们决定用**状态空间模型（state space model，SSM）的数学**来认真分析这件事。

### 动态系统分析：残差是被 A 矩阵"乘"大的

想直接分析那个大循环 block 是很复杂的：它有大量参数、各种非线性——softmax、RoPE、GELU、大前馈网络……所以 Dan 团队的做法是**只看残差（residual）**：每个循环步之后，激活向量变了多少？

第一个经验观察是：**残差其实变化不大**——每个残差 block 只是把向量稍微挪一点，没有翻天覆地的变化。既然变化小，也许可以建模。他们把所有的非线性（注意力、GELU、大 FFN 及其中间层）塞进一个盒子，叫它 $r(\cdot)$；剩下的就是一个关于残差的**线性动态系统**：

$$x_{t+1} = \mathbf{A} x_t + \mathbf{B} u_t + r(x_t)$$

其中 $\mathbf{B}$ 刻画"初始向量怎么被注入"（循环开始前那个向量），$\mathbf{A}$ 刻画"每个循环步残差如何被变换"。把 $r$ 放一边，这个简单的形式足以**统一地看待所有之前的循环 Transformer**——之前的工作对 $\mathbf{A}$ 的选择其实相当随意：有的当成单位矩阵（$A = I$，纯加法），有的用完全可学习的矩阵。

经验上，$\mathbf{A}$ 和 $\mathbf{B}$ 主导了这个方程的幅度。于是问：**如果干脆丢掉那个复杂的非线性部分，会得到什么？** 会得到一个简单到可以用高中微积分解出的系统。闭式解是：

$$x_t = \mathbf{A}^t x_0 + \sum_{k=0}^{t-1} \mathbf{A}^{\,t-1-k} \mathbf{B}\, u_k$$

也就是说，给定初始激活 $x_0$ 与每次的注入 $u_k$，可以直接算出第 $t$ 步的激活长什么样。这个式子被 **$\mathbf{A}$ 的幂**主导——尤其 $\mathbf{A}^t$ 这一项。这里就出现了一个关键的量：**谱半径（spectral radius）**，也就是"范数"的另一种说法。直觉上：你在把 $\mathbf{A}$ 反复乘上很多次。假如 $\mathbf{A}$ 学到了一个标量 $a = 2$，而循环次数 $t = 16$，那么激活会被放大到

$$2^{16} = 65536$$

倍——这还没完，只要谱半径大于 1，$\|\mathbf{A}^t\| \sim \rho(\mathbf{A})^t$ 就会**指数爆炸**。这开始解释那些大 loss spike 了：**之前论文对 $\mathbf{A}$、$\mathbf{B}$ 的选择，要么"边缘稳定"（marginally stable）、要么干脆"不稳定"（unstable）**。

### 修复：把谱半径压到 1 以下

既然问题出在 $\mathbf{A}$、$\mathbf{B}$ 的选择上，那就反过来约束它们：

- **$\mathbf{A}$：参数化成"负对角矩阵"（negative diagonal matrix）**。负对角矩阵乘上自己很多次，元素会**指数衰减到 0**——不会爆炸；
- **$\mathbf{B}$：套一个简单的线性归一化（norm）**——因为 $\mathbf{B}$ 只被应用一次、本身不会爆炸，简单归一化就够了。

这样一来，谱半径 $\rho(\mathbf{A}) < 1$，系统**真的稳定了**。实际训练时，即便用那个对别的模型来说很糟的 $6\times10^{-4}$ 学习率，也得到了一条**稳定的损失曲线**——这就是 Parcae（对 $\mathbf{A}$、$\mathbf{B}$ 重新参数化后的稳定化版本）。并且这种约束**自然地约束了激活的状态范数**。

这里有个对比值得展开。Dan 展示了三条线：

- **橙色**：完全不加约束的模型——直接爆炸，状态范数一路冲到 $10^{19}$；
- **蓝色**：加 norm 的模型——注意它的损失仍然会出"狰狞"的尖刺。原因是两股压力在对抗：模型**想扩张激活**（"空间更大，我能把不同概念分得更开、表示得更好"），而 norm **硬把它拉回 1**。一个想长大、一个往回拽，矛盾就表现在 loss spike 上——即便右侧看范数似乎被压得很好，损失也照样难看；
- **Parcae**：既不靠事后 norm 硬拽、也让系统稳定，训练曲线平滑。

所以这个"很简单的激活侧改动"，不但稳定了训练、稳定了循环，**还带来了更高的模型质量**。

### 效果：质量更好，还有了缩放定律

对比实验中，Parcae 模型全面胜过之前的循环 Transformer（比如 recurrent depth 那类循环模型），也胜过很强的 Transformer 基线（某类"nanochat"风格、很多人想尽快学会的 Transformer）。用同样的基础 Transformer 架构、开始循环、再做稳定化，就能拿到**更好的困惑度与更好的端到端质量**。

然后他们跑了初步的**缩放定律（scaling laws）**。背景是几年前的经典问题：**该把模型做大，还是该喂更多数据？** 当时得到一堆复杂的幂律曲线——识别它们有一个要点：**曲线向右下走，说明数据和参数应该一起缩放**；垂直向下说明"只加数据就够了"；水平向右说明"别加数据、只加参数"。现实是曲线向右下走：训练 1 万亿参数的模型、喂 35 万亿 token，质量更好。

那**循环（recurrence）**在这张图里处于什么位置？有几种可能：永远不要循环；大量循环；或者适度循环。Dan 团队展示的初始缩放定律（所有曲线**等参（isoparametric）**、**等 FLOP（isoflop）**：每条曲线对应一个固定参数量的模型，左边右边参数相同，颜色变化 = 训练数据（即训练 FLOPs）增加），同时变化**数据量**和**循环次数**。结果两种设定下都看到了熟悉的"向右下"趋势——这意味着：

> **在固定参数量的前提下，数据越多，你应该循环得越多。**

他们还发现循环次数遵循经典的幂律，于是可以用缩放定律**联合预测质量如何随"循环次数 × token 数"变化**。

有个同学问起那个"三维图"（同时画循环、数据、参数）。Dan 说那个图又复杂又难看，但它的指向也是"向右下、再向里"——**如果相信它，你应该把三者一起缩放**。而一个很有意思的推论是：**今天的模型一个都没有循环**（它们全都位于这些曲线的最左端），却用了海量数据——这暗示着**训练这些模型时，可能存在稍微更好的做法**。

另一个角度的实验：橙色曲线是固定模型大小的**固定深度模型**（传统 Transformer）；蓝色曲线是在**固定 FLOP 预算**下、循环模型能达到的位置。橙色和蓝色的点用相同的 FLOPs 训练、大小相同，但蓝点通过**增加循环**（而不只是增加数据）来消耗 FLOPs——达到同等 FLOPs 时，蓝点的验证损失更小。这再次暗示：**我们所有的大规模预训练，也许都应该循环**。

## 课堂问答：把细节问清楚

问答环节信息量很大，几乎每一问都补上了正文没展开的部分。

### Q1：Parcae 是从零训练吗？预训练模型能循环吗？

有同学问 Parcae 是否从零训练、对预训练模型能不能做点什么。Dan 的回答是：最近有个"钓鱼"博客，作者声称自己**没训练任何东西**就赢了某个排行榜——他做的是把一个 Qwen 模型的**两三层循环**了一下，结果在数学任务上质量变高了。Dan 实验室有初步工作（可能很快放出）在跟进这个现象。**对某些预训练模型做一点循环，反而能拿到更高的质量**——Dan 说这让他有点不安，因为他也不完全理解为什么会这样，但团队确实很想搞明白（他希望说服 Hayden 去盯着激活和权重看）。

### Q2：循环模型对推理和内存意味着什么？

Percy 追问：你讲了循环模型的"计算最优"，那它的**推理含义**和**内存**方面怎么样？Dan 的回答很直接：他个人对循环非常兴奋的原因之一，就是**服务推理的一个大瓶颈恰恰是 GPU 内存**——参数更少，就意味着**能塞进更多的 KV cache**、意味着**切到更少的 GPU、做更少的通信**。小模型会给你很多灵活性。

他还有一个"梦想"：如果能把循环 block 做得**足够小**，就可以写一个**小小的 MegaKernel**、专门用一个极快的循环去跑那段 recurrence。目前还做不到（block 还没小到那个程度），但这个想法很有意思。而且下一代 **Groq 的 LPU 芯片**只有大约 **250 MB 的内存**——能装进去的东西非常非常小；如果设计出恰好装得进去的模型，就可以**让权重常驻内存，只让激活以最快速度流过**。跨越某些阈值，会有非线性的收益。

### Q3：MegaKernel 的代价是什么？

有同学问 MegaKernel 的权衡。Dan 直言：**代价就是人的血、汗与泪水**——写 MegaKernel 极其费人力。一个非常有天赋的 kernel 工程师，一整年大概能写出**一个硬件平台、两三个模型、batch size 1 到 16** 的 MegaKernel；你想上 batch size 17？抱歉，从头再来。所以它非常难写，Together 正在做一些**编译器**来自动化这个过程。这个想法本身在 GPU 编程的几十年历史里也经历过高峰和低谷。**写得出来，它就是最快的，不可能更快**；但成本确实巨大。

### Q4：为新硬件设计模型时，该改变什么？

有人问：如果模型注定跑在 Groq、Cerebras 这类新硬件上，设计模型时应该怎么改变？Dan 的要点：

- **首先被内存约束**：比如打算跑在 Cerebras 的晶圆上，先去看那块晶圆有多少内存，然后把模型设计成**装得下、还留足 KV cache 的空间**；
- **留意别人的选择**：仔细看中国新出的模型，会发现它们的一些选择暗示着在设计时考虑了华为的芯片；
- **量化格式的选择**：打算在 NVIDIA GPU 上跑的模型（比如 NVIDIA 自己的 Nemotron），会用 **NV FP4**——这是 NVIDIA 芯片专有的 FP4 格式；如果不在 NVIDIA 上跑（比如 AMD），则用另一种叫 **MX FP4** 的格式。两者各有取舍。你会根据目标硬件做这些细微的选择。

### Q5：计算最优时，循环 vs 更多参数？

有同学问：如果只关心计算最优训练，循环是不是永远不如多加参数？Dan 澄清道：**计算最优本质上总是"给定一个 FLOP 预算，决定你想命中什么"**——这多少有点刻意。如果你的目标是更高的质量，那就**加大 FLOP 预算**；如果模型大小已经定了，就训练更久；如果**受限于模型大小**，那就**循环更久**；如果数据用完了，就选一个"对那个大小来说能训练得最好"的模型大小。当然，所有这些选择都在更大的背景里做：这个模型会不会被采用？我打算怎么服务它？如果开源，**多大才能在普通人的笔记本上跑起来**？所以不是"循环永远不好"或"永远好"，而是取决于设计点。把模型做大、喂更多数据，当然总是会更好——但这些工程约束决定了你的选择。

### Q6：不同 use case 的最优架构差异有多大？

有人问 agentic coding 与批处理这类不同 use case 的架构差异。Dan 说差异很大：

- **agentic 循环工作流**：很重要的是让 **KV cache 保持热（hot）**；而大 batch 批处理（每份文档只看一次、翻译完就走）里，KV cache 就不那么重要；
- 所以像 **DeepSeek 的 MLA**（把 KV cache 激进压缩）、或者 **FP8/FP4 精度的 KV cache**，这些对 KV cache 大小的巨大改变，在 agentic 工作流里就很值得关注；
- 最大的差异大概是**因果注意力（causal）还是非因果注意力（bidirectional）**。大 batch 批处理场景，Google 长期以来一直用 **BERT**（大概现在还在搜索里用）——因为不需要生成很多 token，双向注意力一次过、拿到向量存进数据库就行；而聊天工作流**永远有一段 decode**。**T5** 曾经是一个中间选择：一部分双向处理、一部分生成。

### Q7：MegaKernel 遇到多 GPU 通信怎么办？

最后一个问题：MegaKernel 在有多个 GPU 通信时怎么工作？Dan 说他们有一些很早期的初步工作：**把 NIC 通信调用也融进 MegaKernel**（如果编排得当），但还没找到特别好的"杀手级用例"——有时你只是被通信调用本身的延迟钉死。不过通信也是可以融合的碎片之一。他还提到：**DeepSeek v4 发布时，DeepSeek 开源了一个 MoE 推理层的 MegaKernel**，其中就融合了一些通信。所以趋势是：随着这类模型变多，你会看到**计算链条的某个部分**有一个个小 MegaKernel，但未必整个模型都是——除非你愿意付出"血、汗与泪水"的代价。

## 全讲总结

回到本讲的大主题。Dan 希望大家带走的是：**如果你理解这些模型的推理、理解 GPU kernel、理解构成它的所有环节，你就能在机器学习算法上做全栈创新**。无论是：

- 一个新的**路由算法**，让你服务更多流量、或以不同方式服务流量；
- 新的 **kernel**，让你把系统的某个部分跑得飞快；
- 新的**架构**（比如 Parcae），让你用少得多的参数装进更少的 GPU、减少通信。

这些都是"今天我们在研究的那个大问题"的不同片段。Dan 最后说：希望这堂课至少激发了在场某一位同学，去更深入地看看其中的某一块。掌声中，本讲结束——这也是这门课《Language Modeling from Scratch》的**最后一讲**。

# 模型数据集巡礼（下）：从 RefinedWeb 到 CommonPile

## RefinedWeb（2023）："网络数据就够了"

继续时间线。2023 年有一篇论文 **RefinedWeb**，它想论证一个观点：**网络数据就是你所需要的全部（web data is all you need）**。回想我们前面讨论过的那些"专门来源"——GitHub、arXiv、Stack Exchange——这篇论文问：如果我们**只用网络本身**，结果会怎样？

做法是：用 **Trafilatura** 做 HTML → 文本（直接用 **WARC 而非 WET** 文件），然后用 **Gopher 规则**过滤（基本就是"保留看起来像英语的内容"）。特别值得注意的是，他们当时明确说：**避免基于 ML 的过滤**——理由是不想引入偏见、不想把网络过滤成一个过窄的子集。他们做了**基于 MinHash、作用于 5-gram 的模糊去重**，最终共获得 **5 万亿 token，发布了其中 6000 亿**。

后来 **Hugging Face 的 FineWeb** 最初只是 RefinedWeb 的复刻，但把它改进了：用了 **95 次 Common Crawl 转储**，做 **URL 过滤**、**语言识别**（保留英语概率 > 0.65 的文档）、再用 **Gopher、C4 加更多手工规则**过滤，做 **MinHash 模糊去重**，并且**匿名化邮箱与公网 IP（PII 移除）**，最终得到 **15 万亿 token**。可以看到，这些数据集的规模正在快速增长。

## Dolma（2024，AI2）：多来源 + 小心过滤

**Dolma** 是 AI2 的数据集，包含他们自己处理的 Common Crawl、The Stack（下面会讲）、C4 以及一堆其他来源：

- **Reddit**：来自 **Pushshift** 项目（2005–2023），提交（submissions）与评论（comments）分开处理——那时候还能拿到这些数据、还能合法训练，后来就被"锁起来"了；
- **PeS2o**：基于 **Semantic Scholar** 的 **4000 万篇学术论文**；
- **C4、Project Gutenberg、维基百科/Wikibooks**。

对 Common Crawl 的处理是：用 **fastText 分类器做语言识别**（保留英语）；**质量过滤沿用 Gopher 与 C4 的规则**（依旧避免基于模型的质量过滤）；**毒性过滤**用**规则 + Jigsaw 分类器**；用 **Bloom filter 做去重**。最终得到 **3 万亿 token**。

## DataComp-LM / DCLM（2024）：模型质量过滤成为主流

**DataComp-LM（DCLM）** 可能是一个标志性节点：从这里开始，"**基于模型的质量过滤（model-based quality filtering）**"真正成为主流。

DCLM 最初的动机是定义一个**标准化的数据管道/基准**，让研究者可以尝试不同的数据处理算法并公平比较。他们把 Common Crawl 处理成 **DCLM-pool（240 万亿 token）**，再进一步得到 **DCLM-baseline**——用一个**质量分类器**把 pool 过滤成小得多的数据集：

![DCLM 的管道：从 Common Crawl 到 DCLM-pool，再到用质量分类器过滤的 DCLM-baseline](/lectures/13/dclm-filter.png)

**基于模型的质量过滤**具体怎么做？关键在于定义"什么算好数据"。DCLM 的正例（positive examples，约 20 万条）来自两个地方：

- **OpenHermes-2.5**：一个指令数据集，大部分由 **GPT-4 生成**；
- **ELI5**：Reddit 的 r/explainlikeimfive 子版块——满是充满好奇心的问答，比如"为什么天空是蓝的"这类问题。

负例（negative examples，约 20 万条）则来自 **RefinedWeb**——还记得吗，它只是"粗略过滤过的网络"，基本就等于"整个网络"。于是分类器学到的就是：**"像指令数据/好奇问答" vs "像整个网络"**。这听起来有点怪，但确实有效。

```python
from fasttext import train_supervised

# 用"高质量"（__label__good）与"低质量"样本训练一个快速的文本分类器，
# 然后对整个 DCLM-pool 打分并按阈值筛选。
model = train_supervised(input="train.txt", dim=16, epoch=5)

def keep_document(doc: str, threshold: float = 0.5) -> bool:
    labels, probs = model.predict(doc.replace("\n", " "))
    return labels[0] == "__label__good" and probs[0] >= threshold
```

他们训练了一个 **fastText 线性分类器**，跑遍整个 DCLM-pool，得到 **3.8 万亿 token**，并展示了这个"神奇的"质量分类器**胜过他们尝试过的其他过滤方法**：

![DCLM 质量分类器与其他过滤方法的对比结果](/lectures/13/dclm-quality.png)

在一段时间内（至少在开源社区里），DCLM 成了质量过滤的"金标准"。

## Nemotron-CC（2024，NVIDIA）：更多 token + 合成数据

接下来是 NVIDIA 的 **Nemotron-CC**。他们的立场是：**FineWebEdu 和 DCLM 过滤得太狠了**——把大部分数据都删掉了（记得 DCLM 从 240T 只留了 3.8T 吗）。而我们需要**更多 token**。那怎么办？做更精细的事情。

- 在 HTML → 文本这一步，他们用的是 **jusText** 而不是 Trafilatura，**因为它返回的 token 更多**；
- **分类器集成（classifier ensembling）**：先**提示 Nemotron-340B-instruct 模型，按"教育价值"给 FineWeb 文档打分**，把打分结果**蒸馏**成更快的模型；再叠加 **DCLM 分类器**；
- **合成数据（synthetic data）**：这是把合成数据大规模用于预训练的主要数据集之一。对分类器判为**低质量**的数据，用一个语言模型**改写（rephrase）**，让它**看起来像维基百科**；对**高质量**数据，则用语言模型**生成各种任务**——给定一篇维基文章，生成问答对、写摘要、"提取关键信息"等等。

最终得到 **6.3 万亿 token**（其中高质量子集 1.1 万亿）——比 DCLM 大得多。作为参照：**Llama 3 训练用了 15 万亿 token，Qwen 3 用了 36 万亿**。不过 Percy 提醒：看 token 数要小心——论文里的 token 数可能包含重复（比如跑两个 epoch 就翻倍），所以"唯一 token"到底有多少并不清楚。实验结果方面，他们证明了**高质量子集打败了此前的数据集**：

![Nemotron-CC 的数据质量结果](/lectures/13/nemotron-results.png)

## 过滤方法小结：规则 vs 模型、数量 vs 质量

到目前为止我们看了一堆过滤方法，它们在某种程度上都很相似：**拿一次网络抓取，要么用规则过滤，要么用模型过滤**；用模型的话，就得先定义"什么算好数据"，训练一个分类器，再给所有文档打分、筛选。

其中有一个明显的取舍：你可以拿**很多** Common Crawl——想要 240 万亿 token 都行，但那质量可能很低；也可以只要 **1 万亿** token 的高质量数据。**甜点区（sweet spot）大概在两者之间**——这正是数据混合（data mixing）与过滤研究的核心问题。

## 代码数据：The Stack 与 Stack v2

最后聊两件事，先回到代码。**The Stack** 是一个做得非常好的项目：2022 年大家已经清楚编码能力会很重要，所以它立志做一个真正好的代码数据集。初始版本的做法是：从 **GitHub Archive（2015–2022）** 拿仓库名单，**git clone 了 1.37 亿个仓库（510 亿个文件，去重后还有 50 亿个唯一文件）**；用 **go-license-detector** 保留**宽松许可（MIT、Apache）**的仓库；用 **MinHash 与 Jaccard 相似度**移除近重复；最终得到 **3.1 TB 代码**。

**Stack v2**（2024 年更新）加了更多东西：

- 从 GitHub Archive 拿 **issue、评论、Pull Request**；
- 从 **Software Heritage**（前面讲过）拿仓库；
- **爬取文档网站**（如 PyPI、npm、devdocs.io）获取文档；
- 处理上做了很多功夫：去掉**二进制文件**、去掉**恶意软件**、过滤掉 **bot 活动**（GitHub 上很多 PR 其实是机器人提交的）、**去重**、**PII 缩减**，并对海量 PR 做**子采样**以保持代表性；
- 一个很有巧思的设计：世界上编程语言极多，Python 很多、C 很多，但**低资源语言（比如 Nim，Percy 说他都没听说过）**很少见。于是他们把代码**编译成一种共享的低层中间表示——LLVM**（任何 C 编译器都能编译进去），**把低资源语言与其 LLVM 中间表示配对**，这样模型就能从数据量充足的共享低层表示上学到映射，再反哺数据稀少的语言；
- 再加进去各种好用的现有数据集（GSM8K、编程竞赛题、StackOverflow、arXiv、维基百科、OpenWebMath 等）——所以 Stack v2 大致是"大部分代码 + 其他一堆用于训练编码模型的东西"。

关于 **Pull Request**：PR 及其元数据本质上**不是线性的序列**，要经过**线性化（linearization）**才能变成 token 序列。这里一个重要的设计决策是**提供多少上下文**：一个事件可能只是"我改了一行代码"，一行就够了——但想学好它，也许要给几行上下文，甚至围绕这个 diff 的整个文件。下图展示了 Stack v2 中 PR 数据的线性化形式（左），以及它最终训练时的样子（右）——是一种**类似 XML 的结构化数据**：有 PR、一堆 diff、评论事件（"某条评论被发布"）、该 PR 的评审状态等等：

![Stack v2 中 Pull Request 数据的结构化组织](/lectures/13/stackv2-pr1.png)

![Stack v2 线性化后的 token 序列示例](/lectures/13/stackv2-pr2.png)

所以模型学到的**不只是如何生成代码，还有围绕代码的软件开发过程**。

## CommonPile（2025）：只用许可数据能走多远？

还记得我们的前提吗：**网上几乎全部数据都有版权；其中一部分是宽松许可；还有一部分在公有领域**。你可以主张合理使用然后照用不误——但这**尚未尘埃落定**。如果你**极度风险厌恶**（"我不确定行不行，那就是不行"），那就会走向 **CommonPile** 的思路。

CommonPile 回答的问题是：**只用许可（permissively licensed）数据，能训练出好模型吗？——或者说，能走多远？** 他们把互联网翻了个底朝天，寻找所有"值得训练、又带许可"的数据。结果发现意外地多：**Stack v2**（代码）、大量**政府记录**（很多其实是宽松许可的）、**维基**、网络上的一些东西、**一些新闻网站**（有些确实是宽松许可的）、**学术论文**、**在线论坛**、**公有领域**内容、**教育资源**等等。最终收集到 **8 TB**——对"仅许可数据"来说相当不错了。

![CommonPile 的数据组成：各种许可数据来源](/lectures/13/commonpile.png)

做这件事**远比听上去难**——不是"看一眼许可证，哦是 Apache 或 CC，就好"那么简单。有三个微妙之处：

1. **许可洗白（license laundering）**：人们对许可证很马虎——可能有人拿了受版权保护的作品，随手贴一个 CC BY。任何人在网上都能这么写，真假很难分辨；
2. **集合许可不延伸到单个作品**：比如 Dolma 的集合许可是 ODC-By，但**集合的许可以不代表其中每个作品都合规**。所以你不能只看 Hugging Face 上数据集的许可标签——很多数据集写着宽松许可，细究到单个作品层面其实并不宽松；
3. **合成数据**：CommonPile 决定**不用任何合成数据**——因为"用未许可数据训练出的语言模型生成的合成数据"合法性**不明**。虽然开源模型（如 MIT 许可的开放权重模型）技术上可以随意使用，但那些模型本身大概率是用未许可数据训练的——诚实地说，这有点像"**数据洗白（data laundering）**"。

实验把用这套数据训练出的模型与 **LLaMA 1、MPT、Qwen** 等对比：

![CommonPile 模型与其他模型的基准对比](/lectures/13/comma-results.png)

结果"不算差"：**肯定不如 Qwen 系列**，但**明显胜过 2023 年的老模型**。Percy 的结论是：只用许可数据**能做得相当不错**，但要跟那些用了海量数据的模型竞争，**还是很难**。不过他不认为这是终局——如果继续挖掘，公开许可数据里大概还能挤出更多价值。

## 全讲总结

希望这一讲让你对"数据"有了一个丰富的认识。数据**不是从天上掉下来的**——你也不是去 Hugging Face 随便下一个数据集就行。数据有它的来处，而且带着**技术与社会的语境**：

- 最顶层是**活服务（live services）**——互联网就是一堆活服务器，必须有人做"生产原始数据"的工作（要么网站给你转储、要么有人造爬虫）；
- 然后**必须有人决定怎么把它处理成可用形式**——转换（transformation）、过滤（filtering）、去重（deduplication）。所有这些选择都会影响最终语言模型的质量；
- **过滤大概是其中最重要的部分**：怎么从 200 万亿 token 走到不到 3 万亿 token？这是巨大的缩减，值得大量关注；
- **数据在某种意义上就是区分不同语言模型的关键成分**——很多模型架构上都是差不多的 Transformer，但数据处理方式不同，结果可以差很多；
- 围绕数据有**大量的法律与伦理议题**（版权、隐私），远比这一讲能覆盖的多；
- 而且这个过程**非常启发式（heuristic）**——与这门课其他更"有原理可循"的部分不同，数据处理目前很大程度上**靠"感觉"（vibes）**：你定义一个分类器、定义一条规则、设置一些阈值。这意味着**有大量的改进机会**。

所以做作业时不妨想想：有没有更好的数据方法？这完全可能成为一个研究方向。下一讲会继续讲数据——重点是**后期训练（post-training）数据**，以及**更多关于过滤**的内容。

# KV cache 与模型并行：切分、共享与大规模部署

## KV cache 的共享：让"见过的计算"被复用

上一节讲过 KV cache 与前缀共享的基本思想。这一节先从 KV cache 的"共享"继续展开：缓存不仅要复用同一个用户、同一个会话里的前缀，还要能**在请求之间共享**。比如所有用户都会用的系统提示（system prompt）、热门开源模型的公共前缀，或者同一个用户一个月前上传的那本书——只要前缀树命中，这些激活就不必重算。

![KV cache 的分块共享：不同请求可以共享相同的前缀块](/lectures/18/paged-attention-sharing.png)

这里用到的仍然是最传统的计算机科学工具：把 token 序列组织成一棵前缀树，命中即查表。而系统层面要回答的问题始终是：**你能缓存多少个不同用户、多少个会话的 KV cache，从而同时跑起尽可能多的会话**——这直接决定了服务的并发能力。

## 为什么必须切分模型：单卡装不下

另一个绕不开的问题是**模型的切分**。Dan 说："假设你有一个万亿参数的模型，跑在约 280 GB 显存的 GPU 上——你不可能把整个模型塞进每一张 GPU。"（第 10 讲也提过，前沿模型是万亿参数级的。）于是必须把模型拆开，主要有两种思路：

1. **张量并行（tensor parallelism）**：把**每一个张量**都切成若干份、分到多张 GPU 上。比如把每个权重矩阵 4 等分，摊到 4 张 GPU 上——每一层、每一个矩阵乘法都由这 4 张卡协作完成；
2. **专家并行（expert parallelism）**：如今很多 SOTA 模型是**混合专家（mixture-of-experts，MoE）**模型——有一堆专家（expert），每个 token 只选择性激活其中一部分。你可以把不同的专家分配到不同的 GPU 上，token 按需路由过去。

![张量并行：把每个张量切分到多张 GPU 协作计算](/lectures/18/tensor-parallelism.png)

Dan 强调：**你在这一点上做的选择，会直接决定整个系统的瓶颈在哪里**——需要多少张 GPU 才能跑起来？同时能服务多少个会话？这些都是由切分方式决定的。

### 张量并行的通信账

为什么切分方式这么重要？因为并行是要付出**通信**代价的。以张量并行为例：把模型切到 $P$ 张 GPU 后，每一层 Transformer 的前向里，注意力与 MLP 各需要做一次跨 GPU 的**全归约（all-reduce）**来聚合各卡的部分结果，即每层约 2 次全归约。通信量与**激活大小**成正比（要聚合的就是激活），而激活大小又正比于 batch 里的 token 数。

于是两种阶段对通信的敏感度截然不同：

- **prefill**（token 数多）：计算量大，通信相对算可以摊销，瓶颈在计算；
- **decode**（每步 1 个 token）：激活只有薄薄一层，通信量虽小、但计算更小——**通信/计算比很高，通信很容易成为瓶颈**。

这跟"decode 访存受限"是同一枚硬币的另一面：decode 阶段连权重搬运都嫌多，更别提还要在 GPU 之间搬激活了。

### 流水线并行：把层切到不同的节点上

与张量并行互补的另一种切分方式是**流水线并行（pipeline parallelism）**：不切张量，而是**按层把模型切开**——把不同的层放到不同的机器（节点）上，token 从前一阶段的层流向后一阶段的层。模型层数越多、切分越深，每个节点要放的层越少，但 token 需要在节点之间**以流水线的形式传递**。这就是 Dan 在前面"一个 token 的一生"里说的"把计算切分到不同机器上、跨节点并行"的具体形态。

![流水线并行：把模型的层切分到不同节点，token 按阶段流水处理](/lectures/18/pipeline-parallelism.png)

张量并行与流水线并行经常**组合使用**：节点内用张量并行把单层摊到多张 GPU，节点间用流水线并行把层摊到多个节点。这也解释了为什么大规模部署的关键词是"互连"——切分越细，节点之间的通信越快就越重要。

![GPU 节点结构：一个节点内多张 GPU 通过高速互连连接，跨节点通信更慢](/lectures/18/gpu-node-overview.png)

## 大规模部署：72 张 GPU 连成一个节点

把镜头拉远，看今天的大规模部署。上一代 Blackwell GPU 里，NVIDIA 推出了 **NVL72（Grace Blackwell）**——**72 张 GPU 用极快的互连（interconnect）连成一体**。这带来一系列新问题：

- 怎么把万亿参数模型切到全部 72 张 GPU 上？这有意义吗？切了能换来什么？
- 怎么考虑**容错（fault tolerance）**？

容错为什么重要？因为**这些系统真的经常坏**。Dan 列举了一些现实原因：NVLink 的连接器是**塑料**做的（不是金属），如果你把线缆插得太用力，接头会轻微变形，然后你就得到非常不稳定的 NVLink——这本身就是一个大话题。另外，这个"AI 世代"的散热设计（在芯片上加风扇）也让人困惑。总之，当你把一个模型切到 64 张 GPU 上、对几百万用户服务、每天产生万亿级 token 时，必须问：**如果其中一张 GPU 挂了，怎么办？有没有办法让系统容错？** 这里有很多好玩的问题可想。

还有一个趋势：模型开始拥有**一百万 token 甚至更长的上下文**。怎么处理这种超长上下文？是把上下文切到多张 GPU 上？还是别的办法？Dan 在这里没有展开，只留了一个"这些都有大量开放问题"的伏笔。

## 小结

这一节的主题是"把模型铺开"：**KV cache 在请求间共享**（前缀树命中即复用）、**模型在 GPU 间切分**（张量并行把每个张量 4 等分、MoE 把专家分开），以及由此引出的大规模部署问题——**NVL72 的 72 卡互连、单卡故障的容错、百万 token 超长上下文**。切分方式决定了系统瓶颈，而通信（尤其 decode 阶段的通信）是约束中的关键一环。下一节我们回到"服务"本身：分离式部署、大规模下才会冒出来的内核 bug，以及 KV cache 的分层存储。

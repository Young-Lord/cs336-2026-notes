# 解密：矩阵乘法的性能曲线

现在把前面学到的所有东西拼起来，去理解那个"矩阵乘法的神秘曲线"。先问一个基本问题：**为什么更大的矩阵反而更快？**

一部分答案我们已经有了。其一，**运算强度（compute intensity）**:roofline 告诉我们，必须为每次内存读取准备足够多的工作，才能饱和计算单元——这驱动了曲线整体**对角上升**的趋势，大矩阵的工作量更多、更容易喂饱硬件。其二，**tiling**：大矩阵有更多机会把访问组织进 shared memory 的大 tile。但这些只是"大方向"，曲线上的**锯齿与周期性骤降**还需要更仔细地看。

## 第一部分：tiling 与对齐（整除性）

如果给曲线上的每条线按矩阵维度的**整除性**（divisibility）着色，会发现：

- **蓝色**：只能被 1 整除（连偶数都不是）；
- **橙色**：能被 2 整除；
- **绿色**：能被 8 整除；
- **红色**：能被 16 整除；
- **紫色**：能被 32 整除。

规律非常清楚：**只被 1 或 2 整除的维度，吞吐很差**；一旦进入比较大的倍数（16、32），基本就没有惩罚了，16 和 32 表现一样好。这不是因为 2 的幂有什么"魔法"——而是因为 **16 和 32 已经足够大，恰好能填满突发窗口（burst window）**：整个 tile 可以被一次合并读取读进来。所以整除性通过对齐（coalesced reads）对性能有**重大影响**。

## 第二部分：波次量化（wave quantization）

还剩一个更诡异的谜：某些时候，曲线会出现**周期性**的突然下跌——只是乘一个矩阵，为什么**加一个维度会突然杀死吞吐量**?Tatsu 说 Percy 把这叫作 "GPU trivia"(GPU 琐事)，而他本人恰恰非常喜欢这个例子。

具体来看，骤降发生在 **1792 到 1793** 之间。假设我们用的 tile 大小是 $256 \times 128$:

- 维度 1792：需要的 tile 数量是

$$\frac{1792}{256} \times \frac{1792}{128} = 7 \times 14 = 98 \text{ 个 tile;}$$

- 维度 1793:两边都多出一格,

$$\frac{1793}{256} \times \frac{1793}{128} = 8 \times 15 = 120 \text{ 个 tile。}$$

98 变成 120，听起来只是变多了——但**A100 只有 108 个 SM**。98 个 tile 一波（wave）正好放得下 108 个 SM；而 120 个 tile **放不下了**：先跑完一波 108 个，还剩 12 个 tile 要再等一整轮——这 12 个 tile 只占用了极少数的 SM,**绝大多数 SM 处于闲置**，于是吞吐骤降。

![](/lectures/05/slide-48.png)

这就是**波次量化（wave quantization）**：把 tile 数从 98 提到 120，多出来的一格迫使 GPU 多等一个"波次"，产生非常突兀的性能悬崖。这种现象完美演示了"硬件细节如何决定性能曲线"——也是为什么本讲开头那张图看起来那么"疯狂"。

### 课堂问答的补充

- **超过突发尺寸的倍数还有额外收益吗？** 没有——只要维度能被突发尺寸整除，就够了。这是**整除性质（divisor property）**，更大的除数在这里没有更多好处；
- **为什么 A100 是 108 个 SM?** Tatsu 说："这就是 SM 的数量，你得去问 Jensen（黄仁勋)，我没有答案";
- **为什么 SRAM 这么贵、不能造大一点？** 三个原因：一是 SRAM 本来就贵；二是很难做，因为它必须**物理上靠近计算单元**，信号传播是难点；三是 **SRAM 与 DRAM 是不同原理的存储**——SRAM 必须**一直通电才能保持数值**，非常耗电。所以考虑总拥有成本与能耗，你不会想要一块巨大的 SRAM 芯片，而是要把它用在该用的地方；
- **晶圆级引擎（wafer scale）呢？** 有同学问到单 GPU vs 晶圆级引擎。Tatsu 说自己旁边有更懂晶圆级的同学，而且上一讲之后他们聊过：晶圆级的东西**编译极其困难**——会有波干扰效应（wave interference）和各种可怕的问题，那是一个他不太熟悉、也比现在讲的复杂得多的世界。

## 第二部分小结：一切都关于内存

回顾第二部分，如何让 ML 工作负载在 GPU 上跑得快？大量故事其实就是**内存、内存、内存**:

- **减少内存访问**：用**合并访存**（coalescing）把读聚合起来；用**算子融合**（fusion）避免来回搬运；
- **把内存搬进 shared memory**：用 **tiling** 尽量复用；
- **用其他资源换内存**：用**量化**（quantization）与**重计算（recomputation）**，拿计算/精度去换内存访问。

这些想法几乎都围绕同一个主题：**内存是我们的瓶颈，怎么对付它**。想通这一点，我们就有了理解 FlashAttention 所需的全部零件——下一节进入本讲的"胜利一圈"。

# 一个 token 的一生：推理引擎全景与工作负载

## 推理引擎里的所有环节

这一节回答的问题是：**当你向一个推理系统发出请求时，请求会经历哪些不同的环节？** Dan 用一张"推理引擎全景图"（灵感来自他的学生 Austin 在 Together 的经验）给出了高层描述。按顺序走一遍：

1. **请求调度（scheduling）**：请求进来后，第一件事是被调度（schedule）到不同的 GPU 上。调度策略可以是各种各样的——甚至可能把 **prefill 和 decode 放在不同的机器**上（这就是所谓"分离式 prefill/decode"，后面会细讲）；
2. **KV cache 命中检查**：拿请求去对照 **KV cache（key-value cache）**，看看我是不是见过这个请求、或者见过这个请求的某些版本？是否存在可以**省下来的计算**？这是"前缀复用"（prefix sharing）的一种体现；
3. **执行核心 ML 代码**：接下来开始执行模型的前向计算。这里会有新 token、有需要计算的新运算；
4. **各种并行化优化**：可以**跨机器切分计算**（把同一份计算拆分到不同的机器上）、**跨节点并行**（parallelize across nodes）、**在节点内跨 GPU 并行**（parallelize within a node）。具体怎么切，取决于模型的大小、取决于你打算怎么把模型拆开。随着硬件在演进，这里会出现越来越多不同的选择；
5. **输出与后处理**：所有选择都定下来、代码执行完毕之后，你就得到了 token。模型返回一段回答——比如你可以问它"Percy 上课说的线性回归到底是什么意思"（因为你在他的课上翘课了），得到完整的端到端体验。

## 生产环境的工作负载长什么样

在深入细节之前，值得先想想：**不同的推理工作负载（workload）到底长什么样？** 这里有一个反直觉的事实：生产环境里的真实流量，**既不像训练时看到的 token 分布**（训练时一次性看过所有 token），**也不太像你凭空在脑子里编出来的流量**。

对每一个具体工作负载，你会看到特定的**输入 token / 输出 token 分布**。几个例子：

- **编码工作负载（coding workload）**：比如你是 Cursor 这类工具的提供者，整个代码库对 agent 可见、用户围绕代码库提问——典型形态是**很长的输入**（几万个输入 token），然后根据模型怎么训练的，输出要么是若干"思考 token"（thinking tokens），要么是较短的答案；
- **摘要工作负载 / 叙事摘要（narrative summarization）**：比如用户把整本书贴进聊天窗口，来回讨论书里发生了什么——这跟标准的聊天形态差别很大；
- **标准聊天（standard chat）**：直接问 ChatGPT"给我讲讲一阶微积分"，输入输出都很短，工作负载形态完全不同。

此外，今天使用语言模型的方式大多是**回合式的智能体工作流（turn-based agentic workflows）**。你写代码时跟编码 agent 来回对话："做这个""不对，我不是这个意思，做那个"。编码 agent 自己也会大量地迭代调用语言模型：它们会调用工具（比如"去我的代码库里搜一下这个"）、把结果再喂回给模型；用户还可能让 agent 去互联网搜索某个东西再带回来。所以典型的负载里会有**多个回合（multiple turns）**。

## 不同的应用有不同的时间节奏

除了 token 分布，不同的应用还有**完全不同的时间节奏（cadence）**：

- 如果你处在一个**快速交互式的聊天循环**里（比如对着手机上的 ChatGPT 用语音模式说话），你会期望相对快速的响应；
- 如果你搭了一个 **agentic 工作流**，对它说"你去把这个做完吧，我先不打扰你，你自己迭代"——那是另一种节奏；
- 如果 agent 中途卡住了，喊"嘿我需要建议"，而你又没注意到——那回合之间又是另一种间隔。

于是，"工作负载"由这些要素共同刻画：

- **每次进来多少新 token？总共要生成多少 token？**
- **会话（session）有多长？** 你是那种很"粘"的用户，跟 Claude agent 来回聊很久；还是只问一个问题就走、第二天再来？
- **回合之间隔多久？** Dan 自己举了个例子：他有一个跟 ChatGPT 长期保持的聊天，讨论每周该怎么安排健身计划，他大约**每两周**跟它交互一次——这跟其他流量模式完全不同。

最后，不同的应用还会提出**不同的服务目标（SLA）**：

- 交互式应用可能要求**首 token 在 1 秒以内返回**（time-to-first-token，TTFT < 1s），这样 agent 可以先说一句"我在思考，我要说巴拉巴拉"；
- 反过来，也可能你知道自己会生成 500 个 token，希望**整段响应在某个时限内全部返回**，让用户来得及读完。

## 一个请求的具体处理流程

现在把镜头拉近，看一个请求具体是怎么被处理的：

1. **分词（tokenize）**：进来一段文本，先把它 tokenize 成 token（这你肯定熟悉）；
2. **缓存检查**：一旦有了 token，就进入一个相当复杂的调度流程——要问"**我见过这些 token 吗？能不能直接查表得到某些激活（activations）？**"；
3. **prefill 与 decode**：然后是两块主要的 ML 计算——**prefill** 和 **decode**，它们非常不同：
   - **prefill（预填充）**：假设你有 1 万个从未见过的 token，要一次性算出它们的激活与逻辑（logits）。**1 万 token 进、1 个 token 出**，这是一次**计算受限（compute-bound）**的操作——实际上它长得非常像训练：训练时你有一大堆 token、写 Flash Attention kernel、跑训练循环，prefill 几乎一样，只是**不跑反向传播（backward pass）**；
   - **decode（解码）**：然后开始**一次生成一个 token**。你把这些 token 传进去（"这是我的代码库，告诉我函数 ABC 是干什么的"），模型处理完整个 prompt 之后开始逐个生成 token——没有投机解码时每次一个，有投机解码（speculative decoding）时可能一次三四个。关键观察：**每生成一个新 token，都要把整个模型再跑一遍**。算一下就会知道，这一步需要的 FLOPs 其实不多，所以它是**访存带宽受限（memory-bandwidth-bound）**的——你必须每次把整个模型权重重新加载一遍，只为生成一个 token；
4. **输出后处理**：模型前向的最后，你得到一个表示 token 的数字，把它转成字符串，可能还要做一点处理：**找停止符（stop tokens）**、跑**安全检查**（比如"用户是不是在试图黑进系统"）等等；
5. **循环**：输出给到用户之后，推理引擎真的就是**一直在跑这个循环**——等待请求进来、调度、执行、采样 token（scheduling-execution-token sampling loop）。

## 小结

这一节建立了"一个 token 的一生"的整体框架：请求经过**调度 → KV cache 命中检查 → prefill/decode 执行 → 并行化选择 → 输出后处理**这条流水线；同时理解了生产负载的多样性——不同 workload 有不同的输入/输出分布、不同的回合节奏、不同的 SLA。下一节我们深入其中两块最核心的 ML 计算——prefill 与 decode——以及它们如何在多请求并发时被调度。

# 六个加速技巧：如何把工作负载跑得快

进入第二部分。现在大家对 GPU 是什么、怎么工作有了整体认识，接下来讲让工作负载在 GPU 上跑得快的**基本技巧（tricks）**——它们是拼出高效程序的积木。这一部分的动机，是要解释开头那张"神秘曲线"：横轴是**方阵的维度**，纵轴是**每秒处理的元素数（吞吐量）**。大体上，矩阵越大、工作量越多，吞吐越高——因为有更多工作可以喂饱硬件。但曲线上充满了奇怪的模式，而我们的目标，就是理解为什么会有这些模式，以及**怎么站在曲线的顶部而不是底部**。

## Roofline 模型：先知道瓶颈在哪

Percy 在之前提到过 **roofline 模型**，而那张神秘曲线长得就很像经典 roofline 曲线：一段**对角上升**，然后一段**平坦**。

![](/lectures/05/slide-21.png)

roofline 模型告诉我们：在某个点之前，我们是**内存受限（memory bound）**的——无论你给多少算力，吞吐都不会上去；到了某个临界点，每个单位内存搬运已经有了足够多的工作，能把计算单元完全喂饱；过了这个点，再给更多工作也没有帮助了，因为矩阵乘单元已经**完全饱和**。这就是经典 roofline：对角部分是内存受限区，平坦部分是**计算受限（compute bound）**区。

所以，想让代码在 GPU 上高效运行，关键是要**站到平坦部分**去。一旦到了平坦部分，就没有别的可做了，我们已经拿到最大吞吐。我们想避免的是对角部分，也就是要提高**运算强度（operational intensity，也叫算术强度 arithmetic intensity）**——**每次内存读取要做的计算量**必须足够高。这就是本部分的核心：**如何避免成为内存受限？**

## 六个技巧一览

幻灯片上把"如何让 GPU 跑得快"列成了六个技巧：

1. **控制发散（control divergence）**——不是内存瓶颈，而是执行模型的问题；
2. **低精度计算（low precision computation）**;
3. **算子融合（operator fusion）**;
4. **重计算（recomputation）**;
5. **合并访存（coalescing memory）**;
6. **tiling（分块，把内存搬进 shared memory)**。

下面逐一展开。

## 技巧 1：控制发散（control divergence）

GPU 运行在 SIMT 模型下：**一个 warp 里的每个线程都在执行同一条指令**。条件分支（conditionals）当然没问题，但会带来相当大的开销：当 warp 里的线程走不同的分支时，硬件只能让一部分线程执行、其余线程"掩蔽"掉，再反过来执行另一分支——两拨工作变成串行。这是**执行模型本身**带来的开销，而不是内存瓶颈。控制发散提醒我们：写 kernel 时，尽量避免让同一 warp 内的线程分歧过大。

## 技巧 2：低精度计算

核心思想非常简单：**比特越少，需要搬运的比特就越少**。我们算一个例子：对长度为 $n$ 的向量做逐元素 ReLU（$x = \max(0, x)$）。

**FP32 情形**:

- 内存访问：1 次读（$x$）、1 次写（如果 $x < 0$），FP32 每个数 **4 字节**，共 **8 字节/FLOP**;
- 运算：1 次比较、1 FLOP;
- 运算强度：**8 字节/FLOP**。

**FP16 情形**:

- 内存访问：1 次读（$x$）、1 次写，FP16 每个数 **2 字节**，共 **4 字节/FLOP**;
- 运算：1 次比较、1 FLOP;
- 运算强度：**4 字节/FLOP**。

于是 FP16 下每个 FLOP 只需一半的字节搬运——同样的内存带宽能支持的运算量翻倍（也就是**运算强度翻倍**）。现代 GPU 有大量通过低精度/混合精度运算加速的操作：Tensor Core 支持 FP16/BF16 输入并做 FP32 累加，使 matmul 吞吐大幅提升。做 16 位计算时，通常用 **BF16**(bfloat16，更多指数位、更少尾数位)，它对训练数值稳定性更友好。

### 低精度前沿：FP8 与 MXFP8

进入 **FP8** 之后，事情变得有意思。FP8 有两种口味：

- **E4M3**:4 位指数 + 3 位尾数（尾数更多）；
- **E5M2**:5 位指数 + 2 位尾数（指数更多，尾数更少）。

它们用在不同的地方，比特这么少之后，不再有"一刀切"的格式。

更前沿的是 **MXFP8(Blackwell 上引入)**，它有多重缩放因子。传统 FP8 训练里，所有（比如）激活都是 8 位，然后配一个 **FP32 的缩放因子**来整体缩放。为什么需要缩放因子？因为只有 4 位指数，太少了，很容易上溢/下溢，缩放因子把数据保持在合适的范围内。但人们意识到这**并非最优**：一个矩阵内部的不同区域可能有非常不同的量级——序列的一部分激活可能比另一部分大得多。所以与其一个矩阵一个缩放因子，不如**一个矩阵很多个缩放因子**：每个缩放因子对应矩阵里的一个子块（比如前 4 个元素用一个，以此类推）。而且这些缩放因子本身也用低精度——**8 位 E8M0**，只有指数位，所以全是 2 的幂。

MXFP8 有几个值得注意的设计点：

- **元素用 E4M3**（更多的尾数位)，因为缩放因子已经承担了量级调节的职责；
- **缩放因子本身是 FP8(E8M0)**,**每 32 个元素一个**;
- **转置现在变得非平凡了！**

第三点是最有意思的陷阱。Tatsu 让大家先停一下想：这个设计的大问题是什么？答案是——**转置会破坏缩放模式**。以前转置一个矩阵是平凡的：转一下就行，不用重新量化。现在转置之后，缩放因子的排列方式就错了，你**必须重新量化整块矩阵**来适配"每 32 个元素一个缩放"的模式。实际实现（在训练 MXFP8 模型时）中，这导致：**每个被量化的矩阵保存两份副本——一份原矩阵、一份转置**。需要转置时，转置版本早已就绪。Tatsu 觉得这"疯狂又酷"。

他不想让大家陷入 GPU 琐事，但要传达的要点是：进入 FP8/FP4 之后，事情开始变得很"异国情调"——指数和尾数损失都非常极端，你必须非常巧妙地处理。值得注意的是，**并不是所有层都会量到 FP8**：有些层你认为是安全的才量化（而且转置也单独量化）。这是需要试错的部分。好处也很实在：FP8 训练里那些矩阵乘大概能省 **20~30%**（甚至更多，取决于矩阵大小）的算力/带宽，但**不是 2 倍**——因为还要付出量化/反量化的开销。

课堂问答里的几个补充：

- **为什么首尾层难量化？** 最后一层难量化，是因为它是**一阶因子**，直接贡献了大量 loss，量化它既会不稳定、又会带来很大的 loss 上升；第一层的直觉 Tatsu 说他也说不清；
- **低精度只对矩阵有用吗？** 什么都可以量化（比如 ReLU 之后的激活），只是没必要：矩阵乘量化带来的吞吐提升最大，所以 MXFP8 训练图里全是 matmul 在量化，其他操作的开销不划算；
- **硬件有支持吗？** 有，大量此类操作已内建到硬件里加速；
- **缩放因子要训练吗？** 缩放因子是实现相关的选择：有的库扫描数据取最大/最小值，有的用历史运行统计；严格说不是"训练"（没有梯度)，推理时也许会拟合；
- **结构化稀疏呢？** Chris Ré 等人做了大量不同种类的结构化矩阵工作，但计算收益与表达损失的权衡，经验上"洗平了"——不能说坏主意，但没证实成功；MoE 算一个成功的结构化稀疏操作；
- **量化的 SOTA 是什么？** 大致是：训练更大的模型，然后量化下去；结合一定程度的**量化感知训练（quantization-aware training）**与各种**训练后量化（post-training quantization）**；很多团队仍在做"量化的科学"，远未完全理解。

### 再往前：MXFP4

作为"这太离谱了"的一页，Tatsu 展示了 **MXFP4**：它可以表示的全部值就是 **-6 到 6**——整个数值集合一张幻灯片就放得下。结构上：每 16 个元素配一个缩放因子，缩放因子本身是 FP8（E4M3）。虽然理解 MXFP8 之后就能理解它，但目前只有论文做过 FP4 训练，还没有人听说在"野外"用 FP4 成功训练真正大的严肃模型。不过 Tatsu 判断：**下一代模型很可能就是 FP4**。

## 技巧 3：算子融合（operator fusion）

这个技巧更像一个概念性的编程思想，想法很简单——但你会惊讶于它有多少时候**并没有**自动发生。

把 GPU 想成一座**工厂**：你有**内存仓库**(warehouse)，有小小的**计算工厂**(factory)，还有一条在两者之间来回跑的**传送带**。如果你扩展计算，瓶颈会落在传送带上；而且**操作越多越糟**：如果你有很多不同的操作要依次做，就要把原材料从仓库搬到工厂、再搬回去、再搬过来……你为大量双向的内存带宽付出了代价。更好的方案是：**一个巨大的工厂**，吞下所有原材料，只把成品送回去——这样你只需要为内存带宽付两次钱（一次读、一次写）。这就是**算子融合**。

具体到代码：计算 $\sin^2 x + \cos^2 x$,PyTorch 的计算图是 $x \to \sin \to \cos \to$ 各自平方 $\to$ 相加 $\to$ 输出。**朴素实现**下，图中的每个操作都是一个独立的"工厂"(kernel)：读 $x$、算 $\sin$、写回；再读、算 $\cos$、写回；再平方……整个计算一共**启动 5 个 CUDA kernel**，数据在全局内存与计算单元之间来回 5 趟：

```python
import torch

def sin_sq_plus_cos_sq(x):
    return torch.sin(x) ** 2 + torch.cos(x) ** 2

x = torch.randn(1 << 20, device="cuda")

y_naive = sin_sq_plus_cos_sq(x)             # 朴素:5 个 kernel,来回读写全局内存

y_fused = torch.compile(sin_sq_plus_cos_sq)(x)   # 融合:编译器把 5 个逐点操作合成 1 个 kernel
```

所有 5 个逐点操作**可以融合成一次 CUDA kernel 调用**：读一次 $x$，在寄存器里依次做完 sin、cos、平方、相加，最后写一次结果。这类"简单"融合**编译器可以自动完成**——这就是 `torch.compile` 在做的事。

## 技巧 4：重计算（recomputation）

反向传播里，我们要**存储激活（activation，黄色）**、并**计算雅可比（Jacobian，绿色）**。存储（以及取回）激活可能很贵。

假设我们把 3 个 sigmoid 堆叠起来，$$x \to \sigma_1 \to \sigma_2 \to \sigma_3 \to \text{loss}$$，朴素地存下每一层激活再算反向，一次前向+反向需要 **8 次内存读写**，运算强度极低——这对性能是"真正的灾难"。

但如果你**把激活扔掉，反向时重新计算**呢？关键观察：**重算这些激活的计算成本是廉价的（它们只是前向的几行），而省下的内存访问是昂贵的**。在这个例子里，丢弃激活并重算，内存访问降到 **5/8**——**丢掉计算反而可以是最优的**。这就是**激活检查点（activation checkpointing）**的核心思想：用计算换内存，而且往往划算。FlashAttention 在反向传播里重用的正是这一招（后面会看到）。

## 技巧 5：合并访存与 DRAM

DRAM（全局内存）以**突发模式（burst mode）**读取：**每一次读都会给你一大块字节**（比如 128 字节，只要它落在同一个连续块里）。突发模式来源于 DRAM 的物理结构：慢速的"逐行复制到感测放大器（sense amplifier）"这一步——内存单元排成网格，读取放大器按列工作，激活电压很费时间；一旦选中了列，该列内多个元素的读出就相对便宜很多。所以如果你的读在**连续**处聚在一起，会快得多。

**合并（coalesced）访存**这个词的意思是：**一个 warp 里所有的线程都落在同一个突发窗口里**。比如有 4 个线程，它们都从一个突发段里读，那就完全利用了这个突发段的带宽——这就是合并。多个 warp 对应多个突发段，把读聚合起来就能高效地从内存读数据。

为什么讲 DRAM 琐事？因为矩阵：你经常想一大块一大块地读矩阵做 matmul，而矩阵乘里某些访存模式是"特权"的，结构比别的优雅得多，能利用这个特性获得极快的读取。记住这条口诀：**对于行主序（row-major）矩阵，沿着主序方向移动的线程是没法合并的**。看图：一个 4×4 行主序矩阵，内存里按黄色块、红色块……的线性顺序排列。如果线程每个时钟周期读一列、向右移动，那么第一次迭代就命中了黄色、红色、绿色、蓝色各一个元素——**每个元素都在不同的突发窗口里**，而你实际上"读了一遍整个矩阵"，尽管你只想要一列。反过来，如果沿着行的方向读，整个块一次就读完了。

![](/lectures/05/slide-39.png)

所以，合并访存能给你从大而连续的结构（比如矩阵）读数据的显著收益，这也是值得考虑按行还是按列（以及其他排列）的原因之一。

## 技巧 6（重头戏):tiling

最后一个、也是最重要的想法，是 **tiling（分块)**。在作者看来，它对性能的影响可能超过其他任何想法。tiling 的核心是：**尽可能多地利用内存层级做事**——把内存访问尽量分组，shared memory 的访问要凑在一起、并且**在 shared memory 上做**。

为什么叫 tiling？你要把需要的东西**切成块（tile）**，把每个 tile **加载进 shared memory**;tile 一旦加载进来，你就反复从它读取、尽可能多做事情。

回到矩阵乘：要算 $C = M \times N$($M$ 在左、$N$ 在右上、输出 $C$ 在右下)，朴素做法下，同一个输入条目会被读很多次——准确地说，在 $n \times n$ 的矩阵乘里，**每个条目要被读 $n$ 次**（从全局内存）。你自然会想：既然 $m_0$ 这个条目要被读很多次，为什么不把那些访问**聚在一起**？矩阵的好处是它有一种非常自然的"分组"方式：把矩阵切成子矩阵，加载它们，然后在它们上面运算。

![](/lectures/05/slide-41.png)

一个非常简单的算法：把矩阵切成 $2 \times 2$ 的子矩阵，分阶段计算：

1. 把 $M_{0,0}$（左矩阵左上角）与 $N_{0,0}$（上矩阵左上角)tile 加载进 shared memory;
2. 在 shared memory 里算出 $C$ 的部分和（这一个 tile 就算完了）；
3. 把 $M_{0,0}$ 与 $N_{2,0}$ 的 tile 加载进 shared memory;
4. ……

**优点**：重复的读取现在访问的是 shared memory，而不是全局内存；而且内存访问可以被合并。每个 tile 只从全局内存慢速搬运一次，之后就都在快的 shared memory 里读写，算完再一次性写回。

### tiling 的数学

- **非 tiled 矩阵乘**：每个输入从全局内存读 **$N$ 次**;
- **tiled 矩阵乘**(tile 大小为 $T$)：每个输入从全局内存读 **$N/T$ 次**，在块内再访问 **$T$ 次**。

也就是说，全局内存访问量减少了 **$T$ 倍**。极端情形 $T = N$：从全局内存读 1 次，在 shared memory 里访问 $N$ 次。大的 shared memory tile，意味着能在 matmul 上大幅削减全局内存访问。

课堂问答确认了几件事：做 tiling 是因为你没法一次性把整个矩阵放进片上内存（如果你造一种全 SRAM 的另类加速器，比如 Grok，确实可以把整个矩阵放进去——但非常贵）；数据并行、张量并行等各种并行化，看起来都有一点像 tiling（在不同轴上下刀)；以及——**PyTorch 里你调用的任何 matmul kernel，底层都会自动做 tiling**。如果是某种奇特的操作，你可能要自己考虑 tiling 以便局部复用，但连 PyTorch 也不是完美的，我们下面就要讲它的"不完美"之处。

### tiling 的复杂性之一：tile 尺寸与整除性

tiling 很强大，但也复杂。假设 tile 是 $128 \times 128$，矩阵是 $256 \times 256$——完美，4 个 tile。但把矩阵边长加 1，变成 $257 \times 257$：现在你得到两个"细长"的、里面基本没东西的 tile，利用率骤降。所以 tile 尺寸实际上是一个需要调优的对象。影响最优 tile 尺寸的因素：

- **合并访存**;
- **shared memory 的大小**;
- **矩阵维度能否被整除（divisibility）**。

如果你知道 PyTorch 的编译选项，有一个叫 **max-autotune** 的 flag：打开后，接下来 15 分钟 PyTorch 会跑一连串基准测试——它其实就是在你的矩阵上试各种 tile 尺寸，看哪个最快，而且你能从中获得不小的收益。

### tiling 的复杂性之二：内存对齐

与合并访存相关：如果 tile（或矩阵）的尺寸不对，**你试图读一个 tile 的动作可能触发很多次内存读取**。设想一个理想世界：蓝色的是某一行，tile 的宽度正好等于突发窗口的宽度——那 4 次读就能把整个子矩阵读出来，合并很完美。可一旦把矩阵尺寸移动一格，蓝色盒子错位了，你就无法用一次合并读把单个 tile 读完——因为现在这些读是参差、不对齐的，至少要读"两个 tile 的量"才能取出这一个 tile。解决办法是 **padding（填充)**，把边界对齐到突发窗口上。

这些复杂性，正是下一节"矩阵乘法的神秘曲线"里那些怪异现象的来源——我们马上把学到的一切用起来。

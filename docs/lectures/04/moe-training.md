# 训练 MoE 与系统稳定性：从负载均衡损失到 DeepSeek 演进

路由的机制清楚了，专家配置也讲完了，现在进入**训练**——这是 MoE 里最出人意料、也最能体现"深度学习魔法"的部分。Tatsu 回忆说，他最初学 MoE 时觉得"这种东西绝不可能训练好"，但事实证明，**一堆小技巧组合在一起，就能又好又稳地把它练出来**。

## 核心困境：训练时也要稀疏，但门控不可微

前面那个问题（训练时是否也激活全部专家）已经被预告过了，现在正式展开。训练时**不能激活所有专家**——否则就要付全部专家的 FLOPs，等于训练一个贵 $N$ 倍的模型。所以**训练时必须保持稀疏**。

但稀疏带来了两个大麻烦：

1. **门控决策不可微**:Top-K 是离散选择，argmax 类操作的梯度处处为零或未定义，梯度无法直接穿过；
2. **看不到反事实（counterfactual）**：你永远不知道"如果当初选了另一个专家，会发生什么"——只有被激活的专家给了你信号。

所以这个问题确实有点像 RL/bandit。有三种可能的解法：

1. **用 RL 优化门控策略**;
2. **随机扰动（stochastic perturbations）**：借鉴 explore-exploit 的思路加入随机性；
3. **一堆启发式的"平衡（balancing）"损失**。

猜猜实践中大家用哪个？答案就是**第三个**——一组非常有趣的启发式，它们最终把 MoE 训练得又好又稳。下面把三个方案依次讲一遍（前两个不被广泛使用，但值得知道）。

## 方案一：RL——能工作，但不是明确赢家

Clark 等人 2020 年研究过"能不能用 RL 学习路由器"。结论是：**能工作**——图里绿色那条线就是 REINFORCE 基线，它没问题。但**它并没有好到成为明确的赢家**；而且论文里提出的其他方法能**轻松击败**用 REINFORCE 梯度做路由的方案。

所以 RL 是"**原则上正确**"的方案——但**梯度方差与复杂度**让它非常难伺候，因此不被广泛使用。

## 方案二：随机扰动——给路由加点噪声

接近 RL、但更偏向"写下目标然后试"的启发式世界的是**随机近似（stochastic approximation）**，来自 Shazeer 等人 2017 年那篇早期稀疏门控 MoE 论文。做法是：训练时不做过硬的决定，而是**做随机的决定**。路由的内积照旧，但在取 Top-K 之前，**注入与输入规模相关的噪声**:

$$H(x)_i = (W_g x)_i + \epsilon_i \odot \mathrm{Softplus}\big((W_{\text{noise}} x)_i\big), \qquad \epsilon_i \sim \mathcal{N}(0, 1)$$

$$g(x) = \mathrm{softmax}\big(\mathrm{KeepTopK}(H(x),\, k)\big)$$

这里 $W_{\text{noise}}$ 是学出来的"噪声幅度"参数（经 Softplus 保证恒为正），相当于控制"注入多少噪声"的旋钮。它的作用机制是：如果两个专家分数接近，**随机地选其中一个而不是另一个**；反向传播时，对你有帮助的专家会获得更高的权重。于是：

1. **专家更鲁棒**：噪声让每个专家随机收到一些"意料之外"的 token，不至于过度专门化、变得脆弱；
2. **softmax 让模型学会"给 $K$ 个专家排序"**，而不是简单做硬选择。

另一个密切相关的方案是 Fedus 2022（Switch Transformer）的 **stochastic jitter**：对路由分数做**均匀的乘性扰动**，目标同样是"别让专家太脆弱"。这个技巧后来在 Zoph 2022 的论文里**被移除了**——消融显示，这些随机的"鲁棒性技巧"其实**并非必需**，去掉它们反而对**稳定性和最终质量**都有帮助。

## 方案三：启发式平衡损失——真正被使用的那个

先看如果不做任何平衡，会发生什么。你路由 Top-K 专家，然后**最强的专家获得更多信号**：反向传播说"这个专家表现好，把它的权重调高"→ 权重越高 → 被选得越多 → 更强……这就是"**富者愈富**"（rich gets richer）效应：被选中的专家权重越来越强，最终**跑掉（run away）、吞掉一切**。这就是**专家坍塌**（expert collapse）或**专家饥饿**（expert starvation）现象——它是 MoE 启发式训练必须解决的核心问题。

解法很直接：**加一个辅助损失（auxiliary loss）**，让 token 在不同专家之间**均衡分配**。最经典的是 **Switch Transformer(Fedus 2022)** 的版本。设 batch 里有 $T$ 个 token、$N$ 个专家，定义：

- $f_i$:**实际被路由到专家 $i$ 的 token 比例**——"硬"的分配：

$$f_i = \frac{1}{T} \sum_{x \in \mathcal{B}} \mathbb{1}\{\mathrm{argmax}_k\, p_k(x) = i\}$$

- $P_i$:**路由器"打算"给专家 $i$ 的概率质量**——把 softmax 分数在 batch 上平均,是"软"的分配:

$$P_i = \frac{1}{T} \sum_{x \in \mathcal{B}} p_i(x)$$

辅助损失就是这两个向量的内积（它们都粗略地像概率分布，内积衡量"像不像"）：

$$\mathcal{L}_{\text{aux}} = \alpha \cdot N \cdot \sum_{i=1}^{N} f_i P_i$$

其中 $\alpha$ 是损失权重。这个目标本身不是你能从第一性原理"推出来"的东西——**最容易理解它的方式,是看它对概率的导数**。把 $f_i$(来自 argmax,没有梯度)当作常数,对 $p_i(x)$ 求导:

$$\frac{\partial \mathcal{L}_{\text{aux}}}{\partial p_i(x)} = \frac{\alpha N}{T^2} \sum_{x' \in \mathcal{B}} \mathbb{1}\{\mathrm{argmax}_k p_k(x') = i\} \propto f_i$$

也就是说，**下压的力度与专家被使用的频率成正比——越常用的专家，被压得越狠**。这就是这个损失的作用：把热门专家"泼冷水"，把概率质量从热门专家身上推开，路由分布被推着走向均匀。

![](/lectures/04/slide-40.png)

几乎所有人都在用这种 $f \cdot P$ 形式的技巧来均衡 token 在不同"单元"之间的分配。剩下的问题是：**"单元"到底是什么？**

## DeepSeek v1/v2：逐专家平衡 + 逐设备平衡

DeepSeek v1/v2 的做法基本照搬上面这套，再加一个设备级变体：

- **逐专家平衡（per-expert balancing）**：和 Switch Transformer 完全一样——对每个专家，平衡"实际分配 $f_i$"与"意图概率 $P_i$";
- **逐设备平衡（per-device balancing）**：目标函数相同，但**把"按专家求和"换成"按设备分组求和"**——统计哪些 token 去了哪些设备。为什么要这个？DeepSeek 在系统设计上很精明：如果你的专家分布在不同设备上（比如这台机器 4 个专家、那台机器 4 个专家），你希望**两台机器都被用满**。所以不仅要让专家均匀，还要让**设备均匀**——这是纯粹的**利用率**（utilization）考量。

## DeepSeek v3：逐专家偏置与"并非完全无辅助损失"的平衡

到了 DeepSeek v3，他们换了一种方式：为每个专家维护一个**偏置项 $b_i$(bias)**。路由器照常算亲和度，但**在做 Top-K 时，给分数加上偏置再排名**:

$$g'_{i,t} = \begin{cases} s_{i,t}, & s_{i,t} + b_i \in \mathrm{TopK}\big(\{s_{j,t} + b_j\},\, K\big) \\ 0, & \text{otherwise} \end{cases}$$

$b_i$ 的更新**不靠梯度,而是在线学习(online learning)**:每个训练步结束,监控每个专家在整个 batch 上的负载——**过载(overloaded)就减小 $b_i$,欠载(underloaded)就增大 $b_i$**。相当于一个"越冷门的专家越容易被选上"的动态调节器,不产生梯度、不干扰主损失——所以他们管这叫"**无辅助损失平衡(auxiliary-loss-free balancing)**"。

但 Tatsu 特别指出:**这个说法并不完全诚实**——为了防止极端不均衡,DeepSeek v3 仍然保留了**序列级(sequence-wise)的辅助损失**(本质还是 $f \cdot P$,只是把聚合单位从 batch 换成单条序列)。所以至今**没有任何方案能完全摆脱辅助损失**——只是把"难看的"那部分最小化。

## 如果去掉负载均衡损失,会发生什么?

OlMoE 论文做了一个非常直观的消融。**右上角**:有负载均衡损失(粉色/紫色曲线),loss 曲线很正常;去掉负载均衡损失,loss 显著变差。**左下角**更触目惊心:看每个专家实际分到的 token——**没有负载均衡时,几乎所有 token 都涌向两个专家**(黄色和粉红色),**其余专家"死亡"、什么都不做**;而有负载均衡时,所有专家都被均匀利用。

![](/lectures/04/slide-43.png)

换句话说,没有负载均衡损失,你**白扔了大部分参数**——无意中训练了一个"2 专家 MoE"。Tatsu 的总结是:这个训练过程其实非常反直觉——你有一个**非可微的、相当复杂的对象**(Top-K 选择),而**你只需要加一个平衡损失把专家拉均匀,其余一切照常"泵"梯度进去,模型就能训练得很好**。背后的动态是:

> **"有用的专家被强化"的正反馈循环,恰好被"均匀化"的负反馈抵消**——两个动力互相制衡,训练就稳了。

(同样的技巧在 DSA 里也用过——Top-K 选择 + 辅助损失来支撑不可微性,以后会在更多架构里看到这个"配方"。)

## 课堂问答:专家的语义与平衡损失的粒度

### 问答:这些"专家"真的有语义分工吗?

(同学:把 MoE 联系到系统优化——但当你真的去看它们,它们算"专家"吗?真的有不同领域分工吗?)

**Tatsu**:有些论文会画出"哪些 token 激活了哪些专家"的可视化。因为**路由器实在太简单了**,专家并不是"聪明的专家"——不是"医学专家""法律专家"这种。你确实能看到某种倾向:**标点可能被路由到某个专家、其他符号/非英文字符集可能被路由到另一个专家**。但绝对不存在"这是华尔街日报专家"之类的东西——**没有语义**,这大概是最准确的说法。

### 问答:为什么既要逐专家损失,又要逐设备损失?

(同学:为什么有 per-expert loss 还有 per-device loss?后者有什么特别的?)

**Tatsu**:**逐专家损失如果被完美执行,在专家均匀分配的前提下,其实也会带来逐设备的平衡**。但我个人的理解是:你**不希望把逐专家损失调得太高**,强求完全均匀——那会损害训练动态。而**逐设备平衡足够重要**,值得为此额外加一点损失去鼓励设备间的均衡。所以两者各有各的位置:专家级平衡主要是模型质量的事,设备级平衡主要是系统利用率的事。

## 训练 MoE 的系统侧

MoE 给系统带来了新的动态。回顾一般的并行化:**数据并行**把数据集切成多份分给多台机器——但一旦 batch size 到头,**数据就没什么可切的了**;**模型并行**按模型的自然切点切——切点用尽,也就到头了。MoE 的**专家并行**(expert parallelism)提供了**另一个可并行化的轴**:每个 FFN 天然是一个可放置到不同设备的"块",把激活路由过去即可。

### 稀疏矩阵乘:MoE 与硬件的"共设计"

另一个系统要点与**稀疏矩阵乘法**(sparse matrix multiplication)有关。如果你在一个 GPU 上有多个专家,一种想法是做**多个小矩阵乘**——但这不好,你希望的是**更大的矩阵乘**(能复用 cache、做各种优化)。于是取而代之的是:**利用硬件原生的结构化稀疏(sparsity)**——**块对角(block diagonal)是最基本的形式**,但你可以用更复杂的结构化稀疏,它们**在硬件里原生支持**。MoE 的计算模式几乎就是这些结构化矩阵乘法——非常适合硬件高效执行。这就是正在发生的**硬件-架构共设计(hardware-architecture co-design)**。现代库如 **MegaBlocks**(许多开源 MoE 都在用)就实现了更聪明的稀疏矩阵乘。

### Nemotron 3:向下投影激活以减少通信

专家并行要求**把激活从设备搬去设备**("你属于那个专家,我把你搬过去"),这会带来显著的**通信开销**。Nemotron 3 提出了一个很新的想法:**既然共享专家不需要通信,可以让它保持大维度;而需要通信的路由专家,让它们的激活维度尽量小**。做法是:**先把残差流向下投影(down-project)到低维,再做那个"把激活发出去"的集体通信(collective communication)调用**。这样既大幅省下通信,又不至于完全牺牲隐藏维度。这是一种**在通信与模型尺寸之间做权衡的投影技巧**。

## 一个"有趣的副作用":MoE 的随机性

Naive 的 MoE 推理基础设施还有一个麻烦:**token dropping**。除非专家在输入分布上完美均衡,否则某些专家会比其他更受欢迎。一旦某个专家(比如专家 0)特别热门,它的**token 队列会越积越长**,最终你不得不**丢弃 token**。

早期一代的 MoE 推理代码的做法是:**静默丢弃**——假装无事发生,把零送回去。后果是诡异的不确定性:**token dropping 发生在 batch 层面**——也就是说,**别的用户发的查询如果撞上了你正在用的专家,就可能把你的 token 挤出队列**,让你得到更差的结果!好在现在的**无丢弃(dropless)架构**已经把这类问题解决了——MegaBlocks 等常见开源 MoE 框架没有这个问题。

## 稳定性:又一个 softmax

上一讲讲过稳定性:指数运算与除法是两大"雷区",所以 **softmax 是稳定性问题的危险地带**。而 MoE 在路由里**又引入了一个 softmax**。Zoph 等人很早就注意到了 MoE 中 softmax 的潜在危险,专门写了一篇关于 MoE 稳定性的论文。

常见的解法是:**只对专家路由器(router)使用 float32**(训练里最敏感、最棘手的部分用更高精度),有时**再加上一个辅助的 z-loss**。z-loss 我们上一讲讲过(惩罚 log-softmax 归一化常数偏离零),在 MoE 路由稳定上**相当流行**。OlMoE 对"加不加 z-loss"做过消融:去掉 z-loss,训练损失曲线会出现**明显的尖峰**。

## 微调问题:稀疏 MoE 会在小数据上过拟合

你可能在实践里也遇到过:**MoE 很难微调**。它参数太多,微调专家时**过拟合非常严重**。看 train/val 的差距:稠密模型两者很接近、不会疯狂过拟合;而**稀疏模型的 train/val gap 极大**——在某个 GLUE 任务上微调时,训练损失降得很低,验证损失却远远落在后面。

对策有几类:

- **只微调非 MoE 的层**(Zoph 等人的方案)——比如微调非 MoE 的 FFN、或者**只微调注意力**。其中"只微调注意力"是 Tatsu 在近期的 MoE 工作里经常看到的做法;
- **使用大量数据**(DeepSeek 的方案):用 **140 万条 SFT 样本**之类的大规模数据,在微调阶段**基本把 MoE 整个重新训练一遍**,这样泛化差距就没那么大了。这是"苦涩教训(bitter lesson)"式的答案:如果你数据够多,直接重训就好。

## 其他训练方法:upcycling(从稠密模型"升级"成 MoE)

最后一个 MoE 专属的技巧是 **upcycling**。这个技巧在过去一年**已经没那么流行了**——Tatsu 说今年他没见过一个 upcycled 的模型——但早期有一些非常漂亮的模型用了它,值得知道。

做法:如果你想得到一个 MoE,**直接拿一个已经训练好的稠密模型**,把它的 MLP **复制成很多份**,再加一个**随机初始化的路由器**,然后继续训练。因为"哪些输入去哪个 MLP"有随机性,这些专家会**开始专门化**,最终你就得到了一个 MoE。最早的论文证明:**upcycling 一个稠密模型,比继续训练同一个稠密模型,能拿到更好的性能**。

两个成功案例:

- **MiniCPM**:把 24 亿参数的 MiniCPM upcycle 成 134 亿参数的 MoE(top-k=2,8 个专家,约 40 亿激活参数,训练约 5200 亿 token)——拿到一堆"几乎免费"的收益;
- **Qwen**:把 **Qwen 1.8B** upcycle 成 **Qwen MoE**(top-k=4,60 个专家、4 个共享,约 27 亿激活参数)——这是**最早的大规模 upcycling 成功案例之一**,也是当时性能最高的开源小模型之一。

不过如今**几乎没人再 upcycling 了**——大家不再"先训稠密、再转换",而是**直接就把 hero run 训练成 MoE**。但 Tatsu 强调,这仍然是 MoE 动作空间里的一个重要的、值得知道的想法。

## 完整走一遍:DeepSeek MoE v1 → v2 → v3

最后,把 DeepSeek 三代模型走一遍——从中能学到很多,也推荐大家去读 DeepSeek 的论文(写得非常好、细节非常多)。

### V1(160 亿总参数 / 28 亿激活):"柏拉图式的理想"

**DeepSeek MoE v1** 已经是一大批现代 MoE 的原型:它有**共享专家(2 个)+ 细粒度专家**(64 个、切成 4 份)的结构,用**标准 Top-K 路由**,配**标准的辅助损失平衡(专家级 + 设备级)**。在某种意义上,这是 MoE 的"**柏拉图式理想形态(Platonic ideal)**"。

### V2(2360 亿总参数 / 210 亿激活):把系统放进目标函数

**DeepSeek MoE v2** 基本就是把 V1 **放大**:2 个共享专家、更多细粒度专家(160 个、切成 10 份),6 个激活。新增了两样东西:

- **Top-M 设备路由(device routing)**:不只选专家,还显式考虑设备;
- **通信平衡损失(communication balancing loss)**:同时平衡**通信进与出**。

这两者本质上都是**为了优化系统而加的辅助损失**。Tatsu 强调一个观点:**成功的语言模型训练不只是深度学习,还关乎"真正尊重你的系统"**——DeepSeek v2 正是这种哲学的体现。

### V3(6710 亿总参数 / 370 亿激活):平衡方式的再创新

**DeepSeek MoE v3** 仍然沿用共享 + 细粒度的设计(1 个共享 + 256 个细粒度,8 个激活),但换了**平衡方式**:用前面讲的**逐专家偏置 + 在线学习**(号称"无辅助损失"),并且从 softmax 换成了 **sigmoid + softmax** 的组合来加权专家。其他大体与 V2 相似。

## 组成 DeepSeek v3 的额外组件:MLA 与 MTP

既然讲到了 v3,顺便把让 v3 成为顶尖系统的两个额外组件也讲了。

### MLA:多头潜在注意力(Multi-head Latent Attention)

基本想法:**不直接产生 $Q$、$K$、$V$,而是先产生一个低维的"潜在(latent)"激活 $c$,再把 $Q$、$K$、$V$ 表示成 $c$ 的函数**。收益是:做 KV cache 时,**不需要缓存所有 $K$ 和 $V$,只需要存 $c_t^{KV}$**——而 $c$ 维度低得多(所以叫"潜在注意力"):$W^{UK}$ 还可以合并进 $Q$ 投影里。

唯一的复杂之处:**MLA 式缓存与 RoPE 有冲突**。没有 RoPE 时,注意力分数是 $\langle h\, W^Q W^{UK},\, c_t^{KV} \rangle$;有 RoPE 时,旋转会插在中间,破坏"先投影成 latent 再缓存"的结构。他们的解法是:**保留少数"非潜在(non-latent)"的 key 维度用于旋转(RoPE)**,其余维度照常走潜在缓存。

### MTP:多 token 预测(Multi-Token Prediction)

DeepSeek v3 还有一个很酷、但没怎么流行开的主意:**MTP**——不再只预测下一个 token,而是**一次预测多个 token**。它的好处有两层:

1. **统计层面**:有统计论证说明同时预测多个未来 token 能帮你更好地预测未来;
2. **系统层面**:MTP 相当于内置了一个**推测解码**(speculative decoding)器——(Percy 之后讲推理时会讲到)。

(DeepSeek v3 实际只做了**多预测一步**的 MTP。)

## 本讲总结

把一切串起来:

- **MoE 利用稀疏性**——**不是所有输入都需要完整模型**;用稀疏激活,你可以拥有比"付钱买的"更多的参数——不付全部参数的计算成本,却拿到参数带来的好处;
- **离散路由很难,但 Top-K 启发式确实有效**——你可能会以为这个路由问题非常难,事实证明**即使在大规模下,非常简单的东西也能工作得很好**;
- **有大量经验证据表明 MoE 有效且划算**——到这个时间点,MoE 已经确定无疑地**会留下来**。所以你应该理解它是什么、它是怎么工作的。

# 插曲：TPU 与 GPU 的强项

本讲大部分内容围绕 GPU，主要是因为大家出去写代码、训练模型，多半会在 GPU 上进行。但 Tatsu 认为讲 TPU 很重要：一是因为 TPU 很酷、也越来越流行；二是因为 **TPU 是 GPU 的"另一种进化分支"**——对照一下，你能看出哪些是相同、哪些是不同的设计决策。

## 趋同演化：为什么 TPU 看起来很像 GPU

一个非常有趣的事实是：**TPU 与 GPU 在高层面上非常相似**。这是**趋同演化（convergent evolution）**：如果你想建造一个能效良好的机器学习加速器，你最终会走到差不多的位置。TPU 在某种意义上**更简单**，更针对机器学习工作负载做优化：它有**更轻量的控制单元**和**大得多的矩阵乘法单元**。

TPU 的基本结构与 GPU 相似：一个专门做矩阵乘法的电路、能做并行向量运算的组件、一些控制单元；内存结构也很像——慢的 **HBM（高带宽内存)** 加上更快的局部内存 **SMEM(shared memory)**。真正的差别在于这些部件的**尺寸与灵活性**。而且，最大的差别其实在**网络（networking）**上，不在单块芯片上——因为单芯片说到底就是"为乘矩阵而活"。这一点本讲不展开，并行化那一讲会细讲。

![](/lectures/05/slide-13.png)

JAX 书里有一张很好的对照表，把 GPU 的概念一一映射到 TPU，这个映射非常精确：GPU 的 **tensor core**（矩阵乘法单元）几乎精确对应 TPU 的 **MXU**(matrix multiply unit)；抠细节的话，它们底层用的甚至是同样的电路——**脉动阵列（systolic array）**，一种把数据流进来、流出去从而完成矩阵乘的结构。

这里有个非常容易混淆的命名陷阱，务必小心：**TPU 管自己的"流式多处理器"叫 tensor core，而 GPU 管自己的"矩阵乘法单元"叫 tensor core**——两者的名字一模一样，但含义完全不同。所以遇到"tensor core"这个词，你得靠上下文区分：对 TPU 而言它指一个处理器，对 GPU 而言它指矩阵乘单元。

## 数量差异：少而大 vs 多而小

两者的主要区别在于**单元数量**。一块典型的 GPU（比如 **H100**）大约有 **132 个 SM**（处理器)；而一块 TPU 只有 **2 个单元**并行运行。再只看矩阵乘单元：GPU 有 **528 个**,TPU 只有 **8 个**。这些数字大致按"可比较的对象"来缩放。

为什么是这种分布？TPU 依靠**更少但更大**的矩阵乘单元；GPU 依靠**更多但更小**的矩阵乘单元。可以想象：小而多的单元给你更多灵活性——你可以把它们编程去做这做那；而 TPU 被锁定在**大矩阵乘**上。Tatsu 讲了一个亲历的趣事：在他最近一篇论文里做 batch size 扫描，一路扫到 64 就停住了——因为 TPU 的 tensor core **拒绝接受任何小于 64 维的输入**，它只做大的矩阵乘。

尽管有这些差异，GPU 与 TPU 共享两个核心支柱：**内存层级（快内存与慢内存）** 与**矩阵乘法单元**。因此，本讲教的核心理念可以直接在 GPU 与 TPU 之间迁移——基本思想永远是一样的，这也是趋同演化的结果：成本有效地分配内存的方式只有那么几种，快速地做矩阵乘的方式也只有那么几种，除了少数设计决策不同，你最终会到达同一个地方。

## GPU 模型的强项

GPU 之所以取得巨大成功，有几个原因：

1. **极易扩展**：想要更多吞吐量，不断加 SM 就行——只要内存带宽能喂饱这些 SM，吞吐量就线性往上走；
2. **SIMT 模型让编程"出奇地容易"**：如果你试着写 PTX 这类接近机器码的低层代码，你会发现它是可写的，因为一切都是 SIMD(Single Instruction, Multiple Data)——你不是在逐线程编程，而是说："这是我的指令，这是我的输入，把它们都跑一遍。"这跟你用函数式风格对集合做 apply/map 其实很熟悉；
3. **线程非常轻量**：可以随时停止、随时启动。调度器可以决定"有另一个 warp 更值得跑，我把你停掉换它上来"，这种任务切换非常快。如果某些任务停滞了、或者有拖慢吞吐的性质，轻量线程就能换来高得多的整体吞吐。

## 硬件史：从"黑客数学"到 Tensor Core

即使是在 Tensor Core 出现之前，人们也早就意识到：消费级图形硬件的巨大并行性，会很适合科学计算。早期的 GPU 编程，**shader（着色器）被黑客们拿来强行算矩阵乘法**——这是最早的"用图形硬件做快速矩阵乘"的论文之一，是非常酷的黑客工程：可编程 shader 本来是为了渲染，但你可以写特定的 shader 来得到矩阵乘，而且**不同的渲染设置甚至给出不同的 matmul 速度**。

如今你完全不需要这么做。从 **V100** 开始，NVIDIA 决定：给你一块专门做矩阵乘法的硬件。一旦这块硬件存在，**matmul 就变成了机器学习里的"特权操作"**：可并行但不是矩阵乘的操作，与矩阵乘操作之间的吞吐差距是**一个数量级**——矩阵乘比 GPU 上任何其他浮点运算快 **10 倍以上**。这也是为什么，任何能随算力扩展的近期机器学习架构里，几乎一定有一个矩阵乘法：这是真正能高效获得大量计算吞吐的途径。

## 算力扩展得比内存快：内存墙

本部分最后一件事：**GPU 的不同部件正以不同的速度扩展**。灰线是总体浮点运算吞吐（FLOPs），增长最快；绿线是**内存带宽**，增长相对缓慢；蓝线是**并行度/设备互联**，也在非常缓慢地增长。

![](/lectures/05/slide-18.png)

这意味什么？在早期做 GPU 编程时，你可能不太考虑内存，因为那时计算并不比内存搬运快太多；但越往图的右侧走，计算与内存之间的**差距越来越大**——这正是本讲讲的很多优化都是**内存优化**的原因。随着差距拉大，内存与通信瓶颈会越来越突出，要用满现有硬件需要付出越来越多的工作。

Tatsu 顺带预告了推理硬件领域更疯狂的局面（他本来不想讲，被同学问到了）：去年大家开始做 **prefill/decode 分离（prefill-decode disaggregation）**——prefill 部分（重矩阵乘）放一种芯片，decode 部分（更受内存带宽限制）放另一种芯片；一些模型（比如中国开源模型 **Step One 3**？）甚至尝试按层分离：**attention 去一种加速器，MLP 去另一种加速器**。如果算力-内存差距继续扩大，任何"巧妙利用你宝贵的快内存"的技巧都会变得非常值钱——而推理比训练更受内存约束。

## 第一部分小结

到这里，我们对 GPU 的硬件有了一个大致的图景。Tatsu 给这一部分的小结是：

- GPU 是**大规模、大规模并行**的：海量执行单元同时执行指令；
- **计算（尤其 matmul）扩展得比内存快得多**——所以内存极其重要；
- 正因为内存重要，我们做的一切都要**尊重内存层级**：尽可能把东西放进 shared memory，而不是全局内存。

有了这些基础，就足够去内化第二部分的内容了：怎么把机器学习工作负载在 GPU 上跑得快。

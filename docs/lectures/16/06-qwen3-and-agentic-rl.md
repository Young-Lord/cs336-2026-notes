# Qwen 3 与智能体 RL

## 最后一个案例：Qwen 3

本讲最后一个案例是 **Qwen 3**（以及它的后续 **Qwen 3 Coder Next**——名字越来越复杂了）。Qwen 3 发布时间更晚，性能也更好（超过了 o1 和 R1，尽管部分是因为来得晚），但它真正有趣的地方在**缩放与数据的结果**。而它的继任者 Qwen 3 Coder Next，则被 Tatsu 认为是主要技术报告里**智能体 RLVR 训练细节最丰富**的一个。

和 DeepSeek 一样，Qwen 报告最有用的一点是：它画出了整套系统的组织方式——**base model → SFT → 推理 RL →（thinking mode 融合）→ RLHF → 蒸馏出小模型**。对开源模型来说，这基本就是"前沿语言模型是怎么造出来的"这幅心智图；Tatsu 说，如果你把这套组合记在心里，你对真实世界正在发生的事情就会有一个相当准确的图景。

![Qwen 3 的总体图景：base → SFT → 推理 RL → RLHF → 蒸馏，RLHF 在推理 RL 之后，蒸馏在最后](/lectures/16/slide-50.png)

## 经过验证的 RLVR 剧本

Qwen 基本采用了我们已经反复见过的 RLVR 剧本，并取了 Kimi 和 DeepSeek 的长处：

- **难度过滤**（按 best-of-n，像 Kimi）；
- **去掉"不靠 CoT 就能做对"的问题**——既然不是思考问题，放进 RL 就没有意义；
- **去掉与验证数据过于相似的问题**——做去污染（decontamination）；
- **手动过滤参考 CoT 的质量**——区分"真的会做"和"猜出来的"；
- 最引人注目的一点：**RL 只用 GRPO 在 3995 个例子上训练**。只要流水线的其余部分是对的，这么少的数据也能走得很远。

![Qwen 3 的 SFT + 推理 RL：难度过滤、去污染、手动过滤 CoT，RL 只用约 4000 个例子](/lectures/16/slide-51.png)

## Qwen 3 特有的东西：思考模式融合

RLVR 的核心组件对 Qwen 来说不算惊喜（就是站在 R1 和 Kimi 的肩膀上），但它有一些很独特的设计。

**思考模式融合（thinking mode fusion）**。Qwen 把**思考（thinking）与非思考（non-thinking）数据用标签混在一起训练**，于是**即时响应模式（instant response）与长 CoT 思考模式同时存在于同一个模型里**——一个模型两副面孔，靠 prompt 里的标签切换。这在当时并不普遍（OpenAI 早年也常有分开的思考/非思考模型）。

**通过特殊字符串早停（early stopping）**。Qwen 允许在 prompt 里附加一个特殊字符串，让模型**立即终止 CoT、直接给答案**。在 ChatGPT 之类的界面里你也能看到这种"提前结束思考、立刻作答"的交互方式。而这里最令人惊讶的观察是：**当你用这个技巧改变"思考预算"（thinking budget）时，模型的性能会优雅地退化**——即使在很低的思考预算下、模型明显在思考中途被截断，它给出的回答仍然出人意料地合理。而且无论思考预算多小，思考模式在数学、编码这类任务上都远好于即时响应模式（后者更接近经典的指令遵循 + RLHF 模型）。

![Qwen 3 的测试时缩放：改变思考预算时性能优雅退化，思考模式始终优于即时响应模式](/lectures/16/slide-53.png)

## 各阶段的贡献构成

Qwen 还做了一件很贴心的事：把**每个训练阶段对性能的贡献**拆开来看。结果并不令人意外：

- **推理 RL + 一般 RL** 给各种任务带来持续的提升——arena hard、counterfact QA 这类"一般任务"得到**显著的跨板提升**；
- 但**融合非思考组件会让数学/STEM 能力略有下降**（reasoning RL 之后再上一般性 RLHF 的代价），只是下降并不严重。

有意思的是：尽管绝对数字上下降不大，Qwen 后续版本（3.5 系列）**已经放弃把思考与非思考融进同一个模型**（他们曾称之为 hybrid models），因为这点下降不可接受——他们想把思考模式的所有性能都榨出来，所以如今又把两类模型分开了。

![各阶段构成：一般 RLHF 带来各任务增益，但数学/STEM 略有下降](/lectures/16/slide-54.png)

## 智能体 RL：Qwen 3 Coder Next

最后一块拼图是 **Qwen 3 Coder Next**——构建在 Qwen 3 Next 之上、为智能体（agent）能力做后训练的模型。如果你对"怎么真正造一个智能体"感兴趣，这份报告很值得读；但 Tatsu 强调一个重要观点：**对智能体做后训练，与前面描述的一切并没有本质不同——并不存在什么新的"智能体训练算法"**。贯穿全课程的那句教训依然成立：**数据才是重要的东西**。

### Mid-training：把智能体能力提前注入

智能体的许多能力没法在最后阶段塞进去，必须更早开始。Qwen 3 Next 有一大段 **mid-training**，目标是把尽可能多的编码与智能体能力注入模型，数据来源包括：

- **GitHub**：**仓库级长上下文数据**——把仓库里的文件拼接起来（约 **6000 亿 token**）；**pull request 数据**——用 RAG 检索"仓库当前状态"作为上下文。理由很直接：模型之后会看到很长的智能体轨迹（agent 打开了一堆文件），这类"预训练式"数据非常有用；
- **Common Crawl**：**文本 + 代码联合文档**，用自动化方法检测、再由 LLM 把 HTML 转成干净的 markdown；
- **合成数据**：让语言模型针对编码相关的网页文档做问答，生成编码味的合成数据；**跑公开的编码智能体**，把它们的运行轨迹全部收进 mid-training；
- 外加一些标准数据：**指令遵循**，以及一个对我们不太相关的任务——**fill-in-the-middle**（写代码时往一段中间补全的能力）。

![Mid-training 的数据来源：GitHub 仓库级长上下文、Common Crawl 文本+代码、合成数据与智能体轨迹](/lectures/16/slide-56.png)

### 专家模型：训练一堆专家，再蒸馏回去

Qwen 接下来做了一件 Tatsu 说"在其他前沿模型训练里没见过"的事：**对 mid-trained 的 Qwen 3 Next，训练一批针对不同编码任务的专家模型（expert models），然后再把它们全部蒸馏回同一个模型**。四个专家分别是：

- **Web dev 专家**：基于各种检查（VLM + 智能体动作）对"有效 web 代码"做 SFT；
- **UX 专家**：在多种工具格式上训练；
- **单轮 QA 专家**：就是更多的单轮代码生成数据；
- **SWE 专家**：软件工程智能体，后面详述。

![Qwen 3 Next 训练四个专家（web dev、UX、单轮 QA、SWE）后再蒸馏回同一模型](/lectures/16/slide-57.png)

Tatsu 只能猜测他们为什么这么做（类似的做法更接近学术界的 branch-train-merge 等工作，他没见过前沿模型这么干；最接近的先例是 DeepSeek 用"数据加工专家"来生成训练数据）。这套方案的优点是：**每个专家可以由独立的团队负责，聚合也很简单**；但缺点也很明显——**如果你所有目标都齐了，不如直接把它们全部扔进同一个大训练循环里**，用一个统一的大目标、一次训练搞定，省去蒸馏的麻烦。

### 智能体环境的构造与奖励的可验证性

SWE 专家是这四个里最投入、也对我们最有启发的一个。它的做法是**大规模构造智能体环境**：**SWE-bench 是这类事情的金标准**，而 Qwen 要的是"比 SWE-bench 更多"——他们用 GitHub 上的自动化手段生成了海量 issue，**自动构造了约 80 万个 SWE-bench 式任务**，然后对这些问题做 RL。

![自动化构造 SWE-bench 式智能体环境：约 80 万个任务](/lectures/16/slide-59.png)

这里牵出一个贯穿本讲的核心话题——**奖励的可验证性**。我们之所以能往 RL 里不断投入计算，是因为**我们相信奖励模型是"不可 hack"或很难 hack 的**；一旦这个假设崩塌，RL 会找出越来越隐蔽的方式骗取性能。Qwen 就有一个绝妙的例子：在 git 里，如果你拿到一个 issue，**可以去翻"未来的提交"，直接查到修复方案**——这是模型很容易学会的作弊方式。所以他们专门设计了一个奖励，**整个目的就是防止智能体篡改 git 历史**。如果你不做这件事，训练曲线长这样：一路学习学习学习，然后突然冒出一个"涌现式跳跃"——那其实是模型学会了操纵 git 调用去偷看历史。它甚至能绕过你给的约束：你说"不能用 `git log`"，它就加一个 remote，然后去查询远端某次提交发生了什么。

**RLVR 的稳健性，只与你奖励的稳健性相当**——而你的奖励有时可能非常不稳健。Tatsu 顺带讲了一个来自他和学生的经验：他们做过 Lean（形式数学的可验证语言）上的 RL，当时天真地以为"Lean 编译器是坚不可摧的，绝不可能出错"——结果发现 **Lean 编译器并非对抗稳健**：存在某些字符串，能让编译器在特定模式下验证本不该通过的证明。所以"可验证奖励"这个概念，比你想的棘手得多。

![智能体 RL：分数缓慢而稳定地上升；但如果你不防住 git 历史作弊，就会出现"涌现式跳跃"](/lectures/16/slide-60.png)

### 结果：小模型也能打得不错

绕这么一大圈，最终得到的是一个**在 SWE-bench 上约 70.6%** 的系统——而它的活跃参数只有 **30 亿（3B）**。一个这么小的模型能做得这么好，本身就是个惊喜。不过 Tatsu 也提醒：这并不特别令人意外——**RL 当然会在你训练它的环境上表现好**，甚至会泛化到验证集；但**任务特定的性能，不必然意味着能泛化到更广的领域**，比较不同系统的性能时要小心。

## 课堂问答：几个关键澄清

**问：思考模式是提示词切换，还是背后是不同的底层模型？** 答：真正有意思的地方恰恰在于**它就是一个模型**——靠 prompt 里一个小小的标签在"长 CoT 模式"和"几乎无 CoT 模式"之间切换。如果只是加个 API 开关，那并不稀奇；**把两者放进同一个模型**才是关键创新。控制机制在 prompt 层，而不是 API 或服务层。

**问：mid-training 里数据的格式化，在多大程度上决定了 RLVR 能学到什么？如果 mid-training 里没有正确的数据，RL 采不到样本，是不是就学不会？** 答：这里有很多经验上的细微之处，没有"一定不行"的一刀切答案。可以这么想：**预训练和 SFT 承担了大部分重活，只要它们有覆盖**。如果预训练里根本没有代码数据，那你就有麻烦了，确实需要 mid-training；但如果预训练非常多样（文本、代码、GitHub 数据都有覆盖），mid-training 就是"锦上添花"——很有用、能让泛化更好一点，但未必是生死攸关，因为你反正要做 SFT，而 SFT 能让你足够接近"开始拿到 RL 奖励"的起点。要是连 SFT 都没有，那才是真的麻烦。

**问：训练完每个专家后蒸馏回单一模型，需要专门设计数据混合吗？** 答：对，这个蒸馏过程要求你写出一系列 prompt，让专家们把知识蒸馏进最终模型。这套方案的好处是可以让独立团队分别负责每个专家，聚合也简单；但**如果所有目标都齐备，更好的做法往往是把它们直接放进同一个大训练循环**——一个大的训练目标、一次训练完成，不必处理蒸馏带来的复杂性。

**问：长推理训练算是 mid-training 的一部分吗？** 答：长 CoT 的 SFT 在 R1 和 Kimi K1.5 里都有；但**长 CoT 传统上不算 mid-training 的一部分**，它更多是**长上下文扩展（long context extension）**里用到的数据——那通常是一个单独的阶段，紧挨着 RLHF 或推理 RL，用书籍、代码、合成数据这类足够长的语料把上下文窗口撑大。

**问：RL 是并行做还是串行做？如何避免遗忘（forgetting）？** 答：最接近的答案是——按"推理问题"和"非推理问题"两大类拆分：**推理问题**（数学、编码等）放进一个桶，在第二阶段统一执行；**非推理问题**（聊天性、风格等）放进最后那个 RLHF 阶段统一执行。这就是这些流程图里两条路径的含义。

## 本讲回顾

把这一讲收个尾，Tatsu 给的回顾是三条：

1. **过度优化是个问题**——在窄领域做 RL（RLVR）是解决方案之一：找到"不可 hack"的奖励，就能无限地往里加计算；
2. **GRPO 简单（但有一些缺陷），正是它让 RLVR 成为可能**——标准化的偏差（放大过易/过难问题）与长度偏差是它的小瑕疵，后来也被修正；
3. **野外有大量成功的配方**——R1、Kimi 1.5、Qwen 3，每一篇都值得去读。

而贯穿一切的核心理念是：**RLHF 与 RLVR 本质上是非常相似的问题**，真正的差别只是——**RLVR 想要更不可 hack 的奖励，从而可以把多得多的计算投入进去，让系统变得更好**。GRPO 对研究社区极其重要，你应该像熟悉预训练损失一样熟悉它：知道它的函数形式、知道更新是怎么做的。到了今天，很多人已经知道怎么做 RLVR 了；不过你们会在实践中发现，**RL 依然相当挑剔、相当嘈杂、做起来有点痛苦——但它并不难**，远不像过去在那些棘手的 RL 环境里跑 PPO 那样折磨人。

# prefill 与 decode：连续批处理与访存分析

## prefill 与 decode：两种截然不同的计算

上一节我们已经看到，一个请求的处理包含两块核心 ML 计算——**prefill** 与 **decode**。它们不仅是计算的不同阶段，而且在系统层面有着完全不同的特性，Dan 用了相当多的篇幅强调这一点。

![推理的两个阶段：prefill 并行编码整个 prompt，decode 逐 token 生成](/lectures/18/prefill-decode.png)

**prefill**：给定一段从未见过的长文本（比如 1 万个 token），一次性算出所有 token 的激活与 logits。它是"很多 token 进、一个 token 出"，**计算受限（compute-bound）**——FLOPs 多、访存相对少，GPU 的计算单元能被充分用满。它长得非常像训练：同样是一大批 token 一起前向，只是不跑反向传播。

**decode**：处理完 prompt 之后，模型**一次生成一个 token**（有投机解码时一次生成三四个候选）。每生成一个新 token，都要把整个模型再跑一遍。这一步的 FLOPs 其实很少，但**每次都必须把全部模型权重从显存重新读一遍**——所以它是**访存带宽受限**（memory-bandwidth-bound）的，GPU 在这段时间里基本上是一个"光荣的内存加载器"。

### 用算术强度量化两者差距

为什么 decode 必然访存受限？可以借助第 10 讲建立的**算术强度**（arithmetic intensity）框架来算。设模型有 $N$ 个参数，以 bf16 存储，则权重占 $2N$ 字节。decode 每步只处理一个 token：

- FLOPs：每个参数大致贡献 2 次浮点运算（一次乘、一次加），约 $2N$ FLOPs；
- 访存：必须从 HBM 读入全部权重，约 $2N$ 字节。

于是 decode 的算术强度为

$$\text{intensity}_{\text{decode}} = \frac{2N}{2N} = 1\ \text{FLOPs/byte}$$

而第 10 讲给出 H100 的"加速器强度"约 $295$ FLOPs/byte——要计算受限，算术强度必须超过这个数。decode 的强度只有 1，差了两个数量级，因此它被内存带宽完全钉死。单步 decode 的时间下限是

$$t_{\text{decode}} \ge \frac{2N}{B_m}$$

其中 $B_m$ 是 GPU 的 HBM 带宽（H100 约 3.35 TB/s）。代入一个 70B 参数模型（bf16 权重约 140 GB），单步 decode 下限约 42 ms——**无论你的 kernel 写得有多快，都至少要把 140 GB 权重搬一遍**。

相比之下，prefill 一次处理 $S$ 个 token，FLOPs 放大到约 $2N \cdot S$，而权重仍然只读一遍（$2N$ 字节），算术强度约为 $S$：

$$\text{intensity}_{\text{prefill}} \approx S$$

只要 prompt 足够长（比如 $S = 1024$），prefill 就远超 295 这个阈值，变成**计算受限**，可以把 GPU 的算力用满。

### 时间结构：一次 vs 很多次

两者在时间结构上也很不同：

- **prefill 单次耗时更长**（一次性处理整个 prompt），但只跑一次；
- **decode 单步短，但步数多**——每个生成的 token 都要跑一步。

所以对一个"输入 $S$ 个 token、生成 $T$ 个 token"的请求，prefill 跑 1 次、decode 跑 $T$ 次。这就是为什么很多系统把这两段计算**拆到不同的 worker 上**：它们需要不同的软硬件调优。

## 连续批处理：多请求并发

真实的推理系统同时服务大量请求，于是出现了**连续批处理**（continuous batching）这一关键技术。Dan 用一张图来讲解（读图的方式是：**时间向下流动**，往下走会有新请求不断进来）：

1. 第一步（step 1），有一个**很长的请求**——比如某个用户在请模型分析一份长文档，引擎正在源源不断地生成 token；
2. 这时**另一个请求进来了**，它也开始占用资源。这里说的"资源"有两类：一是**计算资源**（要同时跑多个请求的前向），二是**内存资源**（KV cache 会被填满）；
3. 于是你会看到多个请求**同时**在引擎里运行；
4. 过了一些步，那个短请求完成了、被移出系统，又有新请求进来跑几步；
5. 接着可能又来一个**很长的请求**（图里那个橙色的）——但也许 GPU 内存不够了（KV cache 都放在 GPU 上，已经满了），于是它开始**排队**（queueing）等待；
6. 等那个长请求完成后，才能启动新的请求。

这就是连续批处理的核心思想（第 10 讲详细讲过 Orca 的迭代级调度）：**请求完成就移出、新请求随时加入，GPU 上同时生活着处于不同生成阶段的许多请求**。这里"批处理"不再是静态的、同一时间进同一时间出的 batch，而是动态流动的。Dan 提醒：看到这里你已经能体会到，当许多不同的请求同时活在一个系统里，复杂度就开始显现了。

### 批处理的延迟-吞吐权衡

顺带一提，为什么大家愿意冒并发调度这么复杂也要批处理？因为**批处理是提高 GPU 利用率、从而提升吞吐（throughput）的主要手段**：把多个请求的矩阵运算拼在一起，才可能用满计算单元（尤其 prefill）。代价是**单请求的延迟会被拉高**——这正是第 10 讲反复出现的"延迟与吞吐的张力"。连续批处理相比静态批处理的优势，正是它让这种张力变得柔和：短请求不用等长请求所在的整个 batch 结束，随时可以离开。

## KV cache 与前缀共享

连续批处理里反复提到的"内存资源"，很大程度上就是 **KV cache**。为什么需要它？想想这两个场景：

- 很多用户都会对模型说"嗨 ChatGPT""嗨 Claude"——**理论上，你不必为每个用户都重新计算一遍这段激活**；
- 用户传入一整本书、对书提问，你对这本书做了一次 prefill；下一次对话轮次里又追加了问题——**你同样不想把整本书重新 prefill 一遍**。

实现这种复用的机制就是 **KV cache 配合前缀共享（prefix sharing）**：当一组新的 token 到来时，用一个非常传统的数据结构（比如一棵**前缀树（trie）**）去查"这些 token 我之前见过哪些、哪些是新的"，然后对见过的部分**直接查表得到激活**，而不必重新计算。

KV cache 的大小对每个序列可以精确写出：对序列长度 $S$、层数 $L$、每层 KV 头数 $K$、头维度 $H$，K 和 V 各存一份、bf16 每个数 2 字节：

$$\text{KV cache size} = 2 \times L \times K \times H \times S \times 2\ \text{bytes} = S \cdot KH \cdot L \cdot 4\ \text{bytes}$$

（第 10 讲用 Llama 2 13B 算过：约 839 MB/序列。）可见 KV cache 是推理显存的大头——它既是你想尽量复用的宝贝，也是限制"同时能服务多少会话"的瓶颈。

## 小结

这一节的核心是两段计算的分析：**prefill 计算受限**（算术强度 $\approx S$，一次跑完整个 prompt）、**decode 访存受限**（算术强度 $\approx 1$，每步重读全部权重）；以及它们在生产系统中的调度方式——**连续批处理**让请求动态进出、短请求不被长请求拖住；而 **KV cache 与前缀共享**让"见过的计算"可以复用。下一节我们看模型的切分（并行）与 KV cache 的更深层管理。

# 激活显存、序列并行与专家并行

到现在为止，我们讨论的几乎全是**参数显存**。但显存是**动态**的：除了静态的参数位，还有**激活（activations）**！而且它们可能非常大。这一节先把激活显存的账算清楚，再介绍两个解决它的并行手段——序列并行与专家并行。

## 每层激活显存：存一切时的账

张量并行与流水线并行都能线性减少参数显存，但**激活怎么办**？这有专门的分析（Korthikanti et al. 2022，Megatron-LM 团队的那篇著名论文）。存储所有激活时，每个 transformer 层的激活显存为

$$\text{每层激活} = 34 b s h + 5 \frac{a s}{h}$$

其中 $b$ 是 batch size、$s$ 是序列长度、$h$ 是隐藏维、$a$ 是注意力头数。两个组成部分：

- **$34bsh$**：来自各线性层与矩阵乘法的激活——注意力的 QKV 投影输入/输出、QK 转置、V 投影、注意力输出投影的输入/输出（8 个 $2bsh$ 的项），MLP 的输入/中间/输出（$8bsh$），两个 LayerNorm（$4bsh$），再加上若干 dropout 项；
- **$5\frac{as}{h}$**：来自**注意力中的二次项**——softmax 概率矩阵与 dropout mask 是 $b \times a \times s \times s$ 的，除以 $h$ 只是为了统一单位（把这部分"换算成"几个 $bsh$）。和 flash attention 的思路一样，**这一项可以通过重计算（recomputation）直接扔掉**。

所以"存一切"是 $34bsh + 5as/h$，用重计算后回到 $34bsh$。

## 张量并行下的激活：剩下的 10 项

张量并行把注意力和 MLP 里的**矩阵乘法**切开了，于是矩阵乘相关的激活（$24bsh$ 里的大部分）随 TP 缩放。但还剩下一部分**不随 TP 缩放**的项：

- 两个 LayerNorm：$4sbh$；
- 两个 Dropout：$2sbh$；
- 注意力与 MLP 的**输入**：$4sbh$。

合计 **$10sbh$**。这些项是"逐序列（pointwise over the sequence）"的操作，随模型规模增长却不受张量并行影响——所以单靠 TP，激活显存并不能线性缩放。

## 序列并行：沿序列轴切

观察到上面那 $10sbh$ 项**全部是沿序列维的逐点操作**，于是自然有个主意：**把 LayerNorm、Dropout 等层沿序列轴切开**。这就叫**序列并行（sequence parallel，SP）**。在张量并行的框架里：

- **前向**：$g$ 变成 all-gather（把序列分片拼回完整序列再做逐点操作），$\bar{g}$ 变成 reduce-scatter（做完后把结果散回各卡）；
- **反向**：两者互换。

![](/lectures/08/slide-48.png)

把张量并行与序列并行组合起来，**激活显存就能真正随机器数量线性缩放**——矩阵乘的激活被 TP 切、逐点操作的激活被 SP 切，两边都摊下去了。

## 专家并行：切专家而不是切矩阵

MoE（Mixture of Experts）模型里还有第三种"切"法：**专家并行（expert parallel，EP）**。它不再去切矩阵乘法，而是**把专家切开放到不同 GPU 上，然后把 token 路由（route）到它们所在的设备**——前向里只有稀疏的 token 激活跨设备流动，而非整块矩阵。

为什么用 EP 而不用 TP？

- 对 MLP 来说，**EP 的行为和 TP 很接近**——同样需要高带宽、同样能减少激活显存；
- 但对 MoE 来说，**切分矩阵乘法会降低效率**——因为 MoE 的矩阵是稀疏使用的（每个 token 只走少数专家）。相比之下，**路由稀疏的 token 激活**要自然得多：token 恰好路由到它们需要的设备，还能省掉一部分开销。既然模型本来就是 MoE，**不如就让专家数正好铺满所有设备**。

> **课堂问答：MoE 里还能用流水线和 FSDP 吗？**
>
> （同学：如果把流水线和 FSDP 用到 MoE 上，还是严格适用的吗？）
>
> **Tatsu**：适用，完全适用。要说标准建议的话，专家并行有点像张量并行——你希望它保持在 8 路左右、走快速的连接（现在人们不那么严格遵循了）。但即使如此，FSDP（以及一般意义上的数据并行）、流水线、张量在所有前沿模型里都仍然被广泛使用。

### EP 的组合复杂度：与 DP、TP 的纠缠

EP 虽然好，但很难和其他策略干净地组合：

- **DP 与 EP 通常共享副本**：朴素的做法（很多老库就是这样）是让 DP 的副本和 EP 的分片**对齐**——比如数据并行度是 8，就把 8 个专家 shard 在这 8 个副本上，数据也在这 8 份上切分路由。这很自然（因为本来就要路由 token），但它给 EP 的并行度设了上限：**EP ≤ DP**，而且还会**约束 DP 与 TP 的相互作用**，可能降低利用率。

### 复杂度：解耦注意力与专家的并行

更系统性的麻烦来自一个事实：**MoE 只改 MLP，完全不动注意力**（少数例外）。于是专家并行只切了 MLP，注意力却没被切。这造成注意力和 MLP 对并行的需求互相冲突：

- **注意力需要高 TP**（不能用 EP，只能靠 TP 切）；
- **MLP 最好用低 TP**（宁可 EP 也不要 TP）。

如果同时要"高 TP 切注意力"和"高 EP 切 MLP"，矩阵会被切成极小的碎片，利用率很差。近年来的系统方案（比如 Megatron）把这个矛盾**解耦**：把并行配置分成两组——注意力侧的 **TP / CP / DP** 与 MLP 侧的 **ETP（专家张量并行）/ EP / EDP（专家数据并行）**——这样注意力层用一种张量并行、MoE 层用另一种，并行配置可以完全独立，得到更复杂但更有效的组合。

### EP 的实现为什么难：DeepSeek 的 DPP 与 Nvidia 的 Hybrid EP

EP 听起来很美好，但实现起来非常非常难——自 FSDP 之后讲的东西（TP、PP、EP），在系统工程上都不好做。这里提两个库，不是为了讲内部细节，而是让你感受一下水有多深：

- **DeepSeek 的 DPP（Dual Path Parallelism / DeepSeek Parallelism）**：DeepSeek-V3 时代的库，专门做专家并行的路由与分发。他们深入 GPU 底层网络原语，把多个操作合并、或者让硬件直接处理某些操作，让 MoE 路由尽可能高效；
- **Nvidia 的 Hybrid EP**：类似思路——在硬件层做非常高效的 EP 分发实现。

为什么这东西难？因为 MoE 的通信模式是**大量的 all-to-all 分发**：每个 MLP 都要把 token 路由到各种不同的地方，而且必须**对延迟极其敏感**——计算在等 token 到达。把分发延迟压下去至关重要。还有一个好玩的八卦：DeepSeek 的人为了把性能榨到极致，甚至翻出了**未文档化的 PTX 指令**（GPU 机器码级别的东西），用这些未公开指令进一步加速他们的网络通信。这就是站在并行与效率前沿所需要的投入。

## 上下文并行 / Ring Attention

这一块想讲的最后一件事是**上下文并行（context parallel，CP）**，也叫 **ring attention**。它把一条**很长的序列的激活切分**到不同加速器上，然后按 TPU 的 mesh 拓扑那样、以**环**（ring）的方式把数据传到需要的设备上。原始的 ring attention 论文就证明了它在 TPU 上效果极好；context parallel 是标准的并行策略，两者都用在**长上下文扩展（long-context extension）阶段**和**模型服务**（serving）中。这一讲不展开，因为它的概念和我们已经讲过的很多东西高度重合。

## 总表：并行策略一览

把第二部分收尾，看一张大表——把各种并行策略放一起比较。前三行是数据并行（DDP/ZeRO-1、FSDP/ZeRO-3），下面是各种模型并行；我主观地把每种方法的**缺点**标成了红色，想传达的核心信息是：

> **不存在一个严格占优的并行策略，一切都是权衡，你要优雅地管理这些权衡才能得到好结果。**

| 方法 | 通信/同步 | 每 rank 参数显存 | 每 rank 激活/KV 显存 | 主要带宽成本 | 扩展全局 batch？ | 易用性 |
|------|------|------|------|------|------|------|
| DDP / ZeRO-1 | 每步梯度 all-reduce | 无参数缩放（ZeRO-1 只切优化器状态） | 无 | 梯度流量 $\sim O(\text{params})$ | 是，随 DP 线性 | 非常容易 |
| FSDP / ZeRO-3 | 梯度 all-reduce（可重叠） | 参数/梯度/优化器状态 $\sim 1/\text{DP}$ | 无 | 参数流量 $\sim O(\text{params})$，比 DDP 高，可重叠 | 是，随 DP 线性 | 中等 |
| 流水线并行 | 层间激活、pipeline bubble | $\sim 1/\text{PP}$ | 取决于 pipeline buffer | 阶段间激活流量 | 否，但需要 micro-batch | 难 |
| 张量并行 | 每块阻塞式激活通信 | $\sim 1/\text{TP}$（TP 切分的权重） | $\sim 1/\text{TP}$（相关 matmul 激活，配合 SP） | 每块激活大小的 collectives | 否 | 难 |
| 序列/上下文并行 | 每层序列分片交换 | 无 | $\sim 1/\text{SP}$ 或 $1/\text{CP}$（序列侧激活/KV） | 激活 / KV 通信 | 否 | 难 |
| 专家并行（MoE） | 每个 MoE 层 token 分发 all-to-all | $\sim 1/\text{EP}$（仅专家权重） | 无 | token 路由 all-to-all | 否，但需要足够 tokens/专家 | 难 |

举个例子读这张表：FSDP 很棒、很优雅，但它**不帮你处理激活显存**，而且它靠**消耗全局 batch size** 来并行化——所以它有天花板。要补这个天花板，可以组合张量并行（削减激活显存、不碰 batch size），但那样就需要快速网络和高带宽；而为了利用慢连接，你可能又想要流水线并行。这些此消彼长的取舍，正是"不存在唯一方案"的原因——大多数大规模架构把一大组合并用起来。

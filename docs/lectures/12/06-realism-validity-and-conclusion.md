# 现实性、有效性与如何思考评估

## 现实性：生态效度（ecological validity）

评估的一个重要方面是**现实性（realism）**，或者说**生态效度（ecological validity）**——**评估在多大程度上捕捉了真实世界的使用方式**？按这个尺度，考试类基准（比如 GPQA）离真实使用最远；Arena 的提示词来自真实的人，但你不免要问：那个"人"的分布真的是正确的分布吗？用户群体和使用场景都对吗？

有一些基准试图在**用例层面（use-case level）**（而不只是单条查询层面）追求生态效度。

**GDPVal** 是 OpenAI 做的基准：他们看了**按美国 GDP 排名前 9 的行业**，找来一批专业人士创建任务——这些从业者平均有**约 14 年的经验**，涵盖护士、礼宾、房产经纪、影视剪辑等职业。

![GDPVal 的职业分布与任务示例](/lectures/12/gdpval.png)

**MedHELM** 是医疗领域的例子。此前，很多医疗基准都基于**标准化考试**——有趣的是，对人类来说也是这样：你考过标准化考试、从医学院毕业，然后……其实还有很长一段路，你不会直接去给病人做手术。所以对语言模型也一样：**不应该让它考过医学考试就直接部署**。MedHELM 的 121 项任务来自 **29 位临床医生**，代表的是"医生们会真正问语言模型的问题"——这和多选题形式的考试题差别很大。

**Clio**（Anthropic）试图触及**真实数据**。如果你问"谁真正掌握着人们用模型做什么的数据"，答案是部署它们的公司。由于隐私原因，你没法直接去看用户数据，但可以**让语言模型去看数据、分析并总结出一般模式**——比如"人们用 Claude 做什么类型的事、是什么类型的人在问"。

![Clio 用语言模型分析出的真实使用模式](/lectures/12/clio-table4.png)

讲者提醒：**现实性与隐私有时候是互相矛盾的**。理想情况下，你当然想直接从真实的查询流里采样——这对评估模型工作得如何、深入理解它的错误模式都极其宝贵——但这马上会撞上隐私问题。

## 有效性：训练测试重叠与污染

另一种有效性是**科学有效性**：我们怎么知道评估在科学上是站得住脚的？这个问题很早就被提出来了，核心就是**训练任务重叠（train-task overlap）**，也就是污染（contamination）。

机器学习 101 就教过：**不要在你的测试集上训练**。在基础模型（foundation model）出现之前，这件事清清楚楚：ImageNet、SQuAD 这些数据集都有明确的训练集和测试集划分，所有人都遵守同一套游戏规则——在训练数据上训练、在测试数据上测试，生活很简单。而现在，模型在互联网上训练、而且远不止于此，你又**不知道训练数据里有什么**——这使评估变得截然不同。

面对这个问题，有四种可以走的路。

### 路径 1：推断模型是否见过测试数据

第一种是**试图推断模型是否真的见过测试数据**。这里有一个来自 Tatsu Hashimoto 团队的巧妙想法——**利用数据点的可交换性（exchangeability）**。

形式化地说，一组数据点 $x_1, \dots, x_n$ 是**可交换**的，如果对任意排列 $\pi$，它们的联合分布满足

$$P(x_1, x_2, \dots, x_n) = P(x_{\pi(1)}, x_{\pi(2)}, \dots, x_{\pi(n)})$$

**一个良构基准里的题目顺序应当是可交换的**——顺序本身不携带任何信息。而如果模型训练过这个基准，情况就不一样了：模型给"按基准原始顺序排列的实例序列"分配的概率，可能系统性地高于给随机打乱顺序的序列分配的概率；或者说，模型的逐题表现会依赖题目在基准里的位置。

![可交换性检验：若模型"偏好"某种特定顺序，则可能见过该基准](/lectures/12/contamination-exchangeability.png)

于是检验就是：把基准实例按**原始顺序**和按**随机打乱的顺序**分别喂给模型，比较模型给两套序列分配的平均对数概率（或逐题的表现）。**如果顺序根本不该有影响（可交换性），而模型却表现出对某个特定顺序的偏好，那就说明它很可能在训练时见过这份基准。**

那篇论文还给出了一个具体的、可操作的检测方法——**Min-K% Prob**：对一个候选文档，取出模型分配给每个 token 的概率，把**概率最低的那 K% 个 token 的对数概率取平均**。如果这个值很高，说明那些"模型本应觉得意外"的 token 却意外地可预测——这强烈暗示文档在训练数据里：

```python
def min_k_prob(token_log_probs: list[float], k: float = 0.2) -> float:
    """Min-K% Prob：对概率最低的 K% 个 token 的平均对数概率。
    数值越高，越可能是训练数据。"""
    n = len(token_log_probs)
    k_floor = max(int(k * n), 1)
    lowest = sorted(token_log_probs)[:k_floor]
    return sum(lowest) / k_floor
```

### 路径 2：鼓励报告规范

第二种是**鼓励报告规范（reporting norms）**。想想科学界的惯例：人们总是报告**置信区间**——你给出一个估计，别人想知道它有多可靠。这应当成为标准做法。同样地，模型厂商在声称某个 GPQA 分数时，**应该同时提供"我没有在测试集上训练"的论证**，并报告与测试集的真实重叠程度。

### 路径 3：放弃抵抗，用新鲜的评测

第三种更务实：**干脆假设最坏情况**——就当大家都在基准上训练过。而我们这边永远有一张牌：**总是可以定义全新的评测（fresh evals）**。比如 **LiveCodeBench**、**UncheatableEval**：它们不断爬取新的网页、归档的新论文或 GitHub 仓库，构造出**晚于模型数据截止日期**的评估——看起来相当稳健。但要小心：**时间戳也不总是可靠的**——我可能刚把一个 GitHub 仓库传上去，可它其实是照抄某个老仓库的，那你怎么知道它真的是"新鲜"的呢？

### 路径 4：私有评测

第四种是**私有评测（private evaluations）**。模型厂商就是这么做的：Google、OpenAI 都有自己的**内部代码库**，假设它们不在互联网上、模型显然也不会拿它们训练，所以可以放心用来评估——通常相当可靠。如果你不是大公司，也可以用**个人的私有写作**：讲者举例说，自己读研时有一堆被拒稿、从未上网的论文，那些就能拿来用。这类评估对**困惑度**尤其友好——测困惑度只需要一个好数据集，然后算对数似然就够了。

## 数据集质量：好基准也需要持续审计

讲者还提醒了另一类问题：**数据集质量**。还记得前面那个 SWE-bench Verified 吗？之所以有 Verified 版本，是因为**原始 SWE-bench 有一批任务质量不过关**——单元测试不够严谨等等——于是被修复了。很多基准都经历过这个过程：GSM8K、MMLU 都被人仔细审计过，结果发现"等等，这道题有问题"——比如题目文字里根本没给曲线图，却要你根据曲线作答；或者"这个婴儿有没有穿袜子？"——根本无法判断。

还有一篇论文指出了**智能体基准（agentic benchmark）**的许多问题——它们甚至更难审计，因为你不能只看题目和选项，而要看整个环境。编码任务有测试用例是很棒，但**测试用例可能不完备**：你能通过所有测试用例，却仍然没有一个真正可用的解决方案。更夸张的案例是：**一个 agent 只要输出空响应，就能拿到 38%**——这些基准里的"平凡解"（triviality）必须非常小心地避免。

对此，讲者推荐了一个工具 **Docent**：它**用语言模型去检查 agent 的执行轨迹（traces）**，从而发现基准里的问题。这是对我们这种"极度量化"的基准化方法的一种**质化（qualitative）补充**。讲者的建议是：**无论你是开发一个基准，还是在一个基准上跑模型，永远要亲眼看输出、去审计它**，确保你测的确实是你以为自己测的东西。

## 怎么思考评估

### 评估的目的是什么？

聊到这儿，话题稍微哲学一点：**评估到底是为了什么？** 讲者已经讲了很多种评估，而真正的答案是——**不存在一个"统御一切的评估"**。当你思考评估时，你必须非常清楚它的**目的**，而这恰恰常常没有被明确说出来。例如：

1. **用户或公司要做购买决策**：针对某个具体用例（比如客服聊天机器人），在模型 A 和 B 之间选一个；
2. **研究者想度量原始能力**：你有个关于"智能"的直觉，想把它量化；
3. **想理解模型的益处与危害**：出于商业或政策的原因；
4. **模型开发者想获得反馈**：用来改进自己的模型。

这四个目的会导向**不同的基准、或不同评估策略的组合**。

### 我们在评估什么：方法还是模型？

另一个值得明确的问题：**我们到底在评估什么？** 在基础模型出现之前，研究者评估的是**方法（methods）**——因为有标准化的训练/测试划分，唯一变化的就是方法本身。而今天，我们大多在评估**模型和系统（models/systems）**——一切皆可。

当然有例外：**nanoGPT speedrun** 就是一个刻意用来评估**算法**的设定——固定数据，看多久能训练到某个验证损失：

![nanoGPT speedrun：固定数据、比谁更快达到目标验证损失](/lectures/12/karpathy-nanogpt-speedrun.png)

评估方法能鼓励研究者的算法创新；评估模型/系统则对下游用户更有用。但无论哪种，**你都需要定义清楚"游戏规则"**。

## 全讲总结

没有唯一真正的评估——**选择取决于你想衡量什么**。这一讲从困惑度、考试类、聊天类、智能体、纯推理、安全这几类基准一路看下来，它们各自在**难度（difficulty）、现实性（realism）、有效性（validity）**几个维度上差异很大，而且往往存在**权衡**：很难同时做到"真实 + 困难 + 生态效度高 + 零污染"。所以你常常必须在某个维度上让步，而**具体让步哪一项，取决于你的目标**。想清楚目的、声明规则、再动手评估——这就是本讲想传达的。

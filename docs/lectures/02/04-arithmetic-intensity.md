# 算术强度与 roofline

## 为什么 MFU 只有 0.5：不只是 matmul

上一节末尾留下一个问题：**为什么 MFU 到不了 1，通常只有 0.5？** 要回答它，得先明白：计算不是“做一堆 matmul，然后看它们各自花多久”这么简单。

Percy 给出了一个（卡通版的）硬件模型：

![](/lectures/02/compute-memory.png)

- 我们有**高带宽内存（HBM）**，tensor 就存在这里；
- 还有**计算核 / 加速器芯片（accelerator）**，真正的计算在这里发生；
- 计算的流程是：把输入（矩阵）从内存**搬到**加速器 → 做计算 → 把结果**搬回**内存。

所以“一次计算要花多久”，取决于**两件事**：

1. **加速器速度**：FLOP/s（上一节讲过的 1979e12/2）；
2. **内存带宽**：bytes/s。H100 的规格是 **3.35 TB/s**（3.35e12 bytes/s）。

### 为什么内存大小影响速度

我们前面算内存，最显然的理由是“模型太大装不进内存就麻烦了”。但另一个原因：内存是要**搬运**的，搬运要花时间——所以**东西越大，跑得越慢**。这正是“省内存 = 省时间”那句不那么显然的话的来源。

## 通信时间与计算时间

对任意一个操作，我们可以数两笔账：

$$\text{通信时间} = \frac{\text{搬运的字节数}}{\text{内存带宽}},\qquad \text{计算时间} = \frac{\text{FLOPs}}{\text{FLOP/s}}$$

这里有一个重要的假设：**通信与计算可以完美重叠（perfectly overlap）**。也就是我们不干坐在那里等数据；数据一到位就开始算，同时后面的数据继续搬。这个假设下：

$$\text{总时间} = \max(\text{通信时间},\ \text{计算时间})$$

实践中不可能完美重叠，总有些开销，但这个模型足够用了。于是瓶颈的定义就出来了：

- **memory-bound（内存受限）**：通信时间 > 计算时间——大部分时间在**等数据到位**；
- **compute-bound（计算受限）**：计算时间 > 通信时间——瓶颈是**计算本身**。

## 例 1：ReLU

ReLU 就是 $\max(x, 0)$，对整个向量逐元素做。设 $N = 1024 \times 1024$ 维的 bf16 向量：

- **字节数**：读 x（$2N$，bf16 每元素 2 字节）+ 写 y($2N$)= **4N** 字节；
- **FLOPs**：N 次比较 = **N**；
- 通信时间 $\approx 4N / 3.35\text{e12} \approx 10^{-6}$ 秒；计算时间 $\approx N/989\text{e12} \approx 10^{-9}$ 秒；
- 总时间 $\approx 10^{-6}$ 秒 → **memory-bound**。

显而易见：计算量比搬运量小太多了。

## 加速器强度与算法强度

我们可以把上面的判断换成一种更优雅的语言——**算术强度（arithmetic intensity）**。

- **加速器算术强度（accelerator intensity）**：加速器每搬运 1 字节能做多少**有用工作**。对任意加速器，从规格表就能算：

$$\text{加速器强度} = \frac{\text{FLOP/s}}{\text{bytes/s}}$$

对 H100：$(1979\text{e12}/2) / 3.35\text{e12} \approx 295$。也就是说每搬一个字节，可以做约 295 次浮点运算——记住“约 300”这个直觉数字。

- **算法算术强度（arithmetic intensity）**：这个具体 workload 每字节实际做了多少工作：

$$\text{算法强度} = \frac{\text{FLOPs}}{\text{bytes}}$$

ReLU 是 $N/4N = 0.25$——非常小。如果别人告诉你你的算术强度是 0.25，你应该说：“这真的很糟。”

### 瓶颈判断的等价说法

两种说法完全等价（就是两个分数比大小，代数上互相一乘一除就得到）：

- **memory-bound**：算法强度 < 加速器强度；
- **compute-bound**：算法强度 > 加速器强度。

**学生问**：典型的算术强度大概是多少？

**Percy 答**：我们马上就会讲到。

## 例 2：GELU

GELU 是另一个激活函数，$\text{GELU}(x) = 0.5x\big(1+\tanh(\sqrt{2/\pi}(x+0.044715x^3))\big)$——没有零的、更平滑的激活。

- **字节数**：还是 4N（读 x 2N + 写 y 2N）；
- **FLOPs**：约 **20N**（每个 GELU 约 20 次浮点运算，tanh 可以用多项式近似）；
- 强度 $= 20N/4N = 5$，依然**远小于 295** → 依然 **memory-bound**。

结论很有意思：**GELU 比 ReLU 做的计算多得多，但在“结构”上两者都是 memory-bound**，所以单独跑 GELU 并不比 ReLU 贵——瓶颈根本不在这里。别被 GELU 复杂的公式骗了。

## 例 3：点积

两个 N 维向量做点积：

- 字节：读 x($2N$)+ 读 w($2N$)+ 写 y（标量，$2$）= $4N+2$；
- FLOPs：$2N-1$（N 次乘法 + N-1 次加法）；
- 强度 $\approx 0.5$ → **memory-bound**。

## 例 4：矩阵向量乘

$x$ 是 N 维向量，$W$ 是 $N\times N$ 矩阵，计算 $y = xW$：

- 字节：读 x($2N$)+ 读 W($2N^2$)+ 写 y（$2N$）；
- FLOPs：N 个点积 $= N(2N-1)$；
- 强度 $\approx O(1)$，只比点积高一点点 → **memory-bound**。

Percy 在这里问大家觉得矩阵向量乘是 compute-bound 还是 memory-bound，然后揭晓答案。更重要的是这个**预告**：矩阵向量乘基本上就是 **transformer 推理（decode）阶段**的情形——推理时一次生成一个 token，只有“一个向量”与矩阵做点积，所以**推理是 memory-bound**。而训练时是整个序列一起处理，所以训练能饱和 GPU。

## 例 5：矩阵乘法

两个 $N\times N$ 矩阵相乘：

- 字节：读两个矩阵 $4N^2$ + 写结果 $2N^2$；
- FLOPs：$N^2$ 个点积 $\approx 2N^3$；
- 强度 $\approx N/3$。$N=1000$ 时约 **340** → **compute-bound**！

直觉：你**搬运**的是 $N^2$ 量级的东西，却**计算**了 $N^3$ 量级的操作，比值随 $N$ 线性增长。所以**矩阵越大越好**。

这就是为什么大家总说“要大批量、大矩阵”：如果你的算术强度低于加速器强度，**把矩阵变小并不会加快速度**（反正都是 memory-bound，都一样慢）；只有强度超过加速器强度，才真正**饱和 GPU**。

只要矩阵够大，就是 compute-bound。好消息是：**transformer 本质上就是“大矩阵乘法 + 中间点缀一些别的操作”**，而且这是**设计出来的**——transformer 被设计成有很高的算术强度。训练时整序列一起算；推理时回到矩阵向量乘，也就是 memory-bound。

**注意**：算术强度依赖**精度**——我们默认按 fp16/bf16 算；换 fp32 数值会变。

## roofline 图

把算术强度与性能的关系画出来，就是 **roofline 图**：

![](/lectures/02/roofline.png)

- **X 轴**：算术强度；
- **Y 轴**：实现的 FLOP/s；
- **每条分段线性曲线**对应一种硬件；
- **拐点（kink）**就是**加速器强度**——从 memory-bound 到 compute-bound 的转变点：左侧低强度区，性能被内存带宽限制（曲线斜着上升），右侧饱和到计算峰值（平台）。

roofline 还能和 MFU 直接挂钩：

$$\text{MFU} = \min\!\left(1,\ \frac{\text{算法强度}}{\text{加速器强度}}\right)$$

## 学生互动

**学生问**：一般来说，这些大模型的大部分计算都是 memory-bound，但加速器的 MFU 却只有 50%（如果能到 70、80 就是很好了）——意思是加速器的能力比内存大太多。为什么会这样？这些大模型为什么是这样？

**Percy 答**：它们只是**在闲置，等内存**（idling or waiting for memory）。这正解释了上一节“为什么 MFU 只有 50%”：大部分时间，计算核在干等数据。

**学生问**：能不能设计出特性更好的加速器？

**Percy 答**：也许可以——等我们讲到 GPU、更深入了解硬件时再展开。

**学生问**：有没有亚三次方（sub-cubic）的矩阵乘法算法？

**Percy 答**：现实中矩阵乘法的优化，更多是关于**如何与系统协同设计（co-design）**，而不是渐进复杂度算法。

## 小结

- 计算的卡通模型：HBM 与计算核分离，数据要搬过去、算完搬回来；
- 通信时间 = 字节/带宽，计算时间 = FLOPs/算力，完美重叠下总时间 = max（两者）；
- 加速器强度 = FLOP/s ÷ bytes/s ≈ 295(H100)；算法强度 = FLOPs/字节；
- ReLU（0.25）、GELU（5）、点积（0.5）、矩阵向量乘（O(1)）全部 memory-bound；
- 矩阵乘法强度 ≈ N/3，compute-bound——这就是要大批量、大矩阵的原因；
- roofline：X 轴算术强度、Y 轴 FLOP/s，拐点是加速器强度；MFU = min（1， 算法强度/加速器强度）；
- 大模型 MFU 只有 0.5 的原因：大部分时间在等内存。

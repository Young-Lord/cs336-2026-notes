# MoE 基础与路由：什么是 MoE、为什么流行

讲完注意力替代方案，现在进入本讲第二个大主题：**混合专家模型（Mixture of Experts,MoE）**。Tatsu 说，MoE 在概念上**并没有改变游戏规则**——一种看待它的方式就是：**MoE 只是一个更高效的 MLP**。有人给了你一个更高效的 MLP，那基本就是 MoE。但理解它仍然很重要，原因有两个：

1. **人人都在做 MoE、人人都在发布 MoE**。如果你想成为真正理解语言模型及其工作原理的人，就该知道它是什么；
2. MoE 里有一些**真正的"机械"组件**。如果你看看 MoE 是怎么搭建的、用了哪些原语（primitives），你会很快发现 **MoE 风格的原语出现在很多其他地方**——然后你会意识到，"原来我可以用神经网络做更多有趣的事"。

## 什么是 MoE：一个更高效的 MLP

MoE 在某种意义上非常简单——**它就是对你 MLP 的替换**。看左侧：一个标准 transformer 里，attention 之后是归一化，然后是前馈网络（FFN）——这是大量稠密信息处理发生的地方。现在做个替换：把那个**大 FFN 切成多个较小的 FFN**（这里示意切成 4 个）。更进一步，假设这些 FFN **和原来一样大**（不切小)，然后——"靠某种魔法"——有一个系统告诉你在**每个输入**下该选哪个 FFN。

结果是什么？你拥有了 **4 倍的参数**（至少对 FFN 而言)，但在任何一次前向/反向传播里，**只付一个 FFN 的成本**。这就是 MoE 的心智模型：

> **你想在不影响 FLOPs 的前提下，增加参数。**

如果你读原始论文，会发现最初的动机是**参数中心**（parameter-centric）的："假设你就是想要更多参数，因为你相信更多参数是好的。"那么如何在多要参数的同时不为其付算力？你需要的就是右边这种东西。

## 为什么 MoE 这么流行？

为什么 Hugging Face 上**超过一定规模的模型几乎全是 MoE**？因为有一个反复出现的经验现象：**在总计算量不变的情况下，只要增加稀疏参数（sparse parameters）的数量，模型通常就会变得更好**。这是"更多参数就是好"这一观点的有力证据——哪怕同一时刻只有一部分参数是激活的。Tatsu 在本讲会频繁引用 Google 的原始论文。以下是四个理由：

### 理由一：同样的 FLOPs，更多参数就是更好

这是 Fedus 等人 2022 年（Switch Transformer）的图：**激活参数不变，专家数增加，测试 loss 一路下降**。只要你在乎前向成本，这几乎是免费的。右侧那张图则是另一个角度：**横轴是训练算力，在同样的训练算力下，专家越多、性能越好**。也就是说，无论训练还是推理，**MoE 都是免费的好处**。

### 理由二：MoE 训练得更快

同样的现象被多次复现。左侧还是 Fedus 的图；而 AI2 的 **OlMoE** 论文——一个开源的 MoE 分析与训练研究——也看到了同样的事情：在训练 loss、验证 loss、下游基准上，MoE 相比稠密对应物在**训练时间**上都有显著优势——**大约快 2 倍**。

### 理由三：与稠密模型相比非常有竞争力

看发布出来的 MoE 模型，它们按**激活参数**（active parameters）算——这才是推理 FLOPs 真正关心的——通常远强于稠密模型。**DeepSeek V2** 以及更早的 DeepSeek MoE 出现时，是一个很大的转变：用少得多的激活参数，在 MMLU 上做到**与其他人持平甚至更好**。这就是 MoE 实实在在的好消息。

### 理由四：多了一个并行化的轴

还有最后一点：MoE 给了你**另一个并行化（parallelization）的轴**。并行化在 LLM 里极其重要——模型太大，训练和推理都放不进单块设备，你需要很多种"切分模型"的方式。MoE 额外的好处是：**每个 FFN 里的专家天然是一个个"块"**，可以放在不同设备上，再把激活路由到对应设备。这就是后面系统部分会讲的**专家并行（expert parallelism）**——它给你一个可以额外优化的系统自由度。

## 工业现状：西部与中国

**西方**：开源侧有几个很强的 MoE 发布，大模型方面有 **Llama 4**、OpenAI 的 **GPT-OSS**。不过 Tatsu 感叹，西方的开源发布大体上已经"停滞"了，所以现在新发布的没那么多了，但至少这两者是各自档位里的顶级模型。

**中国**:MoE 的研究与训练，大量的动作发生在中国。**Qwen、DeepSeek**，还有 **MiniCPM** 等，做了最早一批训练和推广 MoE 的工作，并且持续产出很棒的结果。看早期的 **Qwen 1.5 MoE**：它只有 27 亿激活参数，却比当时许多 70 亿参数的模型做得更好。DeepSeek 与 Qwen 的这些早期"证明性工作"，很大程度上说服了整个开源社区"MoE 就是该走的路"。

（幻灯片里还提到：DeepSeek 现在是靠 DeepSeek R1 等出名的，但 Tatsu 真正欣赏 DeepSeek 的是他们**做了很多年扎实的架构与 LLM 科学工作**——本讲最初的版本甚至就是"完整过一遍 DeepSeek 论文"的一讲。DeepSeek 是最早论证"为什么 MoE 好"的团队之一，他们的早期论文里有大量精心设计的消融——稠密层 vs MoE、hash 路由 vs switch 路由，等等。如果你想研究架构设计，读他们的早期论文能学到很多。DeepSeek V3、V3.2、GLM 这些后续模型也都沿用了这套强大的 MoE 设计——**未来至少一两年，大模型大概率就是 MoE 的天下**。)

### 问答：专家并行不是有通信瓶颈吗？

（同学：专家之间要互相通信，那是不是有通信瓶颈？)

**Tatsu**：是的，某种意义上你付的是"把激活搬过去"的通信成本。我后面会展示一个降低通信的技巧（指 Nemotron 3 的 down-projection），但总体上你是在做权衡：**你得到更多总 FLOPs、更少内存占用，代价是付通信**。所以到底是赚是亏，**高度依赖你的网络拓扑等系统条件**。

## 为什么 MoE 没更早流行？

在很多意义上，MoE 流行得挺慢：2022 年 Google 就在研究、努力推动 MoE，但直到 2024 年之后 MoE 才真正起飞。为什么？如果你在做各种 LLM 研究，多半还是在用稠密模型——MoE 这么好，为什么不用？

因为 **MoE 有一大堆复杂性**:

- **基础设施非常复杂**：前面问答里提到的并行化问题只是其一——要让专家的利用率高效，并不容易；
- **参数很多、放不进单设备**：训练时 MoE 还容易"炸掉"——后面会看到原因；
- **训练目标相当启发式（heuristic），而且有时不稳定**（Zoph 等人 2022 年专门有论文研究这个）。

现在有好的经验法则了，但它依然不是一个"容易操作的对象"。

## MoE 的一般形态

典型的做法是：**用 MoE 层替换 MLP**。不常见的是对**注意力头**做 MoE(ModuleFormer、JetMoE 等少数论文)，但 Tatsu 见过的结果是：**注意力头方向的 MoE 没那么容易驯服**，远不如替换 FFN/MLP 好用。所以大模型基本都只做左边那种：**只替换 MLP 层**。

## MoE 的三个可变轴

设计一个 MoE 时，有三个维度的变量：

1. **路由函数（routing function）**:router 怎么把 token 送到专家——这是最核心的；
2. **专家大小（expert sizes）**：给定预算，你是要"更多、更小的专家"还是"更少、更大的专家";
3. **训练目标（training objectives）**：训练才是真正困难的地方——一旦你意识到 MoE 是怎么工作的，就会发现"训练一个把 token 路由到不同地方的东西"可不容易。

## 路由：三种范式

在所有情况下，我们都不想激活所有专家——**永远只激活一个子集**，所以总要做某种 Top-K。但"由谁来选"有三种范式：

- **token 选择专家（token chooses expert）**：每个 token 挑自己最喜欢的专家；
- **专家选择 token(expert chooses token)**：每个专家挑一批它要处理的 token;
- **全局路由（global routing via optimization）**：一个复杂的全局路由器决定"这个 token 去这个专家、那个 token 去那个专家"，试图全局优化分配。

**几乎所有的 MoE 都在做 token 选择的 Top-K 路由**。OlMoE 论文里对比过 token choice 与 expert choice:token choice 得到**更低的验证 loss、更高的下游基准分**。expert choice 也有成功案例（也能正常训练），但 **token choice 更容易调通**，成了今天所有模型的默认选择。（Tatsu 顺带吐槽：Llama 4 的某个模型可能用了 expert choice——但他狡辩说那是未发布的 Llama 4 之一，不算是强证据。）

## Top-K 路由详细

现在把 Top-K 路由完整拆开。如果你刚才认真看了 DSA 那部分，会发现**这一步和 DSA 长得非常像**——同样的模式在 H-Net 等许多地方出现，值得记住这个模式。

记 $u_t$ 为第 $t$ 个 token 进入该层时的**残差流输入**,$N$ 为专家总数，$\mathrm{FFN}_i$ 为第 $i$ 个专家（一个普通前馈网络）。MoE 层的输出为：

$$h_t = u_t + \sum_{i=1}^{N} g_i(t)\, \mathrm{FFN}_i(u_t)$$

门控 $g_i(t)$ 只在被选中的专家上非零:

$$g_i(t) = \begin{cases} s_i(t), & i \in \mathrm{TopK}\big(\{s_j(t)\}_{j=1}^{N},\, K\big) \\ 0, & \text{otherwise} \end{cases}$$

而 $s_i(t)$ 是"token $t$ 与专家 $i$ 的亲和度（affinity）"，计算起来几乎就是一次注意力——**对每个专家学一个向量 $e_i$（类似每个专家的"身份向量")**，与输入做内积再 softmax:

$$s_i(t) = \mathrm{softmax}_i\!\left(u_t^\top e_i\right)$$

整个流程是:

1. 拿残差流输入 $u_t$ 与每个专家的向量 $e_i$ 做内积;
2. 过 softmax 归一化成分数 $s_i(t)$;
3. 用 Top-K 只保留分数最高的 $K$ 个专家,其余门控清零;
4. 把被选中专家的输出按门控**加权求和**;
5. 加回残差流 $u_t$,得到输出 $h_t$。

**路由器就是这么轻**——本质上只是一个"输入 × 专家向量"的矩阵乘法。没有任何复杂的语义判断:它不会"知道这是不是一个医学问题",它只是做内积,然后选 Top-K。关于"如何学习这些门控",唯一的答案就是:**门控由内积学习,非常轻量**。

下面是一个最简的 PyTorch 实现(为教学清晰起见,朴素地计算了所有专家;实践中为了省 FLOPs 只会计算被选中的 $K$ 个专家):

```python
import torch
import torch.nn.functional as F

class TopKMoE(torch.nn.Module):
    """一个最简的 Top-K MoE 层(DeepSeek v1/v2 风格路由:softmax 在 Top-K 之前)。"""

    def __init__(self, d_model, n_experts, top_k, d_ff):
        super().__init__()
        self.n_experts = n_experts
        self.top_k = top_k
        # 每个专家就是一个标准的两层 FFN(SiLU 激活,无 bias)
        self.experts = torch.nn.ModuleList([
            torch.nn.Sequential(
                torch.nn.Linear(d_model, d_ff, bias=False),
                torch.nn.SiLU(),
                torch.nn.Linear(d_ff, d_model, bias=False),
            ) for _ in range(n_experts)
        ])
        # 路由器参数:每个专家一个可学习向量 e_i
        self.expert_centroids = torch.nn.Parameter(torch.randn(n_experts, d_model))

    def forward(self, u):
        # u: (batch, d_model),残差流输入
        logits = u @ self.expert_centroids.t()   # token 与各专家的亲和度
        scores = torch.softmax(logits, dim=-1)   # 归一化(softmax 在 Top-K 之前)
        topk_scores, topk_idx = torch.topk(scores, self.top_k, dim=-1)

        gate = torch.zeros_like(scores)          # 门控:只保留被选中的专家
        gate.scatter_(1, topk_idx, topk_scores)

        # 朴素实现:计算所有专家,再按门控加权求和
        expert_outputs = torch.stack(
            [self.experts[i](u) for i in range(self.n_experts)], dim=1
        )                                        # (batch, n_experts, d_model)
        h = (expert_outputs * gate.unsqueeze(-1)).sum(dim=1)
        return u + h                             # 残差连接
```

### softmax 的位置:Top-K 之前还是之后?

在 Top-K 这个框架里有一个著名的"小差别"。**DeepSeek v1/v2 的路由器(以及 Grok、Qwen)把 softmax 放在 Top-K 之前**:先对所有专家归一化,再取 Top-K;而 **Mixtral、DBRX、DeepSeek v3 把 softmax 放在 Top-K 之后**:只对被选中的 $K$ 个专家重新归一化。

两者只差一个归一化常数,而**归一化与否其实没那么重要**——下一层还有 LayerNorm,权重比例可以被任意放大。所以这更多是一个"**美学选择(aesthetic choice)**"。

## 各种 Top-K 的"口味"

不同模型选择的 $K$(每个 token 激活的专家数)与专家总数 $N$ 各有不同:

- **Switch Transformer**:$k=1$,最极端的稀疏;
- **GShard、Grok、Mixtral**:$k=2$;
- **Qwen、DBRX**:$k=4$;
- **DeepSeek**:$k=7$(细粒度专家方案的配套选择)。

## 其他路由方式

Top-K 之外,还有几种值得知道但没怎么流行的路由:

- **Hashing**:一个让 Tatsu 一直觉得有点神秘的事实是,很多论文证明**你根本不需要学习路由器**——把输入 $x$ 哈希一下、送进不同的 FFN 就行,居然也能有收益(虽然不如 Top-K)。它常常作为论文里的**常见 baseline**,但出于种种原因**不会用于部署**;
- **RL 学习路由**:把路由器当成策略(policy)用强化学习来学。如果你有经典学习理论背景,这是"自然"的思考方式——这是个 bandit 问题:从 $N$ 里选 $K$ 个,又观测不到没被选中的那些。它出现在最早的工作里(Bengio 2013),但现在**不常见**——因为 RL 的算法与随机性开销太大,而人们已经找到一套能让简单 Top-K **直接跑起来**的启发式配方,没必要做更复杂的;
- **解线性分配问题(linear assignment)**:全局计算"token 到专家"的两两得分,用线性分配精确求解最优指派。Tatsu 说这是他很喜欢的一个想法——"喜欢合理东西的人会喜欢它"——但它**从未在规模上被采用**,因为求解成本相对于收益太贵了。

## 共享专家与细粒度专家:DeepSeek 的标准化设计

即使在"简单的 Top-K"内部,也有来自 DeepSeek 及其同侪的重要创新。**共享专家(shared experts)** 是一个非常直观的想法:

- 在经典 Top-K 路由里,$N$ 个专家之间互相竞争,每次选 $K$ 个;
- 但有些处理是**所有 token 都要的公共处理**——你也许不希望专家"每次都不一样",而是希望**某些专家永远被应用,另一些专家按条件应用**。

DeepSeek MoE 的做法是:把原有专家设计**切成更小的细粒度块(fine-grained chunks)**,其中**一部分设为共享专家(shared experts)——永远在线,绕过路由器**,总是处理所有输入,输出再加回结果。这个想法的好处是:经典专家设计里,大量权重其实在反复做"公共建模";把这些公共计算**卸载进一个共享专家**,可以让被路由的专家**更专精**。

同时,把专家切得更小、数量更多(保持 FLOPs 不变),就是**细粒度专家(fine-grained experts)**。DeepSeek 用精心设计的消融展示了这两者的收益:

- 对比"0 个共享专家 + 16 个大路由专家"(老 GShard 设计)与"细粒度专家 + 1 个共享专家":**两个干预都带来显著收益**;
- 其中**共享专家**的收益在 **TriviaQA、Natural Questions** 上非常明显——有没有共享专家,差别相当显著。

**更多专家、共享专家,一般都有帮助。** 如果你想看更独立的验证,**OlMoE**(西方那套受控很好的 MoE 研究)结论是:**细粒度(更多小专家)有帮助,但共享专家帮助不大**——它在这一点上和 DeepSeek 存在分歧。尽管有分歧,如今绝大多数近期的 MoE 还是**遵循 DeepSeek 的设计**——就像稠密 transformer 的 LLaMA 设计成为标准一样,**DeepSeek MoE / DeepSeek v3 的"细粒度 + 共享专家"设计成了 MoE 侧的标准**。Qwen 3.5、GLM 这些现代模型都还在用,这是一套经受了大规模考验的设计。

## 预告:训练时也要稀疏

在进入训练之前,Tatsu 先预告了一个关键事实:**训练时,MoE 也是稀疏的**。如果训练时激活所有专家,那就太容易了——你能看到"哪个专家对我的输入好",从而学会路由。**难点恰恰在于:训练时每步只有 1 个或 $K$ 个专家被激活,你根本不知道其他专家会表现如何**——只知道自己激活的那几个。尽管如此,你还是得学会路由。这带有一点 **RL / bandit 的味道**。不过我们不会用 RL 或 bandit 去解它,而是用**启发式 + 深度学习魔法**。这就是下一节的内容。

## 课堂问答:关于 MoE 的基本问题

### 问答:切换专家的粒度是什么?

(同学:专家的"切换粒度"是什么——多久切一次?)

**Tatsu**:**token 级别**。每个 token 都被分配专家。而且为了给你一个正确的心智模型:**路由器超级朴素**——它就是"输入和某个权重的一次矩阵乘法",没有任何复杂判断。它不会"知道这是不是医学问题";它更像是:"哦,这个 token 看起来像是日文,路由到专家 7 吧。"

### 问答:MoE 并行化有上限吗?

(同学:训练或推理时,MoE 模型的并行化有上限吗?)

**Tatsu**:**有**,因为当你把模型切到越来越多的设备上,**通信成本会爆炸**。你们在作业里会亲自处理这个问题——我们会让你们根据给定的**网络拓扑**设计合理的切分方案,或者反过来,给定切分方案去推导所需的拓扑。总之上限确实存在。

### 问答:共享专家的并行化怎么做?

(同学:如果有共享专家,并行化怎么处理?)

**Tatsu**:共享专家的情况下,你**拿不到并行的好处**——每个激活都必须流过它。不过你可以**复制共享专家**(用内存换通信):把共享专家复制到多个设备上,避免它的激活也要跨设备传输。

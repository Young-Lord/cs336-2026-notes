# 数据变换：从 HTML 与 PDF 到文本

## 本讲导览

今天是"数据"的第二讲。上一讲我们讲了数据不从天而降——网络由活服务组成，服务上的数据要么被转储、要么被爬取，之后还有一步处理，中间还夹着服务条款与版权（要么获得许可、要么主张合理使用）这类社会与法律问题。今天我们把目光移到**数据流水线的后半段**：拿到原始数据之后，还要依次经过**变换（transformation）、过滤（filtering）、去重（deduplication）与混合（mixing）**，最后再用一小段聊聊**后训练数据（post-training data）**，特别是当下大家如何用**合成数据（synthetic data）**。这一讲的前半部分主要围绕**预训练**来展开。

变换这一步上一讲已经提过，这里只是作个提醒性的回顾。**原始数据并不是文本**——即使你已经抓取了某个网页，打开 Common Crawl 看，里面也不是文本，而是 HTML；有时候是 PDF（比如 arXiv），GitHub 则是代码仓库的目录结构。所以变换这一步的大部分精力都花在**处理 HTML**上——因为网络的大部分是 HTML。

## HTML 转文本：启发式的、有损的

HTML 转文本的处理方式相当启发式（heuristic）。要做的典型操作有两类：

- **移除样板内容（boilerplate）**，比如导航栏（navigation）和广告；
- **提取内容（content）**，也就是页面的主体部分。

"什么算内容"其实存在不少微妙之处。通常你会去掉页脚（footer）、页头（header）、菜单这些，然后尝试提取正文；但你可以想象在某些情况下，导航元素反而有助于模型学习"网页长什么样"。所以**什么是内容、什么不是内容，并不总是清晰**。此外还有图片、表格怎么处理的问题——它们在网页上到处都是。

从根本上说，这是一个**有损（lossy）的过程**：你不得不把 HTML——它至少在结构上是层级化的（hierarchical），或者从渲染后的效果看是视觉化的（visual）——**线性化**（linearize）成一个 token 序列。表格尤其棘手：简单的表格可以用 markdown 渲染出来，但嵌套表格（nested tables）就非常难办，你总得在某处放弃，或者做一些近似。

为什么 HTML 转文本通常用**基于规则**（rule-based）的方法？理由很实际：

- 规则式处理器**非常快**；
- 这一步**不需要太多智能**——你并没有试图在这里做很复杂的事情。

所以规则式方法一般就够了。Percy 也承认：模型驱动（model-based）的干预在这个环节或许有用武之地，但它们必须非常快、并且确实要做更智能的事情。不过，只要你亲眼看过数据就会发现，任何基于规则的处理都有一定的失败率，数据里因此总会残留一些瑕疵。

上一讲已经展示过：**工具的选择会影响下游准确率**。在扩展的 DCLM 评估上，resiliparse 与 trafilatura 这类专用工具，比 Common Crawl 官方发布的 WET 转换文本表现更好：

## 顺带说说 PDF：FinePDFs

接下来简单讲一下 PDF。Hugging Face 有一个工作发布了名为 **FinePDFs** 的数据集。PDF 文件如果不在 PDF 阅读器里打开，看起来根本不像文本——它需要被"渲染"出来才有内容可读。PDF 和网页一样遍布网络，Common Crawl 里也确实有一些 PDF。

这里有几个要点（博客里有大量细节，Percy 表示不展开）：Common Crawl 主要关注文本，但有时给定一个 URL，如果它没有扩展名，你甚至无法在抓取之前判断它是不是 PDF。而 Common Crawl 里的**许多 PDF 是被截断（truncated）的**——因为 PDF 很大，抓取时会截断，所以需要**重新爬取（recrawling）**。拿到完整的 PDF 之后，还有一个问题：如何把它转成文本？有些 PDF 只是扫描件，本质上是图像，所以需要使用 **OCR**——通常是靠**视觉语言模型**（VLM）来跑 OCR，这明显比之前纯文本的处理贵得多。

幸运（或者不幸）的是：**PDF 只占整个网络的很小一部分**。但它们非常有价值——因为**一般只有想认真表达点什么的人才会制作 PDF**，相比之下网页就随意得多。所以 PDF 的平均质量通常高于 HTML 文件。当然，PDF 需要更多的清理与过滤，而且**比网页丢失更多的布局信息**：在 HTML 里你有 `h1`、`p` 之类的标签提供语义信息；而 PDF 天生只关心布局，它并不保留这种语义结构。

经过变换，你拿到了文本，但工作远未结束——下一步是过滤。

# 五个性能考量：warp、占用率、bank 冲突与合并访存

编程模型很优雅，但**编程模型与硬件之间的交互**才是性能的战场。这一节逐一过五个考量，它们会解释“为什么同样正确的代码，性能可以天差地别”。

## 考量一：warp

之前把 GPU 的编程模型描述成“线程 → 线程块 → 网格”这样一幅干净的画面，其中并没有 **warp**——从简化视角看，你写 kernel 时不必知道 warp 的存在（技术上你也可以显式控制它，但入门不必）。那么 warp 到底是什么？

回想线程块是线程的集合，而这些线程在硬件上被进一步分组成 **warp**——**每个 warp 恰好 32 个线程**。例如一个 64 线程的线程块就包含 2 个 warp：前 32 个、后 32 个。

**warp 的关键性质**：正如 Tatsu 上一讲提到的，**一个 warp 内的所有线程必须在同一个 SM 上以“锁步（lockstep）”方式执行同一条指令**——每个周期，它们执行的指令必须完全相同。由此引出一个问题：**控制发散（control divergence）**。当同一个 warp 里的不同线程需要执行不同的指令时（比如 `if A then ... else ...` 这样的分支），硬件只能先执行走 `A` 分支的那些线程、再执行走 `else` 分支的那些线程——两拨执行被**串行化**了。这是低效的，所以一般来说，你**要尽量避免分支**。

warp 还有一个非常酷的特性：**一个 SM 同时运行多个 warp**。SM 上有 warp 调度器（warp scheduler），管理一批将要执行的**驻留 warp（resident warp）**。由于每个 warp 都有自己的一组寄存器，**SM 可以在 warp 之间以零成本（zero cost）切换**——这一点与 CPU 很不一样。这种设计的目的在于**隐藏延迟（hide latency）**：假设一个 warp 正在读 HBM（很贵，可能要等 100 个周期），你当然不希望它干等着；调度器立刻切换到另一个 warp，让它去做 tensor core 运算。等到内存读取完成，再切回来继续。

## 考量二：warp 占用率（occupancy）

warp 概念出现的另一个原因是**占用率**，更准确地说是 **warp 占用率**。

硬件的限制是：**每个线程最多使用 255 个寄存器**；而每个 SM 的寄存器总数是固定的（例如 B200 为 65,536 个）。所以很简单的数学：**每个线程用的寄存器越多，SM 上能同时驻留的线程就越少**——这被称为“占用率下降”。但占用率低**并不必然是坏事**：如果线程少了、但每个线程做的工作更多，效果可能反而更好。占用率是个可以度量的量，但**不是越大越好**，因为存在其他权衡。

一个“想让线程变少”的例子是**线程粗化（thread coarsening）**：假设你要做逐元素运算，可以让每个线程处理一个元素（线程很多），也可以让每个线程处理多个元素（比如 8 个）。后者线程数变少、调度更省事，但每个线程做更多工作——如果你的线程很“轻”，把它们“养肥一点”常常是好的。

### 一个具体的占用率计算

假设一个线程块有 **128 个线程**，每个线程使用 **160 个寄存器**。硬件约束如下：

- 每个线程最多 255 个寄存器（满足）；
- B200 每个 SM 最多 **65,536 个寄存器**；
- 每个 SM 最多同时运行 **64 个 warp**。

逐步计算：

1. 每块的寄存器数 = 线程数 × 每线程寄存器数 = $128 \times 160 = 20{,}480$ 个寄存器；
2. 每 SM 最多能放的块数 = $\lfloor 65{,}536 / 20{,}480 \rfloor = 3$ 块；
3. 这 3 块对应的 warp 数 = $3 \times 128 / 32 = 12$ 个 warp；
4. 占用率 = $12 / 64 = 18.75\%$，约 **18%**。

也就是说，由于每个线程用了大量寄存器，这个 SM 只跑了它理论上能容纳的 warp 的 18%——**内存（寄存器）在这里反过来限制了你能做的计算**。

## 考量三：bank 冲突（bank conflict）

这个考量针对 **shared memory**。回忆一下：shared memory 类似 L1，位于 SM 上。硬件把 shared memory 划分成 **32 个 bank**，每个 bank **4 字节宽**；每个 bank 里存放着若干元素。硬件约束是：**每个时钟周期，每个 bank 至多只能被一个线程访问**（前提是访问的不是完全相同的地址）。

于是，**如果多个线程同时访问同一个 bank，这些访问就会被串行化**——这就是 **bank 冲突**。

最坏情况的例子：想象一个按行铺开的矩阵，每一行恰好横跨全部 32 个 bank；如果有 32 个线程想“大规模并行”地访问第一列（每个线程访问自己所在行第一列的元素），结果它们全都落在**同一个 bank** 里——于是它们只能排队等待，这是一个 **32 路 bank 冲突**，是最糟糕的情形。

你可能会说：“那就别访问列、去访问行不就行了？”但**这常常是无法避免的**。比如做矩阵乘法 $A \times B$ 时，你既要访问 $A$ 的**行**、又要访问 $B$ 的**列**，有时还要处理转置，无法随心所欲地选择遍历顺序。对逐元素运算确实怎么遍历都行；但对 matmul，你没法控制每个矩阵是按行还是按列主导。缓解方案之一是 **swizzling（重排）**——重新布置 shared memory 中的数据排列（比如按“行号异或列号”重排），使遍历时能绕开 bank 冲突。本讲不展开细节，但在做 profiling 时，你可以直接看到 bank 冲突与占用率等指标，从而定位问题。

## 考量四：内存合并（memory coalescing）

这是对上一讲内容的快速复习。当一个 warp 的 32 个线程访问 HBM 时，**内存访问会被合并成若干 128 字节的事务（transaction）**——也就是**缓存行（cache line）**——一次性取回。

**最佳情形（full coalescing，完全合并）**：所有线程访问同一条缓存行。设想内存按行排列，线程 0 访问 $M_{00}$、线程 1 访问 $M_{01}$、……线程 31 访问 $M_{0,31}$——它们正好覆盖一整条 128 字节缓存行（32 个线程 × 4 字节 = 128 字节），硬件一次就能把整行取回。相反，如果线程们沿**列**方向访问，那么每次迭代都会“顺带”取回大量用不上的数据（第二行、第三行……都在白白搬运）。

这个约束看起来和 bank 冲突很像，但要注意它们针对的是**完全不同的内存**：bank 冲突是 shared memory 的限制，内存合并是 HBM（全局内存）的限制。

## 考量五：块占用率（block occupancy）与波次量化

最后一个考量。线程块是按波次（wave）调度到 SM 上的：逻辑上你想定义多少线程块都行，但**物理上芯片只有固定数量的 SM**（比如 B200 有 148 个）。如果启动 **160 个线程块**，第一批只能调度 148 个，等它们跑完，再调度剩下的 12 个——而这 12 个块跑的时候，有 136 个 SM 无事可做。这就是**波次量化问题（wave quantization）**：当**最后一波线程块的数量小于 SM 总数**时，部分 SM 会空转，造成**块占用率低**。

所以通常来说，**让线程块的数量能整除 SM 数**是个好主意。

## 小结与课堂问答

小结一下这一节：存在一个非常优雅的编程模型——**网格 → 线程块 → 线程**；与之对应的是内存视角——**HBM 对所有线程可见（全局），shared memory 局部于一个线程块，寄存器局部于单个线程**。但是，**warp、bank 冲突、内存合并、占用率这些硬件细节，真正决定了性能**。这些细节往往难以凭空掌握：profiling 会给你一堆信息，但你得知道芯片到底有多少个 SM、各级内存的确切容量，而调度器有时候还会做你控制不了的事——**硬件比编程模型“脏”得多**。

**问答：一个线程块能否“共享”一个 SM？**

（同学：能不能让一个线程块与其他块共享同一个 SM？比如 148 个 SM、160 个块时，能不能让两个块挤进一个 SM？）

**Percy**：如果你做对了块的大小，这取决于块的“形状”。如果一个块已经用掉了 SM 上大部分 tensor core，再往同一个 SM 上塞一个块并不会加快速度。从根本上说，这里存在一个“参差不齐”（jagged）的分配问题——**块必须保持完整、不能被拆散**，你没法把一块“摊薄”到别的 SM 上去。遇到这种情况，你真正应该做的是**改变块的大小、进而改变块的数量**，让块数与 SM 数匹配，避免出现这种“尾巴”。

# 数据混合：权重、epoch 与回归式混合

## 从单来源到多来源

到目前为止，我们的流水线是：把原始的 HTML/PDF 变换成文本、过滤出高质量内容、去重——这是针对**单个数据源**做的。但语言模型是在**多个数据源**上训练的。在 **Marin** 项目里，有一个网站跟踪下一个模型要训练的不同数据源——可以看到一堆东西：有 Nemotron 数据、有我们刚讲过的 FinePDFs、还有一些机构书籍、代码等等：

![Marin 的 token viewer：追踪下一个模型将训练的不同数据源](/lectures/14/marin-token-viewer.png)

在较老的论文（比如 The Pile）里，你可以看到当年的数据源清单，以及给每个来源分配的权重——本质上就是**数据源上的一个概率分布**。于是核心问题来了：**这个分布应该是什么？**

## 三个基线做法

假设有三个来源（比如 Wikipedia、Common Crawl、GitHub），一个数据混合（data mixture）就是来源上的一个分布，比如 $p = \{Wikipedia: 0.3, CC: 0.5, GitHub: 0.2\}$。这个权重从哪来？

- **凭感觉（vibes）**：凭直觉手工设置 $p(s)$——这比你想的常见得多，哪怕近期的论文，也常常是"先看两眼、也许用点方法、然后手调几下"；
- **均匀采样（uniform）**：在来源上放均匀分布 $p(s) \propto 1$，采样时先均匀抽一个来源；
- **比例混合（proportional mixing）**：按来源里 token 的数量采样，$p(s) \propto num\_tokens(s)$。数据集 token 多权重就高——这通常也是理性的选择，但你可能会担心：一个巨大的低质量数据集会吃掉你大量 token。所以这也不像最优。

直觉上你应该**给更高质量的来源更高的权重**。但有两点必须记在心里：

1. **要保证多样性（diversity）**：来源之间常常**不可比**——文学、代码、论文，你很难说"这篇论文比那段代码质量高"，它们是不同类型的对象。如果你希望语言模型样样都行，就不能把质量全押在论文上；
2. **每个来源是有限的（finite）**：如果你给一个很小的来源过多权重，你会很快把它"用完"，然后只能一遍遍重复——**反复 epoch** 同一个来源，这对训练是有害的。这一点值得多说几句。

## epoch 的数学：一个让人警觉的例子

把这个"有限性"算一笔账。假设只有两个来源：

- **低质量源**：10 万亿（10T）token；
- **高质量源**：10 亿（10B）token——高质量源通常更小。

如果做一个**朴素的均匀混合**（各 0.5），并且**训练 1 万亿（1T）token**——注意"训练 1T token"并不等于"1T 个唯一 token"，它只是说"训练那么多步 × batch size"这么多 token。那么每个来源里的单个数据点会被训练多少遍？也就是**每个数据点的 epoch 数**：

```python
def billion(x):
    return x * 10**9

def trillion(x):
    return x * 10**12

source_token_counts = {
    "low": trillion(10),   # 低质量：10T token（量大）
    "high": billion(10),   # 高质量：10B token（稀缺）
}
p = {"low": 0.5, "high": 0.5}   # 朴素的均匀混合
train_tokens = trillion(1)      # 训练 1T token

low_num_epochs = (p["low"] * train_tokens) / source_token_counts["low"]
high_num_epochs = (p["high"] * train_tokens) / source_token_counts["high"]
```

- 低质量源：$p_{low} \times \text{train\_tokens} / 10T = 0.5 \times 1T / 10T = 0.05$——**还不到一个 epoch**，也就是说这份低质量数据里只有约 5% 的 token 会被碰到；
- 高质量源：$0.5 \times 1T / 10B = 50$——**每个数据点要重复 50 遍**！因为你需要 5000 亿 token 的高质量数据，而你手上只有 100 亿。

Percy 特别强调：这真的非常重要，而且**一些大型训练跑确实在这个地方栽过跟头**。你不能只是盯着数据集、定义一个分布就开始采样——只看质量、不看**每个来源到底有多少数据点**，就会漏掉 epoch 的问题。

### 课堂问答（epoch 与混合的实现）

**问：为什么要 50 个 epoch？更少的 epoch 不也能达到差不多的性能吗？**

Percy 回答：你的确**不需要** 50 个 epoch。这个数字之所以是 50，是因为如果你直接定义了这个混合就去训练，除非你非常留神，否则你会**在毫无察觉的情况下**做掉 50 个 epoch——最坏情况是浪费算力。所以教训是：**时刻检查你实际在每个数据源上做了多少个 epoch**。

**问：混合在训练中是怎么实现的？每个 step 都在切换来源吗？**

Percy 回答：一般来说，你要填一个 batch：对 batch 里的**每个元素**采样它来自哪个混合分量，然后用该分量的序列把 batch 填满。通常每个序列（sequence）完整地来自一个混合分量——**不是逐 token 采样**。学生补充道：也就是说混合假设是**在 batch 级别**成立的，每个 batch 里应该包含多种来源的样本；Percy 确认：是的，通常你会希望一个 batch 里就有一些混合，以降低方差。

## UniMax：给 epoch 加一个硬上限

这个问题其实很早就被注意到了。在 **UniMax** 论文里，场景是**多语言模型训练**——有些语言资源非常稀缺，必须做点什么。他们观察到：之前的一些工作会把比例混合的结果取一个幂次，$p(s) \propto num\_tokens(s)^\alpha$（$\alpha \in [0, 1]$），用这个办法把分布"压平"。UniMax 的想法更直接：**均匀采样来源，但对任何来源的 epoch 数设一个硬上限 $C$**。达到了上限？不好意思，这个来源不再提供任何 token，换下一个。它就像一个安全网。形式化地说，约束是

$$p(s) \times \text{train\_tokens} \le C \quad \text{对所有来源 } s$$

并且存在一个简单过程，可以在该约束下求出混合。

## 回归式混合：最 principled 的做法

接下来换个角度：**混合本身是怎么定义出来的**？如果有 50 个来源，就有 50 个数要填。比例混合不够，你也可以估计一个质量指标、按质量采样——但那还是启发式。最 principled、也最容易看懂来龙去脉的，是**基于回归的混合方法（regression-based mixing）**，比如 **RegMix**（以及 Omix 等一系列论文）。

思路相当简单：

1. 假设你最终要训练一个**大规模模型**。先到**小规模**（比如 3 亿参数）去试不同的数据混合——比如有三个分量，就试各种混合比例；
2. **训练一群（a swarm of）小模型**，每个模型在某个目标指标上给出一个损失——可以是下游 eval，也可以是困惑度，随你定义；
3. 用这些数据点**拟合一个回归模型**：输入是数据混合权重，输出是损失。于是你有了一个很便宜的模型，可以预测"如果我按这个混合训练，会得到多少损失"；
4. 接着**优化这个函数**，求出最优的数据混合；
5. 用这个混合去训练大规模模型。

这和**缩放定律**（scaling laws）的思路是同构的：先做便宜的运算得出答案，再放大。

![回归式混合示意图：小规模训练一批不同混合的小模型，拟合"混合 → 损失"，再优化并外推](/lectures/14/regmix.png)

### 几个设计决策

- **要尝试哪些混合**：你需要在"分布的分布"上采样——通常用 **Dirichlet 分布**（也有人用指数分布）；
- **回归方法**：人们试过**线性模型**、**梯度提升决策树**，还有效果不错的 **log-linear 模型**；
- **回归目标**：常常基于**下游 eval**。这里必须非常小心不要过拟合！预训练理论上是在训练一个通用模型，不是去拟合某些特定 eval。如果你手头有一堆代码 eval，优化之后权重自然会全压到代码数据上——这并不高明；等你想让它写诗，就发现已经过拟合了。均匀混合和比例混合没有这个问题，因为它们压根不看下游 eval；
- **小规模与大规模的差距**：这是**成本与准确度**的权衡。模型太小可能不具代表性；但如果为了做这件事去训练大模型，那就本末倒置了——等于在最大规模上做超参调优，太贵。

RegMix/Omix 论文里有一张很好的表，展示了一众落入这个框架的方法：代理模型的规模通常是几千万参数；采样多少个混合点；$m$ 是数据域的数量；用 Dirichlet 或指数分布；回归用 log-linear 等；优化方式也各有不同。

![不同数据混合方法一览（代理模型规模、混合采样、回归形式与优化方式）](/lectures/14/data-mixing-methods.png)

### 两个"信仰之跃"

这个方法有两个必须小心的地方：

- **信仰之跃一：回归模型在最小化处仍然准确。** 如果你随机采样一些混合点，经典泛化理论保证回归在"分布内"大致准确；但**优化**会把解推向可能**覆盖不足的极端**——你拟合回归时采样的区域，未必覆盖优化器想去的地方；
- **信仰之跃二：最优混合从小规模迁移到大规模。** 在开放社区通常工作的规模上，这个迁移大体成立（或者说"没有公然失效"）；但显然存在**规模依赖效应**——回想过滤那节的结论：训练 token 越多，低质量数据也越能用，所以最优混合不可能完全一样。你只能祈祷它足够接近。

## 规模依赖效应与两种对策

刚才说的规模依赖效应，我们在 epoch 的例子里已经见过了。假如低质量源有 10T token、高质量源有 10B token：**在低 token 数的小模型上**，你不会 epoch——所以你可能把大量权重放在高质量源上（"维基百科太棒了，干脆全训练维基百科"）；但**如果把这个混合拿给大规模训练**，你会在高质量数据上反复 epoch、严重过拟合。这肯定不行。

**解法一：cap（epoch 上限）**。UniMax 和 Omix 用的就是这种——给每个来源的 epoch 数设上限。

**解法二：simulated epoching（模拟 epoch）**。原则是：**让小规模看起来像大规模**——这也是整个课程反复出现的主题（还记得 Tatsu 讲 MuP 时让超参数跨规模迁移吗？同一个原则）。朴素放大（naive scaling）的问题是：小规模不 epoch、大规模却要 epoch，这两种操作在数据上是**质的不同**。模拟 epoch 的做法是**把所有来源按比例下采样**：

```python
small_run_tokens = billion(10)   # 小规模运行：10B token
large_run_tokens = trillion(1)   # 大规模运行：1T token
ratio = small_run_tokens / large_run_tokens   # 1/100

downsampled_source_token_counts = {s: count * ratio for s, count in source_token_counts.items()}
```

小规模 10B token、大规模 1T token，比例就是 1/100——每个来源都乘上这个比例。**在下采样后的数据上**，"把权重全押在维基百科上"的解不再好看：你没法训练全部维基百科，只能训练它一个极小碎片，于是会疯狂 epoch、损失很糟。这样一来，优化器自然会去寻找**更均衡**的混合——你就在小规模上**模拟出了大规模才会遇到的数据稀缺**。一个典型的结果是：朴素做法把 0.9 的质量压在高质量源上，模拟 epoch 之后会平衡到比如 0.3。

### 课堂问答（数据混合）

**问：下采样会不会让某个来源变得太小、无法泛化？**

Percy 回答：有可能得到极少的 token。通常会发生的是：优化器给那个来源一个很小的权重，等你放大之后反而取到正确的那部分 token。原则上没问题，但可能存在"舍入误差"——本想让某个数据集训练一遍，结果意外训练了零遍。解决的办法是绕过它：比如**总是保证每个来源至少训练一次**。

**问：这些来源恰好对应不同主题。你会不会拿一个多样化的数据集、在数据集内部再做数据混合？**

Percy 承认这个问题问得好，正想补充：是的。在 Nemotron 论文（以及一些 Omix 相关的工作）里，你可以把一个数据集——比如 Common Crawl——**按域（domain）分组**（AI2 的人有叫 web organizer 的工具，可以按主题分组），同时也可以按**质量**过滤。于是你得到一个**二维网格：域 × 质量**，每个格子都是一个可以数据混合的成分——这是自动确定"域"的一种方式；在这个基础上，再叠加人们手工塞给你的额外来源。

## 小结

数据混合的问题就是：**如何给不同来源加权**（维基百科、Common Crawl、代码、还有从某处爬来的数学数据）？**回归式混合**是一个很好的思考框架：在小规模上估计"混合权重 → 损失"的函数形式、优化它、再推广到大规模。但一定要小心 **epoch 与过拟合**——要么 **cap**，要么 **simulated**。最后别忘了这个大教训：**任何你在优化的东西，都要非常小心别优化错了对象**。

# 后训练数据与合成数据：OpenThoughts 到 SWE 系列

## 从任务无关到任务相关

到目前为止，我们讲的都是**预训练**（或者中期训练）数据：它基本是任务无关的——除了回归式混合在优化损失之外，数据本身并不绑定特定任务，目的是发展基础能力。而**后训练数据（post-training data）**则非常**任务相关**。Percy 不打算做全面综述，只想指出最近发布的一些有意思的后训练数据集——特别是**代码**方向，因为这是当下大家最关心的地方。

后训练数据的**通用配方**只有三步：

1. **定义一组环境（environments）**——在代码场景里，环境就是 GitHub 仓库；
2. **定义一组任务（tasks）/ 提示（prompts）**；
3. **从一个强模型（教师，teacher）收集响应（responses）**。

这里有个隐含事实：至少在开源社区，**几乎所有后训练数据都是合成生成的**。教师也可以换成人类——但那样又慢又贵：几年前即使是前沿团队，也得花大钱雇很多人来写响应；如今连前沿团队都可以做"人机混合"了。但不管怎样，背后总有一个教师在产出响应。

## OpenThoughts：推理数据的"大杂烩"

**OpenThoughts** 这个工作出现于 o1 发布之后——当时大家对推理（reasoning）数据（主要是数学和科学）兴趣大增，想知道怎么拿到高质量的后训练数据。最终他们用 **QwQ-32B** 作为教师，产出了 **120 万（1.2M）个样本**。

问题从**27 个人类来源与合成来源**中来——比如 StackExchange、NuminaMath、化学数据等等：

![OpenThoughts 的数据来源：27 个人类与合成来源（这里是其中的编码类）](/lectures/14/openthoughts-sources.png)

这是一个大项目，很多人参与贡献。来源五花八门：有些是编码练习，有些更贴近真实（比如 **code review** 就比较真实；**code golf** 就不太真实）。

他们对"如何生成响应"做了相当全面的分析，结论很有意思：

- **来源不必多**：铺开更多来源不如**对同一个问题采样多个生成（generation）**——16 个响应是有效的；
- **更好的模型不一定是更好的教师**：**QwQ-32B**（如今回头看又老又小的模型）居然比 **DeepSeek-R1**（当时最强的开源模型之一）是更好的教师；
- **基本的答案过滤（answer filtering）没有帮助**；
- **小而高质量的来源**（比如 OpenMath-2-Math）**优于大而多样的来源**。

整个流水线长这样：一堆来源进来 → 去重 → 随机下采样问题 → 每个问题生成多个答案 → 进入最终数据集：

![OpenThoughts 的流水线：多来源 → 去重 → 下采样问题 → 每个问题生成多个响应 → 最终数据集](/lectures/14/openthoughts-pipeline.png)

注意数字的换算：**120 万是样本（example）数，除以 16 才是实际的问题数**。

## 代理编码数据：从"写代码"到"做软件开发"

除了数学与科学，近年大家越来越想训练**代理编码（agentic coding）模型**——不只是会生成代码，而是能做软件开发的模型。

### SWE-smith：用语言模型造任务

**SWE-smith** 的想法是**用语言模型自动生成任务**。他们有一个 agent 先把仓库整理到可用状态（安装依赖等），然后生成任务——通常是**以某种方式修改代码、甚至故意引入 bug**——任务经过验证后成为任务实例。这些是**合成任务**，但规模可观：**128 个 GitHub 仓库生成了 5 万（50K）个任务**，在去年（2025）已经算很大了。

![SWE-smith：给定仓库，用语言模型生成任务（引入 bug 等），验证后得到任务实例](/lectures/14/swe-smith.png)

### SWE-Zero：没有执行反馈也行？

接下来是 **SWE-Zero**（Nvidia）。它源于一个观察：**SWE 任务的依赖重得离谱**。大多数 GitHub 仓库根本跑不起来；要装依赖、要回滚到 PR 时代的版本（早就过时了），一团糟；为几千个仓库各配一个 Docker 镜像简直是**基础设施噩梦**。于是他们想：能不能不做仓库特定的执行环境？

关键观察是：**强模型其实已经足够好，很多任务不需要执行反馈就能解**。比如有的模型允许执行时能到约 80%，不允许执行时也有接近 70%——不能执行代码还有这个成绩，说明**模型内部有对代码语义的"世界模型（world model）"**：

![SWE-Zero 的观察：允许执行与禁止执行时各模型的通过率对比（差距很小）](/lectures/14/swezero-noexec.png)

于是他们生成了 **30 万（300K）条 agent 轨迹**——全部来自**真实的 GitHub PR**（比 SWE-smith 的合成任务真实得多），源自 **15 万（150K）个 PR**。脚手架用 **OpenHands**。这里有很多细节，比如**防止 agent"hacking"**：通常你给 agent 的指令是"探索、测试、实现"；而 SWE-Zero 的 3.0 版本干脆规定：**不能运行 Python 代码，只能用 `sed`、`grep` 这类基本操作**（还要移除未来的 git 提交，防止 agent 靠"读 git 历史"作弊）：

![SWE-Zero 的 prompt 设计：限制 agent 只能做基本文件操作，防止其运行代码或"hacking"](/lectures/14/swezero-prompt.png)

数据从**大编码模型蒸馏**而来，并且做了**过滤**——因为有些编码模型会无视指令、仍然尝试执行代码。他们还准备了 **1.3 万（13K）条确实需要执行反馈的轨迹**（叫 **SWE-Hero**）。训练流程是：先在 SWE-Zero 样本上微调，再在 SWE-Hero 样本上微调——确实取得了一些进展（虽然离前沿还差得远）：

![SWE-Zero + SWE-Hero 两阶段微调后的结果](/lectures/14/swezero-results.png)

### SWE-rebench：再来一次大规模 PR 收集

**SWE-rebench** 是另一次"抓取海量 PR"的尝试。套路和前面都类似：拿一批 GitHub 仓库、尝试安装（大多数会失败、就再试）、然后用语言模型产出响应。具体数字：从 **3,400 个 GitHub 仓库**得到 **2.1 万（21K）个可交互的 Python SWE 任务**；PR 来源是 **45 万（450K）个 GitHub 与 GitHub Archive 的 PR**；用 **Qwen 2.5-72B-Instruct** 来安装依赖并评估 PR 质量：

![SWE-rebench：从 3,400 个仓库、45 万 PR 构造 2.1 万个可交互 Python SWE 任务](/lectures/14/swe-rebench.png)

### SWE-ZERO-12M-trajectories：把规模推到 1200 万

最后一个（这节课当天刚发布）：把 SWE-Zero 的思路**扩大到 1200 万（12M）条 agent 轨迹**。SWE-Zero 的好处是**非常轻量**——不需要任何仓库特定执行。任务来源用了 **SWE-rebench-v2** 的任务：其中 3.2 万（32K）个可以执行、12 万（120K）个不能执行——而 SWE-Zero 不在乎，**不能执行的也能全用**。因为数据量巨大，这次用的是**非常小的模型**：**mini-coder-1.7b**（很小，pass@100 是 50.4）+ **mini-swe-agent** 脚手架。

## 整讲总结

最后把整个讲座收个尾。回顾一下：

- **过滤**：定义"好数据长什么样"，训练一个轻量分类器，扫过网络爬取，得到与你想要的匹配的一小撮数据；
- **去重**：避免过拟合、节省 flops；
- **混合**：在小规模上尝试各种混合，外推到大规模；
- **后训练数据**：从无环境的数学，到如今体量暴涨的代码数据集——提示（prompt）的来源谱系是：**完全合成（fully-synthetic）**、**半合成（semi-synthetic，真实环境 + 合成任务）**、**真实（real，比如 GitHub PR）**；响应则来自"有能力、同时是好的教师"的模型；代码环境非常痛苦；还有大量的过滤与其他细节。

Percy 最后提醒一句：**真实的数据工作其实非常"脏"（grungy）**——高度领域特定、需要反复盯着具体例子才能做出高质量的数据集。这一讲只能算"数据版图"的一幅概览，而不是数据工作的真实样貌；但希望它让你对整个数据生态有了感觉。今天的课就到这里。

# LLaVA 与 LLaVA OneVision：把图像注入语言模型

## VLM 的基本模板：把图像编码注入语言模型

现在我们已经有了 CLIP 和 SigLIP 这两种图像编码器：输入一张固定尺寸的图像，输出一个携带语义的向量。接下来要做的是**构建视觉语言模型（vision language model，VLM）**。本讲会讲两个开源模型家族——**LLaVA** 和 **Qwen**——它们在"大致模板"上非常相似，只有一些细节不同。

基本想法是：**把图像编码器的输出直接注入一个语言模型**。这更像是一次"中期训练 / 后训练"（mid-training / post-training）式的操作：**取一个现成的图像编码器，取一个现成的 LLM，把它们"缝合"起来**——而不是从头训练一个多模态模型。

## LLaVA（2023）：一个开放的视觉助手

**LLaVA**（Large Language and Vision Assistant）论文发表于 **2023 年**，当时让很多人兴奋。背景是：那时候像 **GPT-4** 这样的闭源模型已经能做一定的视觉推理；LLaVA 证明了**一个开源模型也能做相当程度的视觉推理**——虽然不如 GPT-4，但它是开放的，人们终于能看到"引擎盖底下"是什么。

### 架构：CLIP + Vicuna + 线性投影

VLM 大致有这么几块：

- **视觉编码器（vision encoder）**：LLaVA 用 **CLIP**；
- **文本解码器（text decoder）**：一个语言模型，LLaVA 用的是 **Vicuna**——第一代 LLaMA 模型在 ShareGPT 对话数据（人们分享出来的与 ChatGPT 的对话）上微调得到的模型；
- **投影器 / 适配器（projector / adapter）**：把视觉编码器的输出变成语言模型的输入。

具体到 LLaVA，投影器简单得令人发指：**只是一个线性投影（linear projection）矩阵 $W$**。

![LLaVA 的架构：CLIP 编码图像 → 线性投影 W 映射到文本嵌入空间 → 与文本嵌入拼接送入语言模型](/lectures/17/llava-architecture.png)

具体流程：图像经过视觉编码器 CLIP（用的是表现最好的 CLIP 版本，14×14 patch）得到一个向量，但这个向量并不在"文本嵌入所在的空间"里；于是乘上一个矩阵 $W$，得到另一个与文本嵌入同空间的向量。文本那一侧就走标准嵌入。于是**整个序列**（文本嵌入 + 图像向量）一起通过一个标准 Transformer，产生输出。我们在某种意义上**把图像"翻译"成了文本 token**，从而能够复用预训练语言模型的能力。

注意这里 LLaVA 是"最简"的：投影器只有一层线性层。Flamingo 的 cross-attention 层、Q-Former 之类的设计都要复杂得多。

### 数据：用 GPT-4 合成 158K 条指令数据

LLaVA 的数据来自 **MS COCO**：这是一个人工标注的数据集，Mechanical Turk 工人标注了大量图像的**边界框**（bounding box）和描述图像内容的 **caption**。LLaVA 的做法本质上是**为自己合成一个数据集**：

- 把 **caption 或检测到的物体** 作为提示词喂给 **GPT-4**；
- 让 GPT-4 生成**问题 / 对话**（比如一个问答对）、**详细描述**、或者**复杂推理**；
- 把生成结果与原始图像配对。

![LLaVA 的数据生成：MS COCO 图像 + 人工 caption → 提示 GPT-4 生成对话、详细描述、复杂推理 → 与原图配对成 158K 训练样本](/lectures/17/llava-gen.png)

具体来说：给你一张 MS COCO 图像和一段人工 caption，你问 GPT-4"生成一段对话"，它会给出问题和答案；你请它生成详细描述，它会给出和 caption 类似但更详细的东西；你请它做复杂推理，它也会照做。这样总共凑出了 **158,000 个例子**。

### 训练：两阶段

LLaVA 的训练分两个阶段：

1. **第一阶段（对齐，alignment）**：**冻结视觉编码器和语言模型，只训练 $W$**。这个阶段的目标就是让图像向量被映射到与自然语言 token 嵌入"看起来差不多"的空间——如果你用随机的 $W$，图像向量当然不代表任何自然语言 token 的嵌入。训练 $W$ 就是为了让它们"像"自然语言 token 嵌入；
2. **第二阶段（微调，fine-tuning）**：**仍然冻结视觉编码器，同时训练 $W$ 和语言模型**。在合成的数据（图像 + 对话 / 描述 / 复杂推理，即"图像 + 文本 → 文本"）上微调整个系统。

### 一个例子

论文里有个挺有意思的例子。给定一张输入图像和一段对话，用户问："这张图里有什么不寻常的地方？"（what's unusual about this image？）LLaVA 能回答：**"你一般不会在一辆小货车的后背上熨衣服。"** 而且作者强调，即使用户的提示并没有直接引导"异常性"，模型依然会主动谈起它——GPT-4 当然做得到，但当时其它模型做不到。

![LLaVA 的例子：用户在问"这张图有什么不寻常"，模型答"你不会在一辆货车的后背上熨衣服"](/lectures/17/llava-example.png)

## LLaVA OneVision（2024）：单图、多图与视频

时间跳到 **2024 年**。LLaVA 之后还有一系列后续工作：LLaVA 1.5、LLaVA-Next，然后就是 **LLaVA OneVision**。核心配方没变，但在**应用野心**上更大——**能处理多张图像和视频**。Tatsu 说他会用 OneVision 把这一系列的所有创新都收进来讲。

### 架构升级：SigLIP + Qwen2 + 两层 MLP

还是那张熟悉的图，但现在输入可以是**单张图像、多张图像、或者视频**（视频本质上就是按帧采样的图像序列）：

- **视觉编码器**：升级为 **SigLIP**（用最后一个 Transformer 层前后的 grid 特征）；
- **文本解码器**：改用 **Qwen-2**（当时大概是最好的开源语言模型）；
- **投影器 / 适配器**：从线性投影升级为**两层 MLP**。

![LLaVA OneVision：同一模板，输入升级为单图 / 多图 / 视频](/lectures/17/llava-onevision.png)

这有点像"你有一套系统，然后把零件逐个升级"——大框架没变。

### 数据处理：为什么需要 AnyRes

做 **OCR**（光学字符识别）是他们的目标之一，而 OCR 需要**极其细粒度的信息**——不然"J"会被看成"I"。回忆一下：CLIP 会把图像缩放到 336×336 再中心裁剪，一份文档如果被压成 336×336，**根本没法读**。所以他们的解决方案是 **AnyRes**——这个想法其实是 LLaVA 1.5 引入的：

- 把一张图像**拆成多块**；
- 每块都缩放到视觉编码器期望的分辨率（比如 336×336）；
- 分别编码每一块，得到一堆向量，然后**拼接**起来。

道理很简单：既然视觉编码器处理不了高分辨率，那就**不要下采样，而是裁剪**，用"多块拼起来看"的方式覆盖整张图像。而如果原图真的超高清、或者输入是视频，块数会爆炸、token 太多，那就再做下采样。**AnyRes 的核心是"自适应（adaptive）"**——而这恰好和 Transformer 的"自适应"是同一件事：语言的句子可以任意长，Transformer 本来就处理得很好；那么图像为什么不能是任意分辨率呢？

![AnyRes：整图下采样一条路径 + 切成 336×336 的块分别编码 + 拼接；块太多时再用双线性插值压缩](/lectures/17/llava-onevision-anyres.png)

具体到他们的做法（图里是一张论文页面的例子）：先下采样整张图得到一条"全景"路径；再把图切成一块块视觉编码器能吃的尺寸，逐块编码；最后把所有 patch 拼接起来。如果 patch 太多，就用双线性插值（bilinear interpolation）减少块数。

### 三种输入：让各种模态的 token 量大致相当

能处理图像、多图和视频了，但**所有模态本质上都可以归约成图像**——他们却在分配上"动了手脚"，因为要保证各模态的 token 量**大致可比**：视频可能很长，不能让数据集被一堆重复帧主导。

![LLaVA OneVision 对三种输入的处理：单图用高分辨率（整图 + 最多 9 块裁剪）；多图每张用基础分辨率；视频每帧用更低分辨率](/lectures/17/llava-onevision-modalities.png)

具体策略：

- **单张图像**：整图下采样 + 最多 9 块裁剪，用高分辨率仔细看；
- **多张图像**：每张只给**基础分辨率**——"如果我要同时看多张图，就每张都远距离瞥一眼"；
- **视频**：每帧用**更低分辨率 / 更少 token**——视频最多取 32 帧，很快会撞上上下文长度（context length）的限制。后面会看到，**处理长上下文是多模态的一大关键**。

### 数据：质量优先

LLaVA OneVision 的数据哲学是"**质量优先于数量**"（quality over quantity）。另一种理解是：数据**高度任务化（targeted）**——很多数据都是面向具体任务的，比如视觉问答、回答关于表格的问题。这明显是**后训练**的领域：你希望模型会做这些任务，于是造出这些任务的数据。

另外，这项工作**毫不掩饰地在蒸馏 GPT-4**（用 GPT-4 类模型合成数据换取最好性能）——Tatsu 直言这"不算理想，但如果你没有标注预算，这就是你会做的事"。数据集覆盖单图、多图、视频；有些任务非常具体，比如"给你两张图，找出它们之间的差异"。

![LLaVA OneVision 的数据集：大量合成的、任务化的数据（单图、多图、视频）](/lectures/17/llava-onevision-data-1.png)

![LLaVA OneVision 的数据集（续）：视觉问答、表格问答、找不同等](/lectures/17/llava-onevision-data-2.png)

### 训练：由易到难的三阶段

训练思路和之前差不多，但从两阶段变成了**三阶段**：第一阶段只训练**投影器（适配器）**；第二阶段引入高质量、偏知识的数据；第三阶段训练整个模型，数据换成更像下游任务的例子。Tatsu 说，他也不确定这里有没有什么原则性的理由，大概就是：**第二阶段放高质量、偏知识的数据，第三阶段放更像下游任务的数据**。整体哲学是"**从易到难**"（easier to harder）。

![LLaVA OneVision 的训练：三阶段，由易到难](/lectures/17/llava-onevision-training.png)

### 有趣的发现：模态之间的迁移

这篇论文里一个有意思的发现是**模态之间会迁移**：

- **图表（diagram / chart）数据只有单图**，但在测试时可以泛化到**多图**：训练时从没见过"一张表 + 一张图、然后对着它们提问"的例子，测试时却能对着两个图像（一个是表、一个是图）进行对话；
- **OCR 只用单图数据、关系推理用多图数据**，却能泛化到**驱动 GUI 智能体**（agent）的场景：给智能体一堆截图（多张图），它能生成对这些截图的描述；
- **视觉提示（visual prompting）**：在一张图里画一个圈来指出"你应该关注这里"，这类数据只存在于单图，却能泛化到**视频**——比如用户说"描述一下视频里被高亮的那个球员"，而该球员出现在多个帧里。

![迁移一：单图的图表数据泛化到多图（表格 + 图表）问答](/lectures/17/llava-onevision-transfer-s1.png)

![迁移二：单图的 OCR 与多图的关系推理泛化到 GUI 智能体（多张截图）](/lectures/17/llava-onevision-transfer-s2.png)

![迁移三：单图上的视觉提示（画圈）泛化到视频（跨帧高亮球员）](/lectures/17/llava-onevision-transfer-s8.png)

Tatsu 的第一反应是："这看起来不就是每个任务各搞一个数据集、像监督学习一样吗？" 但**当任务足够多时，这些模型似乎确实学到了一些跨模态的迁移能力**——这本身就是很有意思的结论。

## 小结：LLaVA 系列的意义

- 标准 VLM 模板是 **视觉编码器 + 投影器 + 语言模型**；
- 大量的工作投入在**数据整理**（data curation）上，而且非常依赖**合成的、任务化的数据**；
- LLaVA 系列是少数**不仅开源模型权重、还开源数据**的工作——这意味着别人真的可以复现和研究这一切。

## 连接 Qwen

LLaVA 是"开放"的极致（连数据都开源）。接下来要讲的 **Qwen** 系列则走了一条略有不同的路线：架构上有更多自己的设计（交叉注意力适配器、动态分辨率、新的位置编码、跨层融合），数据细节反而公布得很少。我们把目光转向 Qwen。

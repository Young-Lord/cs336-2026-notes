# 动机与网络：从单卡到数据中心

欢迎回来。上一讲 Percy 讲了并行的**底层机制**——集合通信原语（collective operations）、数据并行、张量并行、流水线并行的最初版本。今天这一讲我要讲的是我最喜欢的东西：关于现代语言模型训练中并行的一切"知识细节和八卦（trivia）"。我们的目标是真正摸清：当你不得不训练一个巨大模型、用上巨大的算力时，到底牵涉到多少复杂的系统问题。

## 本讲预告：为什么"4D 并行"是存在的

开场先给一个预告：本讲末尾会有一张写着"4D 并行"的幻灯片，因为存在**四种可以同时做**的并行化策略——实际上我讲到的比四种还多。而且你会发现，要在最大规模上并行化训练，你几乎需要把它们**全部（或大部分）都用上**，我们也会讨论为什么。

这还直接连着你们的作业：作业的一部分，就是给定一种**网络拓扑**（network topology）和**一个模型**，找出对该配置来说**最优的并行化策略**。最后我会带着大家看一些公布了细节的近期大规模训练案例，看看这些概念在真实世界中是怎么落地的。

## 为什么需要并行？两个瓶颈

先快速过第一大部分：这部分多少有点复习性质——基础的 collectives、基础的网络原语。为什么需要这套东西？因为有两个瓶颈，只能靠**多台机器、多块 GPU** 来解决：

1. **算力（compute）**：我们需要的算力超过任何单颗芯片能提供的。解决方式就是把很多很多机器连起来。世界上最快的超算拥有 **exaflops** 量级的算力，而单块 GPU 离这个数字差着十万八千里；
2. **显存（memory）**：模型太大了，单块 GPU 装不下。于是必须把模型**切碎**（shard）成小块，分布到多块 GPU 上。

这两条引出了"很多台机器、很多块 GPU"带来的全部复杂性。

### 节点内 vs 节点间

本讲从头到尾会反复出现一个重要的概念性区分：

- **节点内并行（intra-node parallelism）**：同一台机器内的 GPU 之间连接**非常快**，所以可以做通信代价很高的事；
- **节点间通信（inter-node communication）**：跨机器的通信**慢**得多，因此我们不得不采用更"尊重信道通信约束"的做法。

两种并行方式都必须掌握。另外提醒一句：我们今天讨论的所有东西都不涉及实际"发包"——我们处理问题的层面是**集合通信原语（collective communication primitives）**。做通信量的记账时，我会说"这里需要做一次 all-reduce"或"这里需要做一次 all-gather"。要实现这些操作的极致效率当然要一路做到硬件层，但今天我们的讨论是**算法层面**的，所有网络原语都停留在这个抽象级。

## 一个重要的等价：all-reduce = reduce-scatter + all-gather

上一讲 Percy 已经讲过一个对今天非常关键的等价关系：

> **all-reduce 可以拆成两步实现：先 reduce-scatter，再 all-gather。**

为什么这对今天的讨论特别重要？因为在**带宽受限**（bandwidth-limited）的情形下，这是你能做到的最优。于是会出现一种情况：某个算法一边做一次 all-reduce，另一边做"reduce-scatter + all-gather"这两个不同的步骤——而这两者在某种意义上代价相同，意味着**右边的算法是免费的**。这个事实我们今天会反复用到。

> **课堂问答：为什么单独强调这个分解？**
>
> （同学：有没有特别的理由，说梯度都要走 reduce-scatter？）
>
> **Tatsu**：你是问为什么我专门讲这个分解。当然还有别的分解方式——你完全可以说"all-reduce 等于别的组合"。我特意强调**这一个**，是因为它对后面的 **ZeRO 算法**特别有用。其他的分解当然也存在。

## 硬件栈：TPU 的 toroidal mesh 与 GPU 的 fat-tree

今天大部分讨论是**硬件无关**（hardware agnostic）的——一旦你理解了基本概念，就能套用到任何硬件底座上。但在开始之前，我想稍微讲讲底层的硬件栈，一方面因为它本身挺有意思，另一方面也因为我认为**不同模型训练公司会因此采用不同的并行化策略**。

还记得 TPU 吗？它是 Google 的加速器。在 GPU 那一讲我提过：TPU 有点像"轻量级 GPU"，但它与 GPU 最大的不同在**网络**。

### TPU：toroidal mesh（环形网格）

用一张幻灯片就能说清：**TPU 网络是所谓的环形网格（toroidal mesh）**。你可以想象一张网格，然后把网格的**两端连起来**（两端互相通信）——实际上它比这更复杂，是一个三维结构，课程里有一个很酷的 3D 可视化网页，可以亲眼看到三维的 toroidal mesh。但你的心智模型用这张简图就够了：

![](/lectures/08/slide-9.png)

所有芯片只和**邻居**相连，而邻居是"绕一圈"接上的。这带来一个极好的性质：网络拓扑**极其简单**，可以**无限扩展**——无论你的网络变多大，每个芯片的邻居数都不变。

### GPU：fat-tree（胖树）与 all-to-all 哲学

GPU 的网络哲学则完全不同，它更像一种 **all-to-all** 哲学。它的组织方式是**树**——通常叫 **fat-tree（胖树）**：最底层 GPU 之间连接得非常非常快；若干 GPU 组成一个 **pod**；pod 之间再通过**脊柱交换机**（spine switch）互相通信。这意味着当节点数增长、树越长越大时，你的通信代价会上升、通信拓扑会变得更复杂，因为你是在一路往上做 all-to-all 连接。

这两种哲学的分野在于：**如果你只和邻居通信，TPU 很棒**——它成本效益高，同样的功耗可以把每条连接做得更"粗壮（beefy）"；**如果你的通信模式很随机、很不可预测**，那 GPU 的联网方式更灵活。

### 为什么用 mesh、为什么用 tree？

把上面的直觉提炼成两个"利（pro）"：

- **支持 mesh 的理由**：更便宜、更容易运维，而且可以做得很快——你只需要做 **tensor parallel**（邻居间通信就够了）；
- **支持 tree / all-to-all 的理由**：对**非结构化通信**更友好——典型例子就是 **expert parallel（专家并行）**，token 会被路由到不同专家，通信模式完全取决于数据。

这也是 Bill Dally 和 Jeff Dean 讨论过的硬件分工：**GPU 适合 mixture of experts**（MoE）这类通信不可预测的工作负载（token 路由到不同专家）；**TPU 适合密集模型（dense model）**——如果你做的切分是"可预测的"，那就是后面要讲的 **tensor parallel**。

### 但事情在变化：TPU 8i / 8t

这个二分法本来是今天早上之前我打算停在的地方——结果 Google 就在今天早上发布了 **TPU 8i** 和 **TPU 8t**。我备课看到这个的时候心想："哇，TPU 8i 是树状拓扑，他们转向了更 all-to-all 的连接方式。"仔细想想这完全合理：**现代语言模型都是 MoE**。如果你要**服务**一个 MoE，token 在专家之间路由时会有大量带宽飞来飞去，推理时这些通信就是真正的瓶颈，你确实需要更强的连通性来应对。就连训练芯片 **TPU 8t** 的跨机架（cross-rack）连接也更像 GPU——他们正在构建一个叫 **Virgo** 的交换式（switched）高层网络栈，风格上接近 GPU 的 all-to-all 交换机。

所以我认为行业里正在发生很有意思的**趋同演化（convergent evolution）**：TPU 和 GPU 在彼此靠近，而真正的驱动者是**工作负载定义了网络**。

### 为什么不全连起来？华为 Ascend 910 的教训

最后一个硬件话题，我特别爱聊中国 AI 圈的事。还记得在 GPU 那一讲有人问："如果 SRAM 这么好，为什么不全都用 SRAM？"答案就是 Groq——它确实很成功。顺着同样的思路你可能会想：**如果 all-to-all 连接这么好，为什么不把一切都连起来、用很快的光纤芯片？**——那么你就会得到 **华为昇腾 910（Huawei Ascend 910）**。

昇腾的规格非常有意思：单看每一颗芯片，它比 H200 差得多——矩阵乘慢、很多方面都慢；但如果你愿意专门腾出**一整个巨大的光纤交换机机架**去连接数量大得多的芯片（昇腾的方案是一个大机架里连 **384 颗**），你就可以用"数量补质量"来抵消单芯片慢的劣势。

这揭示了一个很有意思的权衡：一旦你看到这个架构，就会意识到它的**功耗高得离谱——是同规模 Nvidia 系统的 4 倍**。换句话说：**只要愿意付电费，你可以"暴力"解决很多通信问题、把规模激进地扩展到 300 多颗芯片，但你要为功耗买单**。这和 SRAM 的故事如出一辙：如果你想要一个在功耗和制造上都高效的设计，你会落在一个位置上；如果你想暴力破解，你落在完全另一个位置上。这是很值得品味的一组硬件设计权衡。

## Part 1 小结

把第一部分收一下尾：

- 首先，**计算的新单位不是 GPU，而是整个数据中心（datacenter）**；
- 我们对多机扩展的期待有两件事：**线性显存缩放**（能装下的最大模型参数量随 GPU 数线性增长）与**线性算力缩放**（模型 FLOPs 随 GPU 数线性增长）；
- 以及上面复习过的一套**简单集合通信原语**。

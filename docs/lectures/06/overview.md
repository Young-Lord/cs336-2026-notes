# 开场与回顾：GPU 硬件与编程模型

欢迎回到课堂。上一讲（第五讲）Tatsu 出色地概述了 GPU 的高层图景——如何思考性能、以及 GPU 带来的各种“怪癖”。本讲是它的延续，但视角要从“看图”转向“写代码”：我们会**更深入代码**，亲手编写一些 **Triton kernel**，并做**基准测试（benchmarking）与性能剖析（profiling）**。课程开始前，Percy 先快速回顾了 GPU 的硬件图景，帮大家把上一讲的知识捡起来。

## GPU 硬件回顾：一张简化图

下面是一张典型的 GPU 简化示意图（左侧是主机的内存，右侧才是真正的 GPU）。理解它的关键在于记住 GPU 的**容量特征（characteristics）**：

![](/lectures/06/gpu-hardware.png)

我们讨论的是 **NVIDIA GPU**（Tatsu 上一讲也提到了 TPU、AMD 等，但本讲聚焦 NVIDIA）。NVIDIA 已经历了好几代产品，从 **A100** 到 **H100** 再到 **B200**。每一代 GPU 内部都有若干**流式多处理器（streaming multiprocessor，SM）**，其数量大约在 **100 到 200 之间**——这个数字历代变化不大。再看每个 SM 内部：

- **寄存器（register）**：例如 B200 每个 SM 有 65,536 个 32 位寄存器，合计 **256 KB**，这一容量历代也几乎没变；
- **L1 缓存与 shared memory**：注意这两者是**同一块物理内存**——shared memory 你可以自己控制，L1 不行。它们按 SM 配置，大小也在同一个量级；
- **L2 缓存**：这不是每 SM 一块，而是**整个芯片共享**，容量更大一些；
- **高带宽内存（high-bandwidth memory，HBM）**：容量最大，而且**这个数字历代涨得很快**。

上表的具体数字，下面用规格表完整呈现（A100 / H100 / B200）：

| 加速器 | A100 | H100 | B200 |
|------|------|------|------|
| SM 数量 | 108 | 132 | 148 |
| 寄存器大小（每 SM） | 256 KB | 256 KB | 256 KB |
| L1 缓存 + shared memory（每 SM） | 192 KB | 256 KB | 256 KB |
| L2 缓存大小 | 40 MB | 50 MB | 96–126 MB |
| HBM 大小 | 80 GB | 80 GB | 192 GB |
| 寄存器带宽 | 约 116 TB/s | 约 401 TB/s | 约 447 TB/s |
| L1 缓存 + shared memory 带宽 | 约 19 TB/s | 约 33 TB/s | 约 19 TB/s |
| L2 缓存带宽 | 约 5–8 TB/s | 约 12 TB/s | 约 9 TB/s |
| HBM 带宽 | 2 TB/s | 3.35 TB/s | 8 TB/s |

除了容量，还要关注**带宽**：内存层级中的速度与容量大体成**反比**。寄存器非常快，L1 略慢一点，L2 更慢，HBM 最慢——当然，B200 的 **8 TB/s** 放在大背景下仍然不算慢。总结成一句要在脑子里扎根的话：

> **大而远的内存慢；小而近的内存快。**容量大、离计算单元远（比如 HBM）的内存，带宽最低；容量小、位于 SM 内部（寄存器、L1）的内存，带宽最高。

顺带一提，还有几样“看不见”的硬件：H100 与 B200 还有**线程块簇（thread block clusters）**——线程块的簇，支持一定程度的分布式共享内存；B200 还为 tensor core 引入了**张量内存（tensor memory，TMEM）**，位于寄存器与 shared memory 之间。这些对程序员大体不可见，本讲入门阶段不细究。

## 编程模型：线程、线程块与网格

那么，怎么给 GPU 编程？编程模型如下：最基本的概念是**线程（thread）**——每个线程在一小块数据上执行一段代码（图中每一根箭头都可以看作一个线程）。线程被组织成**线程块（thread block）**，也叫**并发线程数组（concurrent thread array，CTA）**——一组线程。最后，若干线程块组成**网格（grid）**。当你**启动（launch）一个 kernel** 时，实际上就是启动一个由线程与线程块组成的网格，让它们同时做计算。

这就是全部编程模型了——简单、干净。但在动手之前，值得先回答一个问题：

### 为什么需要线程块？

一个很自然的疑问是：为什么不能只有“网格 + 线程”，让每个线程随便拿一块数据算完就完事？答案是：**如果你只做逐元素（elementwise）运算，这样确实够了**。例如 **GeLU** 就是逐元素应用的激活函数，线程模型非常自然——每个线程处理一个元素，就像写一个 `for i in range(...)` 的循环，$f(i)$ 对 $i = 0, \dots, N-1$ 逐一计算。

但对于需要**线程间通信**的运算，比如 **softmax** 或**矩阵乘法**，这个视角就不够了。严格说，它“够”的前提是你愿意支付反复读写 HBM 的代价：例如矩阵乘，可以让每个线程负责输出矩阵的一个元素，直接读写 HBM——但前面已经强调过，HBM 很慢，这不是好策略。

所以正确的做法是使用 **shared memory**——它位于 SM 内部、局部于该 SM。线程块的意义正在于此：**一个线程块 = 一组共享同一块 shared memory 的线程**。于是，一个线程块会被调度到**某一个 SM** 上，它的工作方式是：从 HBM 读入一批数据 → 处理（处理过程可能涉及线程之间通过 shared memory 的通信）→ 写回。这正是后面要讲的 **tiling** 的整个“游戏”。

事实上，**Triton**（本讲主要的 kernel 编写方式）就是**原生以线程块为单位思考**的——一旦你习惯了用线程块来思考，一切都会顺理成章，生活会轻松很多。

## 编程模型与硬件的交互

编程模型本身是硬件的**抽象**，它非常好用：你只需要知道“有一堆线程块，定义它们，再定义每个块里的线程要做什么计算”，写起来就像写 Python。**如果只关心正确性，知道这些就足够了。**

但在实践中，**性能对硬件极其敏感**——本讲讨论 GPU 与 kernel 的全部理由，就是想榨出性能。于是有两个层面：理解**计算**只是编程模型的一部分；而它**跑多快**，则强烈依赖于硬件。

# 数据并行与 ZeRO：把显存摊到所有 GPU

进入本讲主体：标准的大语言模型并行化原语。大致可以归成三类：

1. **数据并行（data parallelism）**——朴素数据并行（naïve data parallel）与 **ZeRO** 的 stage 1 到 3；
2. **模型并行（model parallelism）**——流水线并行（pipeline parallel）与张量并行（tensor parallel）；
3. **激活并行（activation parallelism）**——序列并行（sequence parallel）。

我们先从最直觉的数据并行讲起。

## 朴素数据并行：把 batch 分下去

想象我们在做朴素的随机梯度下降（SGD），参数更新为

$$\theta_{t+1} = \theta_t - \eta \sum_{i=1}^{B} \nabla f(x_i)$$

也就是把大小为 $B$ 的 batch 里每个样本的梯度加起来，沿负方向走一步。**朴素数据并行**的做法很直接：把大小为 $B$ 的 batch **切分成 $M$ 份**分给 $M$ 台机器，每台机器在自己那一份样本上算梯度，然后**交换（all-reduce）梯度**来同步，再做更新。

这套方案的表现如何？

- **算力缩放**：每块 GPU 只算 $B/M$ 个样本，算力随机器数线性扩展——这部分没问题；
- **通信开销**：每个 batch 需要传输**约 $2 \times$ 参数量**的数据（一次全量梯度的 all-reduce），只要 batch 足够大、通信可以摊薄，就还说得过去；
- **显存缩放**：**完全没有**。每块 GPU 至少需要持有完整的参数量，复制了模型的所有副本。

所以问题来了：显存似乎是个大麻烦。我们把模型参数复制到每块 GPU 上，再仔细看看账目。

## 显存记账：五份拷贝，每参数 16 字节

我们的显存处境**不是不好，而是非常糟糕（terrible）**。原因是你需要存的东西远不止参数本身。粗略的经验法则是（具体取决于精度）：**我们需要约 5 份权重的拷贝、每参数 16 字节**。逐项看：

| 存的是什么 | 大小（每参数） |
|------|------|
| FP16/BF16 模型参数 | 2 字节 |
| FP16/BF16 梯度 | 2 字节 |
| FP32 主权重（master weights，SGD 累加的目标） | 4 字节 |
| Adam 一阶矩估计（first moment） | 4 字节（或 BF16 2 字节） |
| Adam 二阶矩估计（second moment） | 4 字节（或 BF16 2 字节） |

其中"FP32 主权重 + 两个矩"这一坨就是我们常说的**优化器状态（optimizer state）**。你可能会想："主权重为什么是 FP32？"因为数值稳定性——你在 FP32 里做累加，避免低精度累积误差。而 Adam 要追踪梯度的一阶、二阶矩，而且是**跨时间**追踪，所以必须一直存着两个矩。

把账算完你会发现：**优化器状态是显存的最大头**。训练一个模型，你存储成本的大头不是模型本身，而是优化器状态。这就引出了这一讲第一个真正优雅的想法：能不能**用结构化的方式把这些显存摊到各块 GPU 上**，从而"几乎免费"地拿到显存收益？

## ZeRO 的核心思想：切分昂贵的部分

**ZeRO**（Zero Redundancy Optimizer）解决的就是数据并行里"显存开销冗余"的问题。它的核心思想有两句话：

> **把昂贵的部分（优化器状态）切分（split）开来，并利用"reduce-scatter + all-gather"与 all-reduce 的等价性。**

看这张经典的显存构成图（绿色是优化器状态，占大头；橙色是梯度；蓝色是参数，参数与梯度大小相同，状态比它们都大）：

![](/lectures/08/slide-18.png)

如果做**朴素数据并行**，每一块 GPU 都要复制这一整份（参数 + 梯度 + 优化器状态），显存消耗随加速器数量**线性增长**——这显然很浪费。而我们可以逐级切分：

- 只切**优化器状态**——很大一笔节省；
- 再切**梯度**——又是一笔；
- 极端情况下**切一切**（参数、梯度、优化器状态全切）——图最右边显示的显存收益非常戏剧化，从 baseline 的 **120** 一路降到 **1.9**。

当然天下没有免费的午餐：越往下切，要付出的通信代价越大。而**最了不起的地方在于，其中很大一部分其实是"免费的"**——下面我们一步步看。ZeRO 的三个 stage 正好对应这三种切法。

## ZeRO stage 1：切优化器状态

**stage 1 是最简单的**：只切**优化器状态**，把它分散到各 GPU 上。每块 GPU 仍然持有**完整的参数和完整的梯度**。于是可以这样想：**每个 worker 负责更新参数的一个切片（slice）**——如果你是 GPU 0，你只负责更新最前面那一小片参数，其他 GPU 负责别的片。

怎么运作？四个步骤：

1. **每个人在自己的数据子集上算出完整梯度**（因为数据并行，每个人拿的是不同的数据项）；
2. **reduce-scatter 梯度**：把你的梯度切块、分发到所有其他机器——别人不需要你的全部梯度，只需要与它们负责更新的那部分参数对应的梯度片。这一步的通信量是**一个参数量**；
3. **每台机器用自己收到的梯度 + 自己维护的状态更新自己负责的参数片**；
4. **all-gather 参数**：我负责的那 $\tfrac14$（举例）参数已经更新好了，把它们发给其他所有人。这又是一次**一个参数量**的通信。

![](/lectures/08/slide-20.png)

### 通信量与显存：为什么 stage 1 是"免费"的

把 stage 1 和朴素 DDP 并排对比：

| | 朴素 DDP | ZeRO stage 1 |
|------|------|------|
| 通信原语 | 一次 all-reduce（梯度） | 一次 reduce-scatter（发梯度）+ 一次 all-gather（收参数） |
| 通信成本 | $2 \times \#\text{params}$ | $2 \times \#\text{params}$ |
| 显存 | $(4+K) \times \#\text{params}$ | $(4 + K/N_{\text{gpu}}) \times \#\text{params}$ |

其中 $K$ 表示"每个参数除参数本身之外还要存几份拷贝"（比如 Adam 下 $K=12$）。关键观察：朴素 DDP 里我们要做一次 all-reduce；stage 1 里我们做 reduce-scatter + all-gather——而前面复习过，**reduce-scatter + all-gather 与 all-reduce 等价**。所以 stage 1 的通信特性与朴素 DDP **完全相同**，却拿到了显存收益：

> **在带宽受限的情形下，ZeRO stage 1 是免费的——通信不增加，显存省一大截。**

## ZeRO stage 2：顺手把梯度也切了

受此鼓舞，stage 2 说：**我们连梯度也切了**（图上那一片粉色）。

- 高层想法：除了优化器状态，把**梯度**也 shard 到各机器上，用与 stage 1 类似（粗略）的技巧；
- 复杂之处：我们**再也无法实例化一个完整的梯度向量**了，但每个 worker 仍然要**算出完整梯度**（毕竟我们还是数据并行）。

怎么绕过去？这其实只是一个**系统技巧**。关键改动是：不再一次性物化整个梯度向量，而是**增量地**走：

1. 每个人**逐步**在计算图上反向（incrementally backward）：
   - **第 1a 步**：每算完一层的梯度，立刻做一次 reduce，把它发给**负责该层的 worker**；
   - **第 1b 步**：一旦某个梯度在反向图中不再被需要，**立刻释放**它；
2. 每台机器用自己收到的梯度 + 状态更新自己负责的参数；
3. **all-gather 参数**。

增量地算、增量地发，和一次性算完再发，总通信量**完全一样**——所以 stage 2 同样是（几乎）免费的。

## ZeRO stage 3（又名 FSDP）：切一切

最后也是最刺激的一步：**把参数也切了**——参数、梯度、优化器状态全部切分。这是我最初学到时觉得像魔法一样的东西。

核心想法和 stage 2 一脉相承：**边遍历计算图边按需（on demand）发送/请求参数**。这真的很棘手，因为任意时刻，每块 GPU 只看到参数、梯度、优化器状态的**一个切片**。这就是 **ZeRO stage 3，又名 FSDP（Fully Sharded Data Parallel，全分片数据并行）**——凡是在 PyTorch 里并行化过东西的人应该都见过它。

### 底层是怎么跑的（baby 版）

看这张图：从左到右是整个更新流程，顶部和底部是两块 GPU：

![](/lectures/08/slide-25.png)

- **前向**：先 **all-gather** 这一层的权重（从所有 GPU 收集分片、拼成完整权重），做这一层的前向，然后**立刻释放权重**——因为前向已经做完，不再需要这些参数；
- **反向**：现在需要本层的激活（一直保留着）和本层参数。**按需 all-gather 参数**，做反向；一拿到梯度就 **reduce-scatter** 把梯度散回去，然后**再次释放权重**；
- 对每一层重复这个"抓参数 → 计算 → 释放"的过程，最后更新权重。

### 通信成本

数一下一共用了多少通信：**两次 all-gather（$1\times\#\text{params}$ 每次）加一次 reduce-scatter（$1\times\#\text{params}$）**，合计 $3\times\#\text{params}$。对比朴素 DDP 的 $2\times\#\text{params}$，这多了 $1.5$ 倍——似乎不太好，而且每个层都在做通信，似乎开销巨大。

但有两个关键想法让 FSDP 几乎"开销无关"：

1. **增量计算/通信 + 立即释放**：我们见过了——边遍历计算图边做必要通信，随后马上释放内存；
2. **重叠计算与通信（overlapping communication and computation）**：这是还没讲过的第二个想法。

看这张来自 PyTorch FSDP 架构论文的图（从上到下分别是 CPU 侧、GPU 计算侧、GPU 通信侧的时间线）：

![](/lectures/08/slide-26.png)

流程是：先 all-gather 第 0 层参数，才能做第 0 层前向；**但在做第 0 层前向的同时**，我们请求第 1 层参数（all-gather 第 1 层）——于是通信被前向计算**掩盖**（mask）了。这就是图里那个重叠：$(W_1 W_0 + W_2 W_0)x = y$，第 1 层参数在算第 0 层时就已经在路上。通信不再"阻塞"计算，FSDP 因此近于免费。

> **课堂问答一：每块 GPU 都有每一层的一部分吗？**
>
> （同学：你是说每块 GPU 都有每一层的一部分，优化器就是为这个而存在的？）
>
> **Tatsu**：对，就是这样。图里的画面是：参数、梯度、优化器状态全都 shard 在不同的 GPU 上。对没有第 0 层的 GPU，我会先"索要"第 0 层参数、做完整计算，再进入下一层。计算本身和朴素数据并行完全相同——只是每个计算操作之间夹着"请求参数、释放参数"。

> **课堂问答二：通信成本为什么没有被层数乘起来？**
>
> （同学：通信成本不应该是层数那么多倍吗？）
>
> **Tatsu**：对，操作**次数**确实随层数乘起来了。但**每一段通信都更小**——这里通信的只是一小个 MLP 的参数，而我对比的是"把整个网络做一次 all-reduce"的代价。分片之后，每一层各自的通信加起来，总量仍是 $O(\#\text{params})$ 级别。所以没问题。

## ZeRO 在实践中：装得下吗？

上面讲的都是"每参数多少字节"。做个具体计算。假设我们做**纯 BF16 训练**（配合 Kahan summation 来保证累加精度，这在现代大规模训练里是可行的），优化器状态可以瘦身：**除主权重外全部用 BF16**，于是每参数共 **12 字节**：

$$\underbrace{2}_{\text{参数}} + \underbrace{2}_{\text{梯度}} + \underbrace{4}_{\text{FP32 主权重}} + \underbrace{2}_{\text{一阶矩}} + \underbrace{2}_{\text{二阶矩}} = 12 \text{ 字节}$$

在 8 卡 A100 80G 的机器上（单卡 80 GB），每个 stage 能装下的最大参数量是"80 GB ÷ 每参数字节数"：

| 方案 | 每卡能装的最大参数量 | 每参数字节数公式 |
|------|------|------|
| Baseline（朴素 DP） | 6.67 B | 12 |
| ZeRO stage 1 | 16 B | $2 + 2 + \frac{8}{8} = 5$ |
| ZeRO stage 2 | 24.62 B | $2 + \frac{2 + 8}{8} = 3.25$ |
| ZeRO stage 3 | 53.33 B | $\frac{12}{8} = 1.5$ |

各阶段每参数字节数的核算如下：

- **Baseline**：全部复制，12 字节/参数；
- **ZeRO stage 1**：只切优化器状态（8 字节：主权重 4 + 一阶矩 2 + 二阶矩 2），剩下参数 2 + 梯度 2 仍全量，于是 $2 + 2 + 8/8 = 5$；
- **ZeRO stage 2**：梯度也切，于是 $2 + (2 + 8)/8 = 3.25$；
- **ZeRO stage 3**：一切皆切，$12/8 = 1.5$。

于是从 baseline 连 7B 模型都放不下（单卡 6.67B），到 ZeRO stage 3 可以装下 **53B** 级模型——用 FSDP 装大模型容易太多了。

> **课堂问答：在别的卡上呢？**
>
> （同学：在 8×A100 上是这些数，那在 H100 或 H200 上会怎样？）
>
> **Tatsu**：我不能心算"乘以 141 再除以 80"这种题，但 H200 就是 141 GB，直接线性缩放：把上面所有数字乘以 $141/80 \approx 1.76$ 就行。从一种加速器换到另一种，数学基本不变，就是线性关系。

## 数据并行的两个遗留问题

FSDP 很干净、很优雅——我真希望课就到这里结束了。但不幸的是，我们得继续进入更"丑陋"、更棘手的部分。有两个原因：

### 问题一：数据并行消耗的是 batch size 这个资源

数据并行在某种意义上消耗着一种重要资源——**batch size**。如果 batch size 是 8，你**永远不可能用超过 8 块加速器**。你可能会想："那我们把 batch 越做越大不就行了？"——不行，因为存在一个**临界 batch size（critical batch size）**：当 batch 大到某个点之后，增加一个 batch 元素带来的收益，**小于单独再走一次 SGD 步**。

在小 batch 区域，加元素等同于多走几步，完全有益；但过了临界点，收益开始递减——**无穷大的 batch 并不比无穷多步更好**。于是我们面对一个硬权衡：**想要小 batch（优化更好）就得让 GPU 更空闲；想要大 batch（GPU 利用率高）就得承受优化上的损失。**

### 问题二：ZeRO 的显存收益有限

另一个问题是显存。ZeRO stage 1、2 几乎不让你的显存扩展；stage 3 能切参数，但**它完全不减少激活（activation）显存**。要想真正把显存压下去，我们需要更细粒度地切模型——这就是下一节"模型并行"的动机。

**模型并行**的概念其实和 FSDP 类似：把参数切到各 GPU 上。但有一个关键的概念差异：

> **FSDP 切参数，但传的还是参数——它只是层"包装"（wrapper），计算本身没变，只是计算前把参数传来传去。而模型并行要通信的是激活（activations）。**

举个例子：如果第 $i$ 层住在 GPU 0、第 $i+1$ 层住在 GPU 1，那我们需要通信的是两层之间的**激活**。模型并行有三种切法，对应三种并行策略：**流水线并行**（切层）、**张量并行**（切矩阵）、**专家并行**（切专家）。

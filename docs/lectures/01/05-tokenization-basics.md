# Tokenization 基础

讲完课程大纲，Percy 正式进入本讲第一单元：**tokenization**。他先推荐了 Andrej Karpathy 那个关于 tokenization 的视频，让大家课后一定去看看。

## 起点：文本是字符串，语言模型操作的是 token

出发点很简单：**原始文本是 Unicode 字符串**；而另一方面，**语言模型是在 token 序列上建立概率分布**的，这些 token 通常用整数索引来表示。例如 `"Hello, 🌍! 你好!"` 这样的字符串，经过编码后得到的是形如 `[15496, 11, 995, 0]` 的索引序列。因此我们需要两个过程：一个把字符串**编码（encode）**成 token，另一个把 token **解码（decode）**回字符串。所谓 tokenizer，就是能够完成这趟**往返（round trip）**的东西。Percy 强调："如果你实现的 tokenizer 不能往返，那你就有麻烦了。"检查的方法很直接：对同一个字符串，先 encode 再 decode，然后断言结果与原字符串一致（相当于代码里的 `assert string == reconstructed_string`）。

为了让大家对 tokenizer 的行为有个感觉，他本想演示一个交互式网站（可以在上面试不同 tokenizer），但临时发现没有网络——"我该早点试网络的，所以这个演示没法做了"——于是转而直接给出几个观察。

## 三个观察：tokenizer 为什么让人头疼

- **带前导空格的词是不同的 token**：一个词和它前面的空格是同一个 token（比如 `" world"`）。你会看到大量 token 其实都是"空格 + 词"的形式，这没什么不对，但确实有点奇怪。
- **"hello" 的两种形态互不相干**：出现在句首的 hello 和出现在句中的 hello，是两个**完全不同的索引**，彼此毫无关系。
- **数字的处理很随意**：取决于 tokenizer，数字有时每几个数字就是一个 token，有时可预测、有时不可。有些 tokenizer 试图让每个数字单独成一个 token，但那会把 token 数量撑爆——所以这里有个取舍。

Percy 说，这些观察会让你体会到为什么 tokenizer 有点烦人、为什么人们想摆脱它。

## GPT-5 tokenizer 与压缩率

Percy 现场展示了 OpenAI 的 **GPT-5 tokenizer（来自 tiktoken 库）**。它把 `"Hello, 🌍! 你好!"` 编码成一串索引，再解码回字符串，能够完美往返。这里引出了**压缩率（compression ratio）**的概念：

$$ \text{compression ratio} = \frac{\text{bytes}}{\text{tokens}} $$

在这个例子里，字符串一共 20 字节、被切成 8 个 token，于是压缩率是 $20 / 8 = 2.5$，即 **2.5 bytes per token**。**压缩率越大，序列就越短，这是好事**——因为 attention 的计算量随序列长度二次增长，你当然希望序列尽量短。理论上，你可以通过**增大词表大小**来提高压缩率，但那样会陷入**稀疏性(sparsity)**问题：词表里的每个元素都被当作一个不同的元素来对待。如今，尤其是多语言的 tokenizer，词表通常有 **10 万到 20 万个**不同的 token。课堂上本来可以顺带看一眼 GPT tokenizer 的实际词表长什么样，不过为了节省时间，Percy 略过了这一步。

## 为什么不能直接用字符、字节或词？

接下来 Percy 快速过了一遍"不那么好"的 tokenizer，说明为什么需要 BPE。

**字符级 tokenizer。** Unicode 字符串本身就是字符序列，每个字符可以通过 Python 的 `ord` 转成一个整数(code point)，再用 `chr` 转回来。例如 `ord("a") == 97`、`ord("🌍") == 127757`。Unicode 大约有 **15 万个字符**，所以词表可能高达 15 万——这还不算太疯狂，但更大的问题是：**许多字符其实非常稀有**（比如 🌍），把它们放进词表是非常低效的。再加上压缩率也不理想，大部分时候你要用大量 token 去表示序列，而词表里很多条目根本用不上，这就成了一种浪费。Percy 的评价是：这个 tokenizer 是"最糟糕的两者结合"——**词表又大，压缩率又低**。

**字节级 tokenizer。** Unicode 有 UTF-8 编码：有的字符只占一个字节（比如 `a`），有的占多个字节（比如 🌍 在 UTF-8 下是 `f0 9f 8c 8d` 四个字节）。于是可以构建一个基于字节的 tokenizer：把字符串转成字节序列——注意，转换后的序列**更长**了，但所有数字都落在 **0 到 255** 之间，因为"字节"的含义就是这样。字节级 tokenizer 的词表只有 **256 个值**，非常小；但压缩率恒等于 **1**，"非常糟糕"——字节序列会很长，而 transformer 的上下文长度又有限（attention 是二次的），这看起来可不太妙。

**词级 tokenizer。** 这是经典 NLP 的做法：用空格或正则表达式把字符串切成词块。它的好处是**每个 token 都有意义**——因为词是人类发明的，往往有稳定的语义。但词表大小等于训练数据中不同块的数量，可能非常大，甚至**实际上无界**：测试时你会遇到没见过的 token，过去的人们会给它一个特殊的 **UNK token**——这很难看，还会搞乱困惑度计算。所以这条路也不太行。

# 大规模推理服务：内核 bug 与缓存感知路由

## 分离式部署：prefill 与 decode 各用各的 worker

前文说过，prefill 计算受限、decode 访存受限，两者耗时结构也不同。于是行业里几乎都开始采用一个很基础的优化：**把 prefill 放到一组 worker 上、把 decode 放到另一组 worker 上**，让两段计算各自针对不同的软硬件栈专门化。

这个"分离"还催生了硬件层面的创新。Dan 提了一个很有意思的例子：

- **NVIDIA 收购了 Groq**——GPU 之王买下这家做"LPU"（language processing unit）的新芯片公司。一个重要的收购理由就是：**decode 工作负载与 prefill 差别太大**，对 decode 这种负载，你可以用完全不同的芯片。NVIDIA 的下一代硬件计划是：**GPU 做 prefill 侧，Groq 的 LPU 做 decode 侧**；
- 类似地，**Cerebras**（OpenAI 有 compute partnership）也是另一款在 decode 上强得多的芯片；
- 还有 **SambaNova** 等公司，也在推理链条的各个位置下注。

简而言之：因为两段计算的特征如此不同，硬件生态开始"分而治之"。

## 大规模系统里的恶性 bug

当推理引擎真的部署到大规模（每天服务**万亿级 token**）时，你会遇到一些非常讨厌的 bug。Dan 展示了一组案例（大多发生在大约一年前，出现在某些开源推理引擎里）。这些 bug 有一个共同特征：**小规模下运行良好、一到大规模必然出问题**——涉及的事件概率大约在 $10^{-8}$ 甚至更低的量级。

### 例一：NaN 让模型开始复读

有时某个 kernel 只有极轻微的错误，但触发它的条件极其罕见（比如某类特定的数值路径）。一旦触发，你的 logits 会在计算中途**变成 NaN**。我们后来发现：**一旦出现 NaN，模型就会开始输出同一个 token**——某个模型的输出会一直"hi hi hi hi"，另一个则一直输出感叹号，就这样陷进死循环。

### 例二：工具调用处理的"死亡循环"

工具调用（tool call）指的是模型说"我要做个网络搜索"、然后由外部的 harness 用老式代码去真正执行搜索。某次有人改动了一个引擎处理工具调用的方式，于是工具调用不再被正确处理。症状是**完成长度（completion length）暴涨**：模型正常时应该说"我要搜索，我说完了，去执行吧、回来给用户结果"；现在它却不会正确返回，只能一遍遍说"我要搜索、我要搜索、为什么没有搜索发生"——陷入几万个 token 的死亡循环。

### 例三：神秘的"突然说中文"

这个案例很有趣，因为它一度**同时放倒了好几家推理提供商**。最开始它被归咎于量化问题，但实际上是一个隐蔽得多的 bug：模型会**毫无缘由地随机开始输出中文字符**。当时有人猜测"是不是模型微调过中文模型"——你问它英文，它却开始用中文回答。真相是：某个 kernel 里有一个 **off-by-one 错误**——有时会多读入一块**未初始化的内存**，把它送进注意力，一路算到最后得到一个随机的中文字符；然后模型想："我为什么突然开始想中文？用户一定是在用中文问我问题"，于是整个模型就跑偏到中文上去了。

所以 Dan 的告诫是：有时模型说中文是因为它**真的被训练成那样**；有时仅仅是因为**某人代码里的一个 off-by-one 错误**。这两种情况要分清楚。

## KV cache 的分层存储：GPU → CPU → 磁盘

接着讲生产系统中 KV cache 的存储问题。Dan 的观点很直接：**运行大型生产系统的核心目标之一，就是让 KV cache 尽可能大**——最好能把来自不同用户、或同一用户跨不同会话的请求都缓存下来，从而同时运行尽可能多的会话。

存储的层次结构是这样的：

1. **先放在 GPU 显存**——很快就把显存用完了；
2. **放到 CPU 的 DRAM**——如果你关注 Jensen Huang 最近的发布会，会发现他对 CPU 性能变得异常执着。原因之一是：**上一代 CPU 实在太慢了**，开始卡住很多重要工作负载。想象一台 5 亿美元的机器，却被上面那枚 1000 美元的 CPU 卡住脖子——这可不妙。而这种情况确实可能发生，比如**你的 KV cache 存在 CPU 内存里**，你就在乎能否快速把它读回来；
3. **再往磁盘（SSD）上放**——这时候你开始在乎 SSD 的空间与速度。你大概也听过"OpenAI 在疯狂扫货 SSD 和 DRAM"的传闻，部分原因正是**想存下尽可能多的 KV cache**。

于是，推理引擎内部在跳一支复杂的舞：某段 KV cache 很久没被访问了，就**驱逐**（evict）它——送到 CPU 内存、磁盘或某个全局存储；而当一个新请求进来、需要某段缓存时，又要去把它取回来、加载到 GPU 上，然后才能继续。

### 驱逐策略：LRU，还是预测未来？

有个同学问了一个很好的问题：**offloading 是不是只针对某一种特殊类型的工作负载？**（言下之意：那些特别快的东西是不是就不用被 offload？）

Dan 的回答把我们带回计算机科学的基本功：他开玩笑说"我敢肯定你们都没上过操作系统课，但你们真该去上"——因为眼前这个调度问题，**除了最右边是 GPU 之外，和 70 年代、80 年代的操作系统教科书图几乎一模一样**。当年的问题是：你在电脑上开了太多应用，CPU 内存不够了，就得把应用挪到磁盘上。**这正是同一个问题**。

处理办法也继承自操作系统：

- **启发式驱逐**：Dan 提到，AI 生成的幻灯片在左侧"幻觉"出了 **LRU（least recently used，最近最少使用）** 驱逐策略——其实这恰恰是一个相当不错的标准启发式（有操作系统方面的论文证明，LRU 的最坏情况在最优策略的 2 倍以内）；
- **预测未来（prefetch）**：当然，最理想的情况是**能预测未来**——你知道马上会来某种请求，就提前把对应的内存预取（prefetch）进来。预测未来并非不可能：比如你打开聊天应用、翻出一个**一个月前的旧对话**，这是一个非常强的信号——你马上就要开始问关于它的问题，于是你可以提前把那部分 KV cache 加载到 GPU 上。

说到底，这是一个"**你到底想往 GPU 上堆多少流量**"的问题。Dan 说，他从来没见过有人想让 GPU 上的流量更少——在满足前面那些 SLA 的前提下，**所有人都想尽可能多地服务流量**。

## 缓存感知的 prefill/decode 分离：两行代码的路由

接下来是 Dan 和他的团队（Together AI）几个月前发表的一项工作，名叫 **cache-aware prefill/decode disaggregation（缓存感知的 prefill/decode 分离）**。这是一个非常简单的优化——**在路由层只改两行代码**——却可能带来很大的效果。

基本观察是：进来的请求里，**绝大多数是对话中的后续轮次（turn）**。假设一个平均对话持续 10 轮、然后用户离开——那就意味着大约 **10% 的请求是全新的、很"新鲜"的请求**。

这两种请求的计算需求截然不同：

- 一个**全新请求**，动辄几千个 token，prefill 起来**昂贵得多**；
- 你**不想**让这样的长 prefill 和一个**对话进行到一半的短请求**混在同一批 GPU 上跑——比如某人贴了一整本书说"跟我聊聊这本书"，和另一个人正在问"1 加 1 为什么等于 2"（回答："因为数和数加在一起……"然后他又说"我没听懂"）。这种极短的问答，不该和极长的请求共用同一批 GPU。

于是可以写一个**极其简单的路由器**：

- 如果一个请求是全新的、**缓存命中率很低**，就把它送到**一组 GPU**，让这些长请求互相凑在一起处理；
- 把其他"热"（warm）请求送到**另一组 prefill 节点**。

Dan 报告的结果是：就凭这么简单的两行路由逻辑，**服务速度最多可以提升 40%**。

他还给了一个整体判断：就研究而言，我们现在**处于非常早期的阶段**。这类技术在 10 到 20 年后回头看，人们会说"这难道不是显然的吗，你们当时为什么还要讲"。但之所以现在值得讲，是因为**我们刚刚开始在生产里、以新的方式运行这些系统，看到新的流量形态**。

## 小结

这一节覆盖了"大规模推理服务"的几个侧面：**分离式部署与硬件专门化**（GPU 做 prefill、Groq LPU/Cerebras 做 decode）、**只有大规模才会冒出的内核 bug**（NaN 复读、工具调用死亡循环、off-by-one 导致的"突然说中文"）、**KV cache 的分层存储与驱逐预取**（GPU → CPU → 磁盘，LRU 与"预测未来"），以及一个简洁有力的路由优化——**缓存感知的 prefill/decode 分离能带来 40% 的提速**。下一节进入本讲的两个研究项目：MegaKernel 与循环语言模型 Parcae。
